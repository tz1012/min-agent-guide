    막힌 일을 찾아 허용된 수정과 재확인 이어가기

    실제 완료를 확인하고 다음 업무까지 연결하기

    정한 시간과 변화에 맞춰 에이전트가 먼저 움직입니다. 지금 쓰는 자료와 도구를 연결하고, 허용된 범위에서 확인·수정·재확인을 이어가는 시스템을 만듭니다.

    할 수 있는 일 보기 ↓구축 시작 방법
    하나·여러 개·전체 선택 개인·팀별 규칙으로 구성 2026-10-28 기준

    이 사이트에서 구축 자료를 받고, 내 환경에 접근할 수 있는 에이전트와 시스템을 만듭니다. 구축 후에는 선택한 접점으로 먼저 제안과 진행 결과를 받고, 필요할 때 요청하거나 방향을 바꿉니다.

    먼저 확인하고, 완료까지 이어가기

    이런 일을 맡길 수 있어요

    지식관리·라이프 관리·기업 업무 중 필요한 것을 하나, 여러 개 또는 모두 연결할 수 있습니다. 아래는 선택한 자료·도구·권한·규칙으로 구성할 수 있는 사용 예시입니다.

    K · 지식관리

    모은 자료를 지금 할 일의 근거로 연결합니다

    에이전트: “새로 모은 자료가 진행 중인 제안서와 관련 있습니다. 근거와 반영할 부분을 정리했습니다.”
    어떻게 처리하나요
    허용된 새 자료나 업무 변화를 확인하면 기존 위키와 대조하고, 관련 근거·상충 내용·활용할 다음 행동을 먼저 제안합니다. 허용된 문서 수정 뒤에는 실제 저장과 검색 결과를 확인합니다.
    무엇이 남나요
    출처가 붙은 지식·초안, 변경 근거와 다음 업무에 쓸 제안.
    L · 라이프 관리

    오늘 무엇부터 할지 먼저 제안합니다

    에이전트: “이번 주 목표와 남은 일, 오늘 일정을 확인했습니다. 제안서 검토부터 시작하면 좋겠습니다. 이유와 첫 행동은 다음과 같습니다.”
    어떻게 처리하나요
    정한 시각·상태 변화에 최신 목표·미완료·일정을 조회합니다. 막힘을 발견하면 허용된 수정과 재조회를 이어가고, 사용자의 판단이 필요한 부분만 묻습니다.
    무엇이 남나요
    이유가 있는 우선순위, 실제 완료 근거, 남은 일과 수정한 다음 계획.
    E · 기업 업무

    멈춘 업무를 찾고 다음 단계로 이어갑니다

    에이전트: “이 건은 자료 보완 단계에서 멈춰 있습니다. 허용된 자료로 초안을 보완했고, 담당자가 확인할 쟁점은 한 가지입니다.”
    어떻게 처리하나요
    지정된 요청·상태·기한 변화를 확인해 필요한 근거를 찾고 허용된 업무를 진행합니다. 반영 결과를 재조회하며 완료 증거가 부족하면 미완료로 유지하고 다음 행동을 제안합니다.
    무엇이 남나요
    처리 결과와 실제 완료 근거, 담당자에게 남은 판단, 변경·재확인 이력.
    C · 대화 보관·전사 — 선택 기능

    회의 뒤 할 일을 먼저 정리하고 추적합니다

    에이전트: “회의 기록을 정리했습니다. 후속 업무 두 건을 연결했고, 담당자가 불명확한 한 건만 확인이 필요합니다.”
    어떻게 처리하나요
    허용된 기록이 도착하면 전사·요약하고 결정과 후보를 구분합니다. 정한 규칙에 따라 후속 업무를 연결한 뒤 상태·완료 근거를 추적하며, 불분명한 담당·기한만 확인합니다.
    무엇이 남나요
    원문 근거, 연결된 후속 업무와 진행 상태, 다음 확인 시점.

    여러 흐름을 함께 쓰는 하루

    아침에이전트가 최신 목표·미완료 업무·일정을 먼저 조회하고, 오늘 우선순위와 이유·첫 행동을 제안합니다.

    낮정한 시간이나 상태 변화에 진행·막힘을 확인합니다. 허용된 수정 뒤 결과를 재조회하고, 다음 행동을 먼저 제안합니다.

    저녁에이전트가 실제 완료와 근거·남은 일을 먼저 정리하고 내일 계획의 수정안을 제시합니다. 판단에 부족한 부분만 묻고, 알림을 보낸 것만으로 완료 처리하지 않습니다.

    상황 확인→우선순위·행동 제안→허용된 수정→결과 재조회→완료 근거·다음 행동

    기본 설계는 사용자가 매번 묻기 전에 에이전트가 정한 시간·이벤트에 먼저 확인하는 운영입니다. 직접 요청도 함께 지원합니다. 조용한 시간·알림 빈도·실행 및 비용 상한·중단 조건을 정하며, 변화가 없을 때 무한 호출하거나 재알림하지 않습니다. 담당 서버가 꺼지면 실제 가능한 접수·대기만 표시하고, 복귀 후 오래된 계획과 상태를 다시 대조합니다.

    능동 운영·완료 추적의 설정과 검증 읽기 · 실행기별 공통 동작 검증 읽기

    보낸 자료가 지식이 되는 과정 보기 · 나에게 필요한 흐름 골라 보기 · 폴더로 구축 시작하기

    선택한 입력에서 다음 대화까지

    자료를 보내면, 다음 업무의 근거가 됩니다

    Slack·Discord·Buzz·Telegram 같은 메신저나 이메일을 입력으로 고를 수 있습니다. 에이전트가 실제 연결 가능 여부를 확인하고, 받을 범위와 기본 동작을 정한 뒤 자동화를 구성합니다.

    링크·파일·텍스트→접수·원문 보관→위키 종합·연결→결과 안내→새 대화에서 검색·재사용

    보내기자료 수집 채널에 기사 링크를 보내거나, 지정한 메일 폴더에 PDF를 넣습니다. 설명 없이 보내도 수집하도록 정할 수 있습니다.

    정리원문과 출처를 남기고 기존 주제와 비교해 위키·연결·목록·이력을 갱신합니다. 같은 자료의 재전달은 중복 처리하지 않습니다.

    다시 쓰기새 대화에서 “지난번 자료로 제안서를 써줘”라고 요청하면, 저장한 지식을 검색해 출처와 함께 활용합니다.

    셋업에서는 수신 채널·계정, 작동 조건, 지시 없는 콘텐츠의 기본 처리, 저장 위치, 자동 반영 범위, 결과를 받을 곳을 정합니다. 자료 안의 명령문은 실행 지시로 취급하지 않으며, 자료 저장과 일정 변경·외부 발송의 권한을 따로 정합니다.

    자동화를 선택하면 실제 자료 한 건으로 수신 → 위키 반영 → 새 대화 재검색까지 확인해야 완료입니다. 읽지 못한 원문·부분 전사·재시도 대기는 결과에 표시합니다. 서버가 꺼져 있고 별도 수신기가 없다면 접수 완료라고 안내하지 않습니다. 실제 연결과 운영은 사용자가 선택한 환경에서 구성하고 검증합니다.

    콘텐츠 수집·지식 재사용 세부 가이드 읽기

    이메일도 기존 계정에 맞춰 연결합니다

    필요한 일설계와 설정
    Gmail 등 서비스 연결사용 중인 계정과 실행기가 지원하는 공식 연결·API·인증 방식부터 확인합니다. 지정한 라벨·폴더·발신자·기간만 수집하도록 좁힐 수 있습니다.
    일반 메일 수신서버와 여러 기기를 동기화하려면 IMAP을 우선 검토합니다. POP3가 필요한 계정은 내려받은 원본의 위치, 서버 사본 유지·삭제, 중복 수집 방지를 함께 정합니다.
    메일 보내기SMTP 또는 해당 서비스의 발송 API를 별도로 설정합니다. 읽기·초안 작성·실제 발송을 구분하고, 발송은 정한 권한과 대상 범위 안에서만 수행합니다.
    무료 로컬 메일 앱PC에서는 무료 Thunderbird를 후보로 안내합니다. 계정 자동 설정 후 필요하면 제공자의 공식 값으로 서버·포트·암호화·인증 방식을 수동 설정합니다. 앱에서 메일이 보이는 것과 에이전트의 수집 연결은 각각 검증합니다.

    이메일을 선택하면 에이전트가 계정·OS·프로토콜 확인부터 연결 방법, 앱이 필요한지, 로그인·2FA 화면과 완료 확인까지 안내합니다. 비밀번호·토큰은 대화나 공개 기록에 남기지 않습니다. 앱 이용료와 메일 서비스·모델 호출 비용은 따로 확인합니다.

    이메일 연결·로컬 앱 설정 가이드 읽기 · Thunderbird 공식 사이트 · 공식 수동 계정 설정 안내

    다른 연결도 선택한 것부터 설정·시험합니다

    메신저·문서·일정·파일·회의 도구도 같은 절차를 따릅니다. 에이전트가 선택한 서비스의 공식 설정 방법과 실제 지원 기능을 확인하고, 계정·앱 등록·권한·연결·사용자 로그인에 필요한 작업을 안내합니다. 연결마다 수신·조회·반영·재조회 중 사용하는 기능을 시험하고, 완료·사용자 조치 대기·지원되지 않음·구축 대기를 구분합니다.

    첫 접점 하나가 성공해도 선택한 다른 연결이 모두 끝난 것은 아닙니다. 전체 선택 목록을 유지하고, 각 연결의 실제 검증을 마치거나 미완료 이유와 다음 행동을 남깁니다.

    Quick start

    구축 폴더를 받고, 에이전트에게 시작을 맡기세요

    공개 구축 문서·빈 기록 양식·검증 사례를 한 폴더로 제공합니다. 아래 ZIP을 받거나 에이전트에게 GitHub 주소를 알려줄 수 있습니다.

    구축 폴더 ZIP 받기 ↓ GitHub에서 구축 문서 열기

    에이전트용 시작 안내 읽기 — 사이트 주소로 시작하는 에이전트는 이 문서에서 구축 폴더와 읽을 순서를 찾을 수 있습니다.

    1

    공개 구축 폴더 열기

    ZIP을 풀어 guide 폴더를 작업 공간에 엽니다. GitHub를 읽는 에이전트는 저장소의 guide/ 전체를 확보합니다.

    2

    내 환경의 에이전트 선택

    Hermes는 적용 예시 중 하나입니다. OpenClaw·Codex·Claude·OmO 등 사용 중이거나 필요에 맞는 에이전트를 선택합니다. 다른 에이전트도 공통 계약과 실제 지원 기능을 확인하며, 구축 도구와 운영 실행기를 따로 정합니다.

    3

    시작 문구 보내기

    복사한 문구를 보냅니다. 에이전트가 환경과 진행 기록을 확인하고 질문에 따라 필요한 구성부터 구축합니다.

    사이트는 문서와 파일을 제공합니다. 웹 읽기만 가능한 에이전트는 설계와 실행 방법을 안내하며, 실제 설치·연결은 대상 환경에 접근할 수 있을 때 진행합니다.

    새로 구축할 때

    https://min-agent-guide.vercel.app/start.md 의 에이전트용 시작 안내를 읽고 내 시스템을 구축해줘.
공개 구축본은 https://github.com/tz1012/min-agent-guide 저장소에 있어.
guide/README.md → guide/AGENTS.md 순서로 읽고, guide/ 전체를 확보해 필요한 연결 문서를 따라가줘.
ZIP을 사용하면 압축을 풀어 guide 폴더를 열어줘. 이미 그 폴더를 작업 공간으로 열었다면 그 안의 README.md와 AGENTS.md부터 읽어줘.
실제 설치 대상과 현재 네 실행 환경·권한을 먼저 확인하고, 셋업 진행 기록이 있으면 실제 상태를 대조해 그 지점부터 이어가줘.
Hermes는 적용 예시 중 하나로 보고, OpenClaw·Codex·Claude·OmO 등 내가 사용 중이거나 필요에 맞는 에이전트를 선택해줘. 이 목록 밖의 에이전트도 공통 운영 계약에 맞춰 실제 제품·버전·지원 기능을 확인하고 진행해줘. 모든 제품이 같은 기능을 바로 지원한다고 가정하지 마.
웹 문서 읽기만 가능하면 실행 가능한 에이전트로 이어갈 설계·명령·진행 기록을 준비하고, 실제 설치한 것처럼 보고하지 마.
대화형 설계·운영 점검 문서에 따라 핵심 질문 하나씩 답변을 구조에 반영해줘.
전체 구성 요소와 연결을 보여 주고 현재 단계의 필수 결정이 모이면 허용된 구축을 시작해줘.
허용된 범위에서 설치·백엔드 구성·첫 업무 검증과 사용 안내까지 진행해줘.
지식관리·라이프 관리·기업 업무는 복수/전체 선택을 허용하고, 내가 선택한 전체 범위와 구축 순서를 따로 기록해줘.
필요한 설계와 제품 도입을 나눠 결정하고, 첫 업무 뒤에도 선택한 후속 흐름과 연결 검증까지 이어가줘.
콘텐츠 자동화를 선택하면 콘텐츠 수집·지식 재사용 문서에 따라 입력·작동 조건·기본 처리·저장·응답 규칙을 구성하고, 실제 자료의 수신→위키 반영→새 대화 재검색까지 검증해줘.
이메일을 선택하면 이메일 연결과 로컬 앱 문서에 따라 계정·OS·API/IMAP/POP3·발송 필요 여부를 확인하고, 필요한 로컬 앱 설정·로그인·2FA를 안내해줘. 메일 앱 동작과 에이전트 수집 연결, 읽기와 발송 권한은 각각 확인해줘.
메신저·문서·일정·파일·회의 등 다른 연결도 연결 대상별 설정 가이드에 따라 공식 방법·권한·로그인·사용자 조치를 안내하고 실제 동작을 검증해줘. 첫 연결 성공으로 전체를 완료 처리하지 말고 선택한 모든 연결의 상태와 다음 행동을 기록해줘.
능동 운영과 완료 추적 문서에 따라, 내가 매번 묻기 전에 정한 시간·이벤트에 최신 목표·미완료·일정을 조회하고 우선순위·이유·첫 행동을 먼저 제안하도록 구성해줘. 허용된 수정→결과 재조회→완료 근거 확인→다음 행동 제안을 이어가고, 부족한 판단만 질문해줘.
조용한 시간·알림 빈도·실행/비용 상한·중단 조건과 서버 OFF 동작도 설정해줘. 끝없는 모델 호출이나 재알림으로 구현하지 마.
실행기 독립 운영 검증 문서로 사용하는 제품·버전·구축 도구/운영 실행기를 구분하고, 실제 트리거·저장·재개·권한·수정·재검증을 시험해줘. 지침 파일을 읽었다는 이유만으로 어떤 실행기에서든 동작한다고 보고하지 마.
선택 구성 검토·최종 체크리스트에 따라 Jev와 Reason Network를 각각 도입/미도입/보류로 검토해줘. 결정·이유·대안·설정/시험 근거를 남기고, 보류이면 담당자·재검토 조건과 기한·영향을 적어줘. 설치를 필수로 취급하지 말고 기존 검증·운영 기록 안의 최종 구축 보고서에 정리해줘.
분류가 필요하면 분류 전용 프롬프트와 검증 문서에 따라 기존 모델+분류 전용 프롬프트를 먼저 비교해줘. 실행이나 완료 상태 변경 없이 판단 후보 JSON만 받도록 하고, 코드 규칙과 기존 모델 프롬프트를 같은 표본의 품질·비용·지연으로 비교해줘. Jev는 필요·권한·예산이 정해진 경우에만 같은 기준으로 추가 비교해줘. 선택한 분류 방식·프롬프트와 모델 버전·시험 근거를 최종 구축 보고서에 남기고, Jev 미도입도 이유와 대안을 기록해줘.

    운영 중 점검할 때

    이 폴더의 대화형 설계·운영 점검 절차로 현재 시스템을 점검해줘.
기존 설계·규칙·실제 설정과 최근 결과를 먼저 조회하고, 기대 동작과 차이를 찾아줘.
이미 허용한 범위의 수정과 결과 재확인을 이어가고, 판단이나 권한이 부족한 부분만 질문해줘.
완료 근거와 남은 일을 구분하고 다음 행동·다음 확인 시점을 먼저 제안해줘. 정한 실행·비용 한도나 중단 조건에 도달하면 그 상태와 재개 방법을 기록해줘.

    검토만 원하면 “설정 변경 없이 차이와 수정 제안만 정리해줘”를 덧붙입니다. 프롬프트 자체가 서비스·계정의 실행 권한을 늘리지는 않습니다.

    D05 · 기존 자료부터 확인

    Sheets와 Drive로 전체 DB를 구성할 수 있습니다

    Sheets에 구조화된 기록과 관계를 두고, Drive 파일 ID로 본문·원본·첨부를 연결하는 하나의 논리적 데이터베이스입니다. 필요한 데이터를 이 조합의 정본으로 정하면 별도 SQLite를 추가할 필요는 없습니다.

    역할Sheets + Drive 구성 예시
    구조화된 기록필요한 goals, tasks, documents, memories, skills, runs, events 표. 고정 ID·상태·관계·시각·파일 참조를 저장합니다.
    본문·파일Drive에 원문·전사·지식·스킬 본문·산출물·백업을 두고 표의 항목과 연결합니다. 파일 버전·소유자·보존을 함께 정합니다.
    실행기와 연결실행기는 필요한 원본을 읽고 허용된 변경을 반영합니다. 제품 고유 세션이나 로컬 캐시가 있더라도 같은 업무 상태의 정본을 두 곳에 만들지 않습니다.

    표 이름은 익명 예시입니다. 이미 쓰는 시트의 열·ID·관계·파일 연결을 먼저 읽고 재사용·보완 범위를 정합니다. 모든 표를 만들거나 기존 데이터를 옮기는 것이 첫 단계는 아닙니다.

    SQLite + 파일과 무엇이 다른가요

    좁은 화면에서는 표를 좌우로 움직여 두 구성을 비교할 수 있습니다.

    판단 기준Sheets + DriveSQLite + 파일
    기기·오프라인허용된 계정·네트워크로 여러 기기에서 접근. 문서의 오프라인 편집 설정과 에이전트 API 실행 가능 여부는 별도입니다.파일이 있는 장비에서 로컬 DB 사용. 다른 기기의 같은 업무 접근에는 연결 경로나 명시적 인계가 필요합니다.
    동시 쓰기·제약사람·에이전트가 함께 수정할 범위, 고정 ID·필수값·관계 검증·충돌 처리를 설계합니다. Sheets와 Drive를 가로지르는 원자적 변경은 별도 보완이 필요합니다.DB 내부 트랜잭션·제약을 사용할 수 있지만 DB별 쓰기는 한 번에 하나입니다. 외부 파일까지 하나의 DB 트랜잭션으로 묶이지 않습니다.
    권한파일·계정·공유 범위와 실행 주체를 정합니다. 탭 숨김이나 범위 보호를 행별 열람 격리로 취급하지 않습니다.OS 파일 접근과 이를 노출하는 서비스에서 권한을 집행합니다. 사용자·행별 권한은 별도 설계가 필요합니다.
    복구표와 연결 파일의 같은 복구 지점, 삭제·권한 회수·부분 반영·중복 재시도를 함께 시험합니다.일관된 DB 백업과 파일 사본을 함께 복원합니다. 실행 중 DB를 동기화 폴더로 여러 장비가 공유하지 않습니다.
    비용·한도선택 API·계정의 최신 쿼터와 요금, 저장 용량·Workspace·자동화·모델 비용을 따로 확인합니다.로컬 DB 호출 비용과 별개로 장비·전기·서버·접속·백업·모델 비용이 듭니다.

    셋업에서 차례로 확인합니다

    1. 이미 어떤 표·파일에 목표, 할 일, 기억, 실행 기록을 저장하며 무엇을 함께 연결하고 싶은가?
    2. 각 데이터의 정본은 어디이며, 누가 어떤 열·파일을 읽고 수정하는가? 개인·기업 자료는 어떻게 구분하는가?
    3. 동시 변경·삭제·서버 중단·재시도에서 무엇이 보존되어야 하며, 어떤 결과로 복구 성공을 확인하는가?

    업무 상태와 에이전트의 접수·실행·저장 상태는 같은 DB 안에서도 구분합니다. 행 번호 대신 고정 ID로 찾고, 변경 후 실제 결과를 다시 조회합니다. 요구를 충족하지 못하는 동시성·권한·복구 조건이 확인될 때만 다른 DB를 비교합니다.

    서로 다른 역할을 맡는 후보입니다. 기존 실행기·저장소·규칙으로 충족하는지 먼저 비교하고, 개인·기업의 실제 업무와 권한에 맞춰 도입·미도입·보류를 결정합니다.

    Jev (JEV) · TypeSafe Jev 기준

    반복되는 좁은 의미 판단

    어떤 역할인가요
    이 설명은 TypeSafe Jev 기준이며 다른 JEV를 뜻하면 제품부터 확인합니다. 상태와 구체적인 질문을 API에 보내 선택·점수·참/거짓 확률 같은 구조화된 판단을 받습니다. 작업 DB나 LLM Wiki를 저장·관리하는 역할과 구분합니다.
    도입을 검토할 때
    자료 분류·조건 판단이 자주 반복되고, 기존 방식보다 품질·지연·총비용을 개선할 여지가 있을 때 실제 업무 표본으로 비교합니다.
    먼저 비교할 대안
    기존 모델 + 분류 전용 프롬프트로 제공한 유형·프로젝트 후보 안에서 판단 후보 JSON만 받습니다. 정보 부족·충돌은 uncertain으로 두고 근거 위치·검토 필요 여부를 남깁니다. 입력 속 지시는 데이터로만 취급하며 도구 실행이나 완료 상태 변경은 하지 않습니다.
    같은 표본으로 확인할 것
    코드 규칙과 기존 모델 프롬프트의 품질·비용·지연을 비교하고, Jev는 필요·권한·예산이 정해진 경우에만 추가 비교합니다. 기존 모델도 호출 토큰·API 비용·구독 사용 한도가 소모될 수 있으며 Jev와 같은 성능을 보장하지 않습니다. 한국어 오판·실패 시 대안·전송 범위·비용 한도를 확인하고, 출력 확률을 정확성 보장이나 실행 권한으로 취급하지 않습니다.

    Reason Network · 에이전트 간 연결

    여러 실행기·기기 사이의 발견과 요청 전달

    어떤 역할인가요
    서로 다른 실행 세션을 찾고 요청·응답을 전달하는 통신 연결입니다. 업무 상태의 정본이나 예약 실행기를 자동으로 대체하지 않습니다.
    도입을 검토할 때
    여러 PC·실행기의 에이전트가 서로의 작업을 찾고 협업해야 할 때 검토합니다. 같은 중앙 PC를 휴대폰에서 쓰는 것만으로 필수는 아닙니다.
    기본 구성으로 가능한 대안
    한 실행기, 기존 메신저·Paseo 같은 원격 접점, 공유한 작업 ID·진행 기록과 명시적 인계로 필요한 흐름을 구성합니다.
    채택 전에 확인할 것
    선택한 실행기의 지원 여부, 데몬·설정 변경, 공개할 세션·폴더, 수신·실행 권한과 OFF 복구를 시험합니다. 요청 전달·처리 완료를 구분하고 작업 정본·스케줄러는 별도로 정합니다.

    Reason Network 비용·적용 검토 읽기 · 공식 소개

    두 항목 모두 최종 체크리스트와 최종 구축 보고서에서 검토합니다. 도입이면 실제 설정·시험 근거를, 미도입이면 이유·대안과 기존 구성의 충족 근거를 남깁니다. 보류이면 담당자·재검토 조건과 기한·현재 구축에 미치는 영향을 명시합니다. 비용과 제공 기능은 도입 시점의 공식 자료·실제 계정 조건을 확인합니다.
