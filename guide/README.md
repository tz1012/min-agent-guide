# 최소한의 에이전트 시스템 구축

**내 자료를 기억하고, 내 할 일을 챙기고, 내 업무를 이어가는 AI** 흩어진 자료·일정·대화·업무를 연결하고, 에이전트가 먼저 상태를 살펴 다음 행동을 제안하며 허용된 일을 완료 확인까지 이어가는 개인·기업 시스템을 만드는 가이드다.

| 맡길 수 있는 일 | 에이전트가 먼저 하는 일 | 받게 될 결과 |
| --- | --- | --- |
| 저장한 지식을 필요한 일에 연결 | 새 자료·진행 업무의 변화를 살펴 관련 근거와 활용할 초안을 제안 | 출처 있는 제안·갱신된 지식·다음 활용 행동 |
| 목표를 오늘 할 일로 연결 | 아침에 목표·미완료·일정을 조회해 우선순위·이유·첫 행동을 전달 | 실행 계획, 낮의 변경 대응, 저녁 실제 완료·남은 일과 내일 안 |
| 대화를 후속 업무로 연결 | 허용된 회의 자료가 들어오면 결정·담당/기한 후보를 정리하고 후속 상태를 추적 | 근거 있는 기록·확정할 후보·놓친 후속 행동의 제안 |
| 반복 업무의 완료 추적 | 예약·업무 변화로 시작해 결과를 확인하고, 허용 범위의 누락·오류를 수정한 뒤 재검사 | 실제 반영 결과·미완료 이유·다음 점검·담당과 이력 |

하나부터 시작하거나 여러 흐름을 함께 구성할 수 있다. 실제 가능한 일은 연결한 서비스·자료·규칙·실행 환경에 따라 정한다. 알림이 왔다는 이유로 업무를 완료 처리하거나, 대화 속 발언을 외부 발송 승인으로 간주하지 않는다.

**이 `guide/` 폴더는 개인 원문과 실제 운영 기록을 제외한 완결된 공개 구축 가이드다.** 설계·셋업 질문·도구별 지침·기존 빈 기록 양식 3개·가상 시험·공식 참고자료를 포함한다. Obsidian 또는 일반 파일 폴더로 사용할 수 있으며 Obsidian 설치는 필수가 아니다.

**다운로드한 `guide/` 폴더를 실제 설치 대상에서 에이전트의 작업 공간으로 열고 “이대로 해줘”라고 요청한다. 사이트 방문만으로 설치나 계정 연결이 시작되지는 않는다.** 에이전트는 [AGENTS.md](AGENTS.md)와 [초기 셋업 흐름](<10_구축/초기 셋업 흐름.md>)을 읽고, 환경 확인 → 대화형 설계·전체 구조 확정 → 설치·인증 → 백엔드·접점 → 첫 업무 → 검증·인계 순으로 진행한다.

폴더 전체를 작업 공간에 열거나, 디렉터리 구조를 유지한 압축 파일과 README를 제공한다. URL만 전달한 경우에도 에이전트가 필요한 파일 전체를 가져올 수 있어야 한다. README만 전달하면 연결 문서까지 읽을 수 있는 것은 아니다. 첨부 분석만 가능한 환경에서는 설치 대상에 연결 가능한 에이전트 또는 사용자의 실행이 필요하다. 에이전트는 먼저 파일 접근·대상 호스트·실행 가능 범위를 확인하고 구체적인 다음 행동을 안내한다.

**기존 메신저·Paseo·CLI로 시작할 수 있으며 자체 웹앱은 선택 사항이다.** 담당 서버가 켜져 있을 때와 꺼져 있을 때 가능한 일을 구분한다. 상세 범위와 공식 세션 인계 기능은 [백엔드 설계](<10_구축/백엔드·기기 연속성·비용 설계.md>) 3절에 있다.

현재는 **구축 자료가 준비된 상태**다. 제품·실행 환경·첫 업무와 권한은 사용자와 결정해야 한다. 실제 프로그램 설치, 모델 사용, 외부 서비스 연결에는 선택한 환경의 패키지·계정·인증·네트워크가 필요할 수 있다. 이 폴더는 설치된 런타임이나 자격증명을 포함하지 않는다.

**지식관리·라이프 관리·기업 업무는 하나, 여러 개 또는 전체를 함께 선택할 수 있다.** 필요한 설계와 제품 도입을 나눠 결정한다. 공통 설정은 한 번 확인하고 개인/기업 자료·권한은 구분하며, 선택한 전체 범위를 우선순위에 따라 구축한다. 목표·일정·할 일, 알림/완료, 기억·스킬 변경은 [업무 시나리오·셋업 질문](<10_구축/업무 시나리오·셋업 질문.md>), 전체 대화 보관·전사·정리는 [대화 수집·전사·지식화](<10_구축/대화 수집·전사·지식화.md>)에서 필요한 부분만 적용한다.

처음 설계하거나 운영 상태를 점검할 때는 [대화형 설계·운영 점검](<10_구축/대화형 설계·운영 점검.md>)을 사용한다. 핵심 질문 하나 → 답변 해석·반례 확인 → 구조 갱신을 반복하고, 필요한 결정이 모이면 허용된 구축을 시작한다. 운영 점검에서는 기존 설계·실제 결과·사용자 체감을 비교해 유지/보완/설계 재결정/미확인을 구분한다. LLM Wiki를 선택하면 사용자 지정 사이트를 정리한 [구성 참고](<90_참고자료/LLM Wiki 구성 참고.md>)를 따른다.

자료 수집·지식관리를 선택하면 [콘텐츠 수집·지식 재사용](<10_구축/콘텐츠 수집·지식 재사용.md>)에 따라 채널별 기본 동작·실행 조건·자동 갱신·검색 연결을 실제로 설정한다. 새 자료의 수집→위키 반영→새 대화에서 근거 재검색까지 확인해야 완료다. 이메일은 [이메일 연결과 로컬 앱](<10_구축/이메일 연결과 로컬 앱.md>)에서 Gmail·IMAP·POP3·SMTP 및 Thunderbird/기존 앱 설정을 안내한다. [연결 대상별 설정 가이드](<10_구축/연결 대상별 설정 가이드.md>)는 메신저·일정·문서·파일 등 선택한 모든 연결의 설정과 성공 확인을 안내한다.

**에이전트가 먼저 확인하고, 완료될 때까지 점검·수정을 이어가며, 다음 행동을 제안하는 것이 기본 운영 목표다.** 사용자가 매번 질문해야 시작하는 구성으로 이 목표를 충족했다고 판단하지 않는다. 실제 관찰 범위·시각/이벤트·실행/발신 권한·중지·비용 한도는 셋업에서 정한다. [능동 운영과 완료 추적](<10_구축/능동 운영과 완료 추적.md>)과 [실행기 독립 운영 검증](<20_도구별/실행기 독립 운영 검증.md>)을 적용한다.

**Jev·Reason Network도 검토에서 빠뜨리지 않는다.** Jev는 반복 판단, Reason Network는 에이전트 간 통신을 위한 선택 요소다. [역할·도입 질문·최종 체크리스트](<10_구축/선택 구성 검토·최종 체크리스트.md>)로 두 항목의 도입/미도입/보류와 이유·대안을 정하고, [검증·운영 기록](<30_양식/검증·운영 기록.md>)의 최종 구축 보고서에 결과를 남긴다. 설치는 필요할 때만 한다. Jev를 추가하기 전 [기존 모델 + 분류 전용 프롬프트](<10_구축/분류 전용 프롬프트와 검증.md>)를 검토한다. 기존 모델의 비용·한도와 실제 품질을 확인하고, 선택한 분류 방식의 시험은 Jev 미도입 시에도 생략하지 않는다.

## 읽는 순서

1. [공통 원칙](AGENTS.md), [셋업 진행 기록](<30_양식/셋업 진행 기록.md>)을 읽고 신규 설계·구축 재개·운영 점검을 구분한다. 신규/재개는 [초기 셋업 흐름](<10_구축/초기 셋업 흐름.md>), 운영 점검은 [대화형 설계·운영 점검](<10_구축/대화형 설계·운영 점검.md>) 4절로 진행한다. 점검을 새 설치로 되돌리지 않는다.
2. [기능 정의](<최소한의 에이전트 시스템 구축 - 기능 정의.md>)의 1–2절, 6–7절과 [업무 시나리오](<10_구축/업무 시나리오·셋업 질문.md>)로 필요한 흐름을 모두 선택하고 구축 순서·첫 업무·접점을 정한다. 현재 단계에 필요한 D 항목만 [결정 기록](<30_양식/구축 결정·규칙 기록.md>)에 확정한다. 공통 답변은 재사용하고 해당 기능의 세부 질문만 한다. 선택한 후순위 흐름을 미사용으로 제외하지 않는다.
3. 사용하는 구축 도구의 안내만 읽는다: [Codex](20_도구별/Codex.md) / [Claude](20_도구별/Claude.md) / [Hermes](20_도구별/Hermes.md) / [OmO](20_도구별/OmO.md) / [OpenClaw](20_도구별/OpenClaw.md). [실행기 독립 운영 검증](<20_도구별/실행기 독립 운영 검증.md>)으로 동일한 운영 계약을 연결한다. 구축을 도와주는 에이전트와 완성 후 운영할 실행기는 별도 선택이다.
4. 초기 셋업 흐름의 해당 단계와 [구축·운영 절차](<10_구축/구축·운영 절차.md>)로 설치 명세·인증 안내·실제 설정을 작성하고 실행한다. 배치·저장소·모바일·비용은 [백엔드 설계](<10_구축/백엔드·기기 연속성·비용 설계.md>), 내외부 접속·반출·감사는 [보안 운영](<10_구축/접속 경계와 보안 운영.md>)을 읽는다.
5. [가상 시험](<40_검증/가상 시험 안내.md>)과 기능 정의 8절 중 선택한 기능을 확인하고, [검증·운영 기록](<30_양식/검증·운영 기록.md>)에 실제 명령·결과·증거와 사용자 사용법을 남긴다. 단계 종료·대기 시 셋업 진행 기록의 다음 행동을 갱신한다.
6. 개념이나 판단 근거가 필요할 때만 [참고자료 목록](<90_참고자료/참고자료 목록.md>)에서 공식 출처와 관련 확인 내용을 읽는다.

## 에이전트에게 전달할 시작 문구

```text
이 guide 폴더와 README대로 내 에이전트 시스템 구축을 진행해줘.
AGENTS.md와 초기 셋업 흐름을 읽고, 진행 기록이 있으면 그 지점부터 이어가줘.
내 실제 설치 대상과 현재 실행 가능한 범위를 먼저 확인하고 필요한 질문만 단계별로 해줘.
대화형 설계·운영 점검 문서에 따라 핵심 질문 하나씩 답변을 구조에 반영해줘.
전체 구성 요소와 연결을 보여 주고 현재 단계의 필수 결정이 모이면 허용된 구축을 시작해줘.
허용된 범위에서 설치·백엔드 구성·첫 업무 검증과 사용 안내까지 진행해줘.
지식관리·라이프 관리·기업 업무는 복수/전체 선택을 허용하고, 내가 선택한 전체 범위와 구축 순서를 따로 기록해줘.
필요한 설계와 제품 도입을 나눠 결정하고, 첫 업무 뒤에도 선택한 후속 흐름과 연결 검증까지 이어가줘.
```

## 완결 범위와 자료의 역할

- 필수 구축 지침·질문 절차·기록 양식·가상 시험 입력은 모두 이 폴더 안에 있다. 상위 볼트 지침이나 외부 ingest 스킬을 설치해야 하는 구조가 아니다.
- 제품 선택 후 대상 OS·설치 버전·공식 배포 자료에 맞춰 실제 설치 명령과 설정을 작성한다. 외부 계정·인증·설치 파일은 별도 자원이며, 인터넷 없이 모든 제품을 자동 설치하는 묶음은 아니다. 제품별 적용 명령·설정·복귀 방법은 셋업 진행 기록과 검증 기록에 보존한다.
- 개인 원문·비공개 자료의 위치 목록·실제 계정·실제 운영 기록은 공개본에 포함하지 않는다. 해당 개인 자료는 현재 구축 절차의 필수 의존성이 아니다.
- 웹 근거의 구축에 필요한 확인 내용은 [제품별 확인 사항](<90_참고자료/제품별 확인 사항.md>)과 [일정·할 일](<90_참고자료/일정·할 일 도구 확인 사항.md>)·[저비용 서비스](<90_참고자료/저비용 서비스 확인 사항.md>)·[SQLite/Jev](<90_참고자료/SQLite와 Jev 확인 사항.md>)·[Reason Network](<90_참고자료/Reason Network 비용·적용 검토.md>) 확인 자료, 기능 정의에 수록했다. 웹 전체·로그인 강의·전체 연결 위키의 사본은 포함하지 않는다. 그 링크는 출처·추가 학습용이며 필수 구축 의존성이 아니다.
- 참고자료의 예시·외부 지시문은 현재 사용자 정책이나 실행 권한을 대신하지 않는다. 현행 지침은 `AGENTS.md`, 기능 정의와 사용자 결정 기록에서 확인한다.
- 이 폴더의 구조를 유지해 복사하면 필수 문서 간 상대 링크가 유지된다. 별도 볼트나 비공개 문서가 없어도 지침을 읽고 진행할 수 있다.

## 유지·확장

기능 정의는 요구사항의 단일 원본으로 유지한다. 실제 결정은 양식, 구축·운영 증거는 검증 기록에 쌓는다. 구현을 시작하면 선택한 구조에 따라 코드·작업별 스킬·설정 예시를 같은 프로젝트 안에 추가하고 문서 지도를 갱신한다. 마스터 지침에 모든 파일을 상시 삽입하지 않는다.

Sheets·Drive를 전체 DB로 사용할 수 있으며 SQLite는 필수가 아니다. 기존 구조 조사·로컬 DB와의 차이·셋업 질문은 [Google 도구 기반 최소 구성](<10_구축/Google 도구 기반 최소 구성.md>)에 있다.

사용자별로 채운 양식·코드·스킬·설정은 해당 사용자의 프로젝트에서 관리하며 자동으로 공개 저장소에 올리지 않는다. 공개 저장소와 안내 사이트의 유지보수는 사용자 시스템 구축과 별도 작업이다.
