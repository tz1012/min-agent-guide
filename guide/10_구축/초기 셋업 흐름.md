# 초기 셋업 흐름

사용자가 폴더와 README를 주고 “이대로 해줘”라고 하면 이 흐름으로 시작한다. [공통 원칙](../AGENTS.md)을 적용하고, [셋업 진행 기록](<../30_양식/셋업 진행 기록.md>)의 현재 단계를 먼저 확인한다. 이미 진행한 작업은 실제 환경과 대조해 재사용한다. 요구사항은 [기능 정의](<../최소한의 에이전트 시스템 구축 - 기능 정의.md>), 결정값은 [결정 기록](<../30_양식/구축 결정·규칙 기록.md>), 실행 증거는 [검증 기록](<../30_양식/검증·운영 기록.md>)이 기준이다.

## 0. 폴더 접근과 실행 가능 범위

- 기존 요청과 진행 기록에서 신규 설계·구축 재개·운영 점검을 구분한다. 운영 점검이면 [대화형 설계·운영 점검](<대화형 설계·운영 점검.md>) 4절로 가서 기존 구조·실제 증거부터 비교한다. 이 설치 순서를 처음부터 반복하지 않는다.
- 실제로 열 수 있는 파일을 확인한다. README·AGENTS·기능 정의·이 흐름·세 양식이 읽히는지 확인하고, 이후 필요한 문서가 누락되면 정확한 상대 경로를 알린다. README만 보이면 나머지도 받았다고 가정하지 않는다.
- 압축 파일은 지원되는 파일 도구로 별도 작업 폴더에 풀고 경로를 유지한다. 압축 해제·폴더 접근이 안 되는 환경에서는 가능한 전달 방법을 안내한다. 자동 지침 발견 여부와 관계없이 필요한 파일을 직접 읽는다.
- 현재 에이전트의 파일 읽기·쓰기·셸 실행·네트워크 도구와 **실제 설치 대상 컴퓨터**를 구분한다. 첨부물을 분석하는 임시 환경이 사용자의 Mac·서버라고 가정하지 않는다.
- 대상에 연결해 실행할 수 있으면 직접 작업한다. 읽기만 가능한 채팅에서는 계획·명령·사용자 작업 안내를 작성하고, 실행 가능한 에이전트에 폴더와 진행 기록을 넘기거나 사용자가 대상에서 실행한 결과를 받아 이어간다. 현재 가능한 방식과 부족한 접근만 설명한다.
- “검토해줘” 요청은 검토로, “구축해줘/이대로 해줘” 요청은 필요한 결정 후 구축으로 진행한다. 이미 허용된 준비·설치·구현을 단계마다 다시 승인받지 않는다. 새 결제·권한 확대·기존 데이터 삭제 등 범위가 불분명한 행동만 구체화해 확인한다.

## 1. 읽기 전용 환경 확인과 첫 안내

가능한 범위에서 대상 OS·아키텍처·현재 경로·설치된 후보 실행기/의존 도구의 버전·실행 권한·저장 여유·관련 서비스 실행 여부를 확인한다. 필요한 제품의 도움말·공식 설치 자료로 확인 방법을 고른다. 환경변수 전체나 인증 파일 내용을 출력하지 않는다.

관찰값에는 대상 호스트·확인 방법·시각을 붙인다. 직접 볼 수 없는 원격 장비 정보는 미확인으로 남긴다. 참고자료의 과거 CLI 버전·Mac mini 등은 현재 사용자 환경으로 재사용하지 않는다. 이미 설치된 도구가 요구를 충족하면 재설치하지 않는다. Hermes는 적용 예시 중 하나다. OpenClaw·Codex·Claude·OmO 등 기존 선택을 우선하고, 미정일 때만 원하는 에이전트와 역할을 확인한다. 다른 제품도 공통 운영 계약을 기준으로 공식 지원·필요 구성·실제 동작을 확인해 적용한다. 구축을 돕는 에이전트와 운영을 맡는 실행기를 따로 기록한다.

첫 안내는 확인된 환경·현재 단계·다음 작업을 짧게 알리고, 아래 중 가장 중요한 미답변 질문 하나를 고른다. 직접 연관된 경우에만 최대 3개로 묶는다. [대화형 설계·운영 점검](<대화형 설계·운영 점검.md>)에 따라 답변→해석·필요한 반례→전체 구조 갱신→다음 질문 순으로 진행한다.

1. 지식관리·라이프 관리·기업 업무 중 필요한 흐름을 모두 고르면 무엇이며, 먼저 얻고 싶은 결과는 무엇인가? — D01, 복수/전체 선택과 첫 구축 순서를 구분한다.
2. 본인만 쓰는가, 팀/조직 또는 혼합인가? — D04·D08, 자료·권한의 경계를 정한다.
3. 어느 장비에서 실행하고 어떤 창구로 사용할 것인가? — D02·D03, 현재 장비/CLI 또는 집 서버/메신저 등 보유 환경을 재사용한다.

기술 선택을 모르겠다고 하면 조사한 환경에 맞는 추천 하나와 대안 하나를 제시한다. 위임받은 세부 구현값은 근거와 변경 방법을 남겨 선택할 수 있지만, 미응답을 데이터 반출·발송·과금 허용으로 간주하지 않는다.

## 2. 필요한 설계 선택과 단계별 구성

[업무 시나리오·셋업 질문](<업무 시나리오·셋업 질문.md>)으로 **전체 필요 → 설계 패턴 채택·보류·제외 → 구축 순서 → 기존 기능·제품 선택** 순서로 진행한다. 택 1로 제한하지 않는다. 공통 설정은 한 번 묻고, 개인/기업의 자료·권한·보존 차이는 각각 정한다. 목표·일정·완료·알림·기억/스킬 자동 변경도 필요 여부부터 확인하며 현재 단계에 해당하는 세부 질문만 1–3개씩 한다.

대화 전체 보관·전사·정리를 원하면 [대화 가이드](<대화 수집·전사·지식화.md>)를 적용하고 여러 흐름의 공통 모듈로 쓸 수 있다. Calendar 안의 할 일을 원하면 별도 앱 설치와 데이터/API 연결을 구분하여 [일정·할 일 확인 사항](<../90_참고자료/일정·할 일 도구 확인 사항.md>)의 실제 지원 범위를 대조한다. 선택한 설계가 특정 제품 도입을 강제하지 않는다.

| 시작 상황 | 우선 검토할 최소 구성 | 필요할 때만 추가 |
| --- | --- | --- |
| 현재 컴퓨터에서 본인 업무 | 기존 실행기/CLI + 내장 세션·재개 + 지정 자료·결과 폴더 | 지속 기억·Wiki 검색·외부 서비스 연결 |
| 기존 Sheets·Drive DB를 사용 | 기존 테이블·고정 ID·파일 참조를 조사하고 정본으로 재사용; 필요한 실행기 연결 | 파생 검색 캐시·Forms·자동화는 필요할 때만; SQLite 추가는 필수 아님 |
| 집/가상/중앙 PC를 휴대폰에서도 사용 | 위 구성 + 선택한 메신저 Gateway 또는 Paseo 등의 기존 원격 접점 | 별도 웹앱·공개 API·Cloudflare 경로 |
| 회사 자료·여러 사용자 | 기존 승인 실행기·접점·인증·저장소 + 실제 역할별 권한·감사 | 동시성 요구에 따른 서버 DB·여러 작업자 |

Reason Network·Jev·벡터 DB·새 큐·자동 장애 전환은 기본 설치 목록에 넣지 않는다. 다만 Jev·Reason Network 두 항목은 [선택 구성 검토](<선택 구성 검토·최종 체크리스트.md>)로 필요성을 확인하고 결정 기록에 도입/미도입/보류·이유·대안을 남긴다. 기존 답변은 재사용하며 미도입 제품의 설치 질문은 생략한다. [백엔드 설계](<백엔드·기기 연속성·비용 설계.md>)에서 첫 업무의 부족한 역할을 확인한 경우에만 추가한다. 기존 기능 재사용으로 구현하는 것도 구축 결과다. 반복 의미 판단이 필요하면 Jev 전에 [기존 모델 분류 프롬프트](<분류 전용 프롬프트와 검증.md>)를 제안한다. 분류 기준·허용 후보·검토 조건 중 미정만 묻고, JSON/근거 검증과 실행 권한 차단·비용 한도를 설치/시험 계획에 연결한다.

저장소 선택 전 기존 표·연결 파일·자동화의 구조부터 확인한다. [Sheets·Drive 전체 DB와 로컬 DB 비교](<Google 도구 기반 최소 구성.md>)로 오프라인·여러 기기 접근·동시 쓰기·관계 검증·권한·백업·비용 차이를 설명하고 D05에 정본과 파생 사본을 기록한다. 단순한 표 열람을 기존 자동화의 정상 작동 증거로 쓰지 않는다.

- 설치 전에는 D03의 대상·제품·방식, D04의 변경 범위, 첫 업무 폴더·복원 방법을 정한다.
- 첫 모델 호출·유료 자원 생성 전에는 D04의 전송 자료 범위와 D06의 비용 출처·허용 한도를 정한다. 기존 구독이 API 비용까지 포함한다고 가정하지 않는다.
- 실제 연결·저장 전에 해당 D02·D04·D05만 구체화한다. 운영 전에는 D07·D08 및 적용하는 D09·자동화 한도를 채운다. 미사용 항목은 적용 제외 사유로 닫고, 나머지는 필요한 단계까지 미뤄 둔다.
- 사용자 답변을 에이전트가 규칙·설정 초안으로 바꾼다. 이미 명확한 답변을 반복 승인받지 않고, 의미가 추가되거나 충돌한 부분만 질문한다. 세부 질문 방법은 기능 정의 7절을 따른다.
- 후순위로 선택한 흐름은 구축 대기와 선행 조건을 기록한다. 미사용·적용 제외와 구분하고 첫 업무 후 계속 진행한다. 전체를 원한 사용자의 범위를 첫 시나리오 하나로 닫지 않는다.

선택한 입력·출력마다 [연결 대상별 설정 가이드](<연결 대상별 설정 가이드.md>)로 기존 연결·공식 설정·지원 OS/버전·권한을 확인한다. 이메일은 [이메일 연결과 로컬 앱](<이메일 연결과 로컬 앱.md>), 지식 수집은 [콘텐츠 수집·지식 재사용](<콘텐츠 수집·지식 재사용.md>)를 적용한다. 필요한 계정/채널/메일함, 무지시 입력의 기본 동작, 자동 범위를 질문하고 결정 양식에 기록한다. 사용자가 기술 설정을 직접 찾아오게 하지 않는다.

## 3. 실행 가능한 설치 계획 작성

2단계의 답변으로 전체 선택 범위의 구성 요소·데이터 흐름·권한·기준 저장소와 구축 순서를 결정 기록의 구조 청사진에 정리한다. 현재 단계의 성공 기준·필수 값·검증/복귀가 확보되면 구조 요약·계획·남은 사항을 보여 주고 이 단계로 넘어간다. 사용자 확정·관찰·가정을 구분하고 이미 허용된 구축에 형식적 재승인을 요구하지 않는다. 후속 단계의 상세값을 모두 채우느라 첫 구축을 미루지 않는다.

선택한 제품마다 진행 기록의 **설치 명세**를 채운다. 제품·버전·대상 OS/아키텍처·공식 출처·확인일·의존성·설치 위치·정확한 명령 또는 화면 경로·변경할 파일/서비스·백업·성공 확인·복귀 방법을 남긴다. 비밀값 없는 설정 예시와 첫 업무의 입력·예상 결과도 준비한다.

- 현재 대상의 설치 버전·도움말·공식 배포 자료를 확인해 명령을 구체화한다. 이 패키지는 모든 OS용 설치 파일을 포함하지 않는다. 외부 자료를 확인할 수 없으면 검증한 로컬 도움말/기존 패키지를 사용하거나 해당 설치만 대기한다. 확인하지 않은 최신 명령을 만들어 내지 않는다.
- 기존 설정은 필요한 부분만 병합하고 변경 전 사본·차이를 남긴다. 전역 지침을 통째로 교체하거나 관계없는 세션·데몬을 종료하지 않는다. 자동 시작·업데이트·포트 개방은 선택한 운영 방식에 맞는 경우만 설정한다.
- 앞 단계의 범위·권한으로 진행 가능한 계획은 설명 후 실행한다. 추가 확인이 필요한 경우 변경 대상·범위·비용·복귀 수단까지 준비한 뒤 그 쟁점만 묻는다. 설치 계획 전체를 매번 재승인받는 단계는 만들지 않는다.

## 4. 설치·인증 — 작은 단위로 확인

Google Calendar·Gmail·Drive/Docs/Sheets를 선택하면 [Google 계정 연결·대리 설정](<Google 계정 연결·대리 설정.md>)으로 진행한다. 기존 연결의 실제 제공 기능과 운영 호스트를 확인하고, 부족할 때만 필요한 어댑터/직접 OAuth 경로를 선택한다. 에이전트가 허용된 설정·비밀값 없는 준비·진단을 수행하며 사용자에게 모든 설치를 넘기지 않는다. 사용자가 직접 할 로그인·2FA·동의와 필요한 관리자 조치에는 화면·행동·완료 신호·재개 위치를 남긴다. 기존 승인 범위는 재사용하며 새 발신·초대·권한 확대를 연결 허용으로 추정하지 않는다.

1. 필요한 의존성 → 실행기 → 선택 접점/연결 순서로 설치한다. 각 단계의 종료 상태·설치 경로·실제 버전을 확인하고 증거를 남긴다. “이미 설치됨”도 호환성과 동작을 확인한다.
2. 모델 인증과 메신저/문서 서비스 인증을 각각 수행한다. 로그인·2FA·관리자 작업이 필요한 경우 **어느 기기의 어느 화면에서 무엇을 하고, 무엇이 보이면 끝인지** 한 번에 한 행동씩 안내한다. 키를 채팅으로 받지 않고 지정 비밀 저장소 또는 대상의 안전한 입력란에 넣도록 한다.
3. 인증 성공은 비밀값을 노출하지 않는 상태 조회·허용된 최소 조회로 확인한다. 브라우저가 닫히거나 사용자가 “했어”라고 말한 것만으로 연결 완료를 기록하지 않는다. 직접 조회할 수 없으면 사용자 확인 결과와 미검증 범위를 구분한다.
4. 실패한 단계와 다음 행동을 기록한다. 인증·권한 오류는 재로그인/담당자 조치로, 버전·설치 오류는 해당 명세의 진단·복귀로 분기한다. 동일한 실패 명령을 반복하거나 이미 성공한 설치를 처음부터 다시 하지 않는다.

## 5. 백엔드·접점 구성과 첫 기동

1. **저장 위치를 먼저 정한다.** 작업 상태·지속 기억·Wiki/자료·산출물·로그·백업의 실제 위치와 소유자를 기록한다. 필요한 역할만 사용하고 내장 저장소가 충족하면 새 DB·스키마를 만들지 않는다.
2. **선택한 실행 환경을 구성한다.** 실행 계정·작업 폴더·비밀 참조·필요한 연결·시간대·한도를 적용한다. 상주 서비스를 선택한 경우 시작/중단·로그·재부팅·절전 동작, 컨테이너를 선택한 경우 영속 볼륨을 확인한다.
3. **추가 저장소를 선택한 경우만 생성한다.** 초기화/마이그레이션·접근 권한·일관된 백업·복귀 방법을 명세에 추가한다. 운영 SQLite 파일을 여러 컴퓨터의 동기화 폴더로 공유하지 않는다.
4. **선택한 접점 하나를 연결한다.** 허용 사용자·채팅/스레드·자료 범위를 적용한다. 회사 외부 접속은 [보안 운영](<접속 경계와 보안 운영.md>)의 실제 정책을 적용한다. 필요한 경로가 기존 기능에 있으면 공개 포트·새 API를 추가하지 않는다.
5. **선택한 자동화를 연결한다.** 연결별 실제 수신 어댑터·실행 조건·담당 호스트·처리 규칙·중단/재개와 검색 접점의 위키 참조를 설정한다. `콘텐츠 수집·지식 재사용`의 K01–K08 중 적용 범위를 설치 명세와 연결한다. 이메일은 로컬 앱과 에이전트 연결을 각각 구성하며 수신·초안·발송·삭제 권한을 분리한다. 다른 선택 연결도 설정 가이드의 C01–C06을 적용한다.
6. **능동 운영을 연결한다.** [능동 운영과 완료 추적](<능동 운영과 완료 추적.md>)과 [실행기 독립 운영 검증](<../20_도구별/실행기 독립 운영 검증.md>)으로 실제 예약/감지·지속 상태·실행 명령/어댑터·발신 채널을 구성한다. 사용자 대화를 닫은 뒤에도 먼저 관찰·제안하고 미완료를 수정·재점검할 수 있어야 한다. 내장 기능이 없으면 필요한 외부 역할을 구현하고 확인한다.
7. **실제 기동을 확인한다.** 프로세스가 켜진 것, 모델 호출 성공, 접점 요청 수신, 결과 저장을 각각 확인한다. 하나의 성공을 전체 연결 완료로 확대하지 않는다. 첫 비용 발생은 2절에서 정한 범위 안에서 수행한다.

## 6–8. 첫 업무 → 적용 기능 검증 → 사용자 인계

| 단계 | 작업과 넘어가는 조건 | 남길 위치 |
| --- | --- | --- |
| 6. 첫 업무 | 허용된 샘플 입력→자료 조회→처리→결과 저장·조회까지 확인. 선택한 업무에 발송이 포함될 때만 허용된 대상으로 전달 확인 | 검증 기록 V01·해당 연결 증거 |
| 7. 적용 기능 검증 | 적용하는 권한·실패·중단/재개·백업 복원 확인. 모바일/서버 중지·Docs 등과 시나리오별 목표/완료·기억/스킬·전사·검색·기업 업무를 필요한 범위에서 시험 | 검증 기록 V01–V26 중 적용 사례 |
| 8. 사용자 인계 | 시작·사용·상태·중단·재인증·복구, 완료 표시·알림 중지·기억 교정·전사 수정 등 채택 기능 사용법 제공. 선택한 전체 범위 중 완료·대기·미해결, 서버 켜짐/꺼짐별 가능 작업 전달 | 검증 기록의 실제 운영 절차·인수인계 |

여러 흐름을 선택했다면 후속 흐름마다 필요한 설정과 6–8단계를 반복하고, 공통 설정·인증·검증 증거는 변경이 없는 범위에서 재사용한다. 대화→업무/목표/일정/지식처럼 연결한 경우 교차 시나리오 V26도 적용한다. 후속 흐름이 남으면 해당 단계를 진행 기록의 다음 행동으로 유지하고 전체 완료로 보고하지 않는다.

능동 운영은 P01–P06과 실행기별 같은 수용 기준을 시험한다. 새 사용자 메시지가 없는 시작, 실패 수정·재검사, OFF 복귀·중단·권한·다음 점검의 실제 증거가 필요하다. 도구의 문서 지원·CLI help 확인과 실제 예약 실행을 구분하고 미확인 실행기는 미검증으로 남긴다.

지식 자동화를 채택하면 실제 선택 접점에서 허용한 자료를 보내 원문·위키·목록/이력·검색 갱신을 확인하고, 이전 대화를 인계하지 않은 새 대화에서 기대 근거를 찾아야 완료다. 메일은 E01–E08 중 선택한 프로토콜과 행동을 실제로 시험한다. 연결별 C01–C06의 적용 증거가 없으면 그 연결은 준비 중으로 남긴다. 자동화 미채택은 제외 사유를 기록하며, 자동화를 선택한 요청을 수동 실행 시연만으로 닫지 않는다.

[가상 시험](<../40_검증/가상 시험 안내.md>)은 선택한 기능의 기대 동작을 확인하는 자료다. 모든 사례를 통과시키기 위해 불필요한 API·DB·작업자를 구현하지 않는다. 실제 환경의 인증·저장·복구 시험은 별도 증거가 필요하다. 적용한 필수 사례가 실패하면 그 기능은 준비 중으로 남기고 독립적으로 통과한 기능은 사용할 수 있게 안내한다.

인계 전 [검증·운영 기록](<../30_양식/검증·운영 기록.md>)의 **최종 체크리스트와 최종 구축 보고서**를 작성한다. Jev·Reason Network 두 행을 포함해 결정·설치·증거·현재 범위를 대조한다. 미검토/빈칸을 미도입으로 간주하지 않으며 보류는 영향·담당·조건·기한을 남긴다. 필수 의존성이 미해결이면 해당 범위는 미완료다.

## 중단·재개와 사용자 안내

- 매 단계가 끝나거나 사용자 조치를 기다릴 때 진행 기록에 현재 단계·마지막 성공·변경 파일/설치 항목·다음 행동·대기 이유·증거 위치를 남긴다. 결정값과 로그를 통째로 복제하지 말고 정본을 가리킨다.
- 새 에이전트는 `README → AGENTS → 셋업 진행 기록 → 필요한 결정·증거 → 실제 대상 상태` 순으로 확인한다. 설치됨·인증됨·요청 접수됨을 재확인한 뒤 미완료 단계만 수행한다. 재실행에 부작용이 있는 작업은 실제 결과를 먼저 조회한다.
- 진행 안내는 “완료한 일 / 현재 단계 / 다음 작업 / 사용자 행동이 있으면 한 가지와 완료 신호”로 짧게 한다. 토큰·계정·정책 승인 등 외부 조치를 기다릴 때도 독립적인 문서·샘플·설정 준비는 계속한다.
- 완료 안내에는 실제 사용할 접점·대표 요청·결과 위치·서버 중지 시 제한·시작/중단/복구 경로·비용 조건·미완료 범위를 포함한다. 문서 점검만 했다면 구축 완료로 보고하지 않는다.
