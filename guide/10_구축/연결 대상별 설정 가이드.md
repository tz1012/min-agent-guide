# 연결 대상별 설정 가이드

선택한 도구는 **공식 설정 확인 → 사용자 인증 안내 → 실제 어댑터 설정 → 작은 표본 시험 → 운영·해제 안내**까지 진행한다. 이 문서는 [기능 정의](<../최소한의 에이전트 시스템 구축 - 기능 정의.md>) 4절의 모든 연결 범주를 다룬다. 전 제품 설치 목록이 아니며 실제 사용할 연결만 적용한다. 공식 자료 확인일은 **2026-10-28**, 실제 계정·설치·런타임 연결은 미검증이다.

무료 앱을 설치한 것과 에이전트 연결은 다르다. 앱의 무료 이용이 API·봇·서버·모델 호출의 무료 사용이나 조직의 연결 허용을 뜻하지 않는다. 기존 커넥터/게이트웨이가 필요한 기능을 충족하면 재사용하고, 자체 앱·OAuth 클라이언트·서버는 필요한 경우에만 만든다.

## 1. 공통 연결 카드와 에이전트의 실행 책임

아래 값은 [구축 결정·규칙 기록](<../30_양식/구축 결정·규칙 기록.md>)의 연결 계약에 기록한다. 별도 빈 양식을 만들지 않는다.

| 구분 | 선택한 연결마다 정할 값 |
| --- | --- |
| 역할·범위 | 수신/조회·검색·초안·쓰기·발송 중 필요한 동작, 계정·조직·사용자·채널/폴더/업무 대상 |
| 실제 방식 | 내장 커넥터·API·CLI·봇·파일·브라우저 중 채택 방식, 제품/어댑터 버전·공식 출처·확인일 |
| 식별·인증 | 연결 ID, tenant/workspace/account 및 대상 ID, OAuth/봇 등 인증 주체·권한, 비밀 저장소 참조·만료/갱신 담당 |
| 실행·처리 | 실행 호스트·설정 경로·트리거/주기·조회 시작점/커서·중복 키·결과 정본·처리/비용 상한 |
| 수신 응답 계약 | 제공자 서명/secret 검증·재전송/재생 방지, ACK 기한·지연 응답·재시도·후속 결과 전달 기한 |
| 운영·복구 | 시작/중지·재인증·접근 회수·재연결 방법, 서버 OFF 동작, 성공/거부 시험 증거·미지원 범위 |

1. 에이전트는 설치된 연결과 실제 기능을 확인하고 첫 업무에 부족한 항목만 선택한다. 최신 문서를 확인해 **대상 OS에서 쓸 정확한 설치 명령 또는 화면 경로, 필수 설정값, 변경 파일, 검증·복귀 방법**을 [셋업 진행 기록](<../30_양식/셋업 진행 기록.md>)에 구체화한다. 링크만 던지고 사용자에게 알아서 설치하라고 끝내지 않는다.
2. 허용된 설치·설정·규칙 연결은 에이전트가 진행한다. 사용자가 해야 할 로그인·2FA·관리자 작업은 한 번에 한 행동과 완료 신호로 안내한다. 비밀번호·토큰·비밀키를 채팅이나 공개 기록으로 받지 않는다.
3. 공개 수신 endpoint는 제공자별 서명/secret·필요한 시각 검증을 설정한다. 검증되지 않은 요청은 payload의 사용자 ID·채널 허용 여부를 판단하거나 작업을 접수하기 전에 거부한다. Slack HTTP는 서명·요청 시각, Discord HTTP interactions는 공개키 기반 서명, Telegram webhook은 지정한 secret header를 해당 공식 규격으로 검증한다. 수신 계층은 인증·지속 접수를 확인하고 제공자 기한 안에 ACK/지연 응답을 반환하며 장시간 LLM·전사·위키 처리를 기다리지 않는다. 저장 실패를 사용자에게 접수 완료로 표시하지 않으며 재전달은 기존 작업으로 이어간다. 최종 답변 경로·전달 가능 기한과 기한 초과 시 허용된 대체 경로도 정한다.
4. 인증 후 실제 계정/대상·읽기·선택한 쓰기 범위를 확인한다. 연결 성공 표시만으로 첨부·스레드·검색·쓰기까지 성공했다고 판단하지 않는다. 수신과 발송, 사용자 UI와 자동 API의 권한을 구분한다.
5. 선택한 수집/검색에는 [콘텐츠 수집·지식 재사용](<콘텐츠 수집·지식 재사용.md>)을 연결한다. 표본 결과와 운영법은 [검증·운영 기록](<../30_양식/검증·운영 기록.md>)에 남긴다. 공식 API가 없거나 권한이 막히면 내보내기·파일 전달·수동 작업 등 가능한 대안을 안내하고 자동 지원으로 표시하지 않는다.

## 3. 메신저와 원격 접점

모든 메신저에 적용한다: 허용 사용자/조직·채널을 ID로 정하고, 멘션·DM·명령·전체 메시지 중 수신 조건을 실제 설정한다. 본문·첨부·답장/스레드를 각각 시험한다. 수신할 수 있는 봇과 지정 채널에 발송만 하는 웹훅은 같은 기능이 아니다. 단순 알림 웹훅을 콘텐츠 수집 완료로 기록하지 않는다.

### Slack

- 설정: 기존 연결이 없으면 Slack 앱을 만들고 Socket Mode 또는 HTTP 이벤트 경로를 선택한다. Socket Mode는 활성화 후 app-level token을 만들고, 필요한 bot OAuth scope·이벤트 구독을 설정한다. 워크스페이스에 설치하고 대상 채널에 앱을 추가한 뒤 실행 호스트의 어댑터에 비밀 참조를 연결한다. HTTP 방식이면 별도의 수신 endpoint 검증·요청 인증을 구현한다. [이벤트 규격](https://docs.slack.dev/apis/events-api/)의 3초 응답 기한과 재시도를 적용하고 긴 처리는 지속 접수 뒤 이어간다. [Socket Mode 공식 안내](https://docs.slack.dev/apis/events-api/using-socket-mode/)
- 사용자 조치·기록: 설치/관리자 승인을 받고 workspace·app·channel ID, 허용 사용자, 실제 scope·이벤트, 토큰 참조·연결 방식을 남긴다. 발송·파일 접근 권한은 해당 기능을 사용할 때 확인한다.
- 시험·해제: 허용 채널의 멘션/DM과 선택한 첨부 → 처리 → 같은 스레드 결과를 확인하고 범위 밖 채널을 검사한다. 중지 시 수신기를 멈추고 앱/채널 접근·토큰을 필요한 범위에서 회수한다. 재연결은 기존 이벤트·작업 상태를 대조해 중복 반영을 막는다.

### Discord

- 설정: Developer Portal에서 앱/봇을 준비하고 필요한 설치 대상·권한으로 서버에 설치한다. 일반 메시지를 수집하려면 Gateway 이벤트와 필요한 intents를 구성하고, 명시적 명령만 받으면 interactions 경로를 선택한다. 메시지 내용 접근이 필요한 경우 실제 privileged intent 조건을 확인한다. HTTP interactions는 요청 서명을 검증하고 3초 이내 초기/지연 응답, 15분의 후속 응답 토큰 유효 기간에 맞춘 결과 전달 경로를 구성한다. 긴 작업은 허용된 별도 결과 전달 방식을 정한다. [Interaction 응답 규격](https://docs.discord.com/developers/interactions/receiving-and-responding) 발송 웹훅만으로 채팅 수신을 구현하지 않는다. [공식 시작 안내](https://docs.discord.com/developers/quick-start/getting-started)
- 사용자 조치·기록: 서버 관리자의 설치 허용, application/guild/channel ID, 봇 자격증명 참조, intents·명령·허용 사용자/역할·응답 위치를 기록한다. 관리자 전체 권한을 편의상 부여하지 않는다.
- 시험·해제: 선택한 메시지/명령·첨부·스레드를 실제 서버에서 시험하고 비허용 채널과 역할을 검사한다. 봇 권한/설치·토큰·interaction endpoint를 회수하고 재설치 후 새 접근 범위를 확인한다.

### Telegram

- 설정: 사용자가 BotFather에서 봇을 만들고 토큰을 지정 비밀 저장소에 입력한다. 에이전트는 `getMe`로 봇 신원을 확인하고 `getUpdates` 기반 조회 또는 webhook 중 선택한 수신 방법을 어댑터에 설정한다. webhook이면 `secret_token`을 설정하고 수신 요청의 `X-Telegram-Bot-Api-Secret-Token`을 확인한다. polling으로 전환할 때 `getWebhookInfo`로 상태를 확인하고 `deleteWebhook`으로 기존 webhook을 제거한 뒤 시작한다. 미처리 자료를 버리기로 정하지 않았다면 `drop_pending_updates`를 활성화하지 않는다. 같은 봇의 수신 담당을 중복 운영하지 않는다. [Webhook 설정·전환](https://core.telegram.org/bots/api#setwebhook) [공식 봇 시작 안내](https://core.telegram.org/bots/tutorial)
- 사용자 조치·기록: 봇 DM 시작 또는 대상 그룹 추가, 허용 user/chat ID, 그룹 privacy 설정에 따른 실제 수신 범위, 봇 토큰 참조·조회 offset/웹훅 상태·파일 한도를 기록한다. 봇 토큰은 브라우저 주소/공개 로그에 노출하지 않는다.
- 시험·해제: DM/그룹 중 선택한 경로의 텍스트·파일·응답과 비허용 발신자를 시험한다. 수신기/웹훅을 중지하고 필요한 경우 BotFather에서 토큰 회수·재발급, 그룹 제거를 진행한다. 재개 시 처리한 update와 남은 자료를 대조한다.

### Buzz

- 설정: 사용할 relay와 커뮤니티를 정하고 사용자·에이전트의 별도 identity를 준비한다. 관리자가 에이전트를 relay와 지정 채널에 초대한다. 선택한 에이전트의 실제 어댑터를 구성하며, Hermes를 쓴다면 해당 버전의 Buzz CLI·WebSocket·인증된 첨부 처리 안내를 적용한다. [Buzz 운영 안내](https://block.github.io/buzz/support.html), [Hermes Buzz 연결](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/buzz.md)
- 사용자 조치·기록: relay URL·운영자·채널·에이전트 공개 식별자·비밀키 참조·허용 사용자·실행 호스트를 기록한다. Block-hosted relay는 종단간 암호화 저장소로 가정하지 않으며 회사 자료의 허용 여부를 확인한다.
- 시험·해제: 채널 메시지·첨부 수신과 스레드 답변, 비초대 채널 접근 거부를 확인한다. relay의 메시지 보관과 호스트의 에이전트 실행을 구분해 OFF 시험을 한다. 해제 시 agent/채널 접근·자격증명을 회수하고 relay 보존 자료는 정한 정책으로 별도 처리한다.

### 카카오톡

- 설정: 먼저 개인 대화 수집, 결과 발송, 사업용 챗봇 중 목적을 나눈다. 카카오톡 메시지 API는 서비스 내 사용자에게 메시지를 보내는 경로이며 개인 채팅 전체를 읽는 수집 API가 아니다. 발송을 선택하면 개발자 앱·카카오 로그인·필요 동의/권한·대상/템플릿을 해당 공식 절차로 구성한다. [메시지 API 범위](https://developers.kakao.com/docs/ko/kakaotalk-message/common)
- 사용자 조치·기록: 앱과 로그인 계정·허용 발송 대상·템플릿·토큰 참조를 기록한다. 개인 대화 수집은 사용자가 허용된 대화를 파일로 내보내 전달하는 경로 등을 선택한다. 사업용 챗봇을 원하면 선택 서비스의 현재 등록·심사·수신 규격을 별도 설치 명세로 확정한다.
- 시험·해제: 허용 대상에게만 발송 시험하거나 내보낸 표본 파일의 읽기/지식화를 검증한다. 개인 대화 실시간 자동 수집을 약속하지 않는다. 로그인 연결/앱 권한을 회수하고 파일 수집 중지·보존 정책을 적용한다.

### Microsoft Teams

- 설정: 조직에서 허용한 기존 연결을 먼저 사용한다. 신규 개발이 필요하면 현재 Teams SDK/등록 도구로 앱·봇 인프라와 tenant의 앱 업로드/배포 정책, HTTPS 수신 endpoint를 설정한다. 조직·계정·앱 등록은 해당 경로의 요구에 맞춘다. [Teams 등록 안내](https://learn.microsoft.com/en-us/microsoftteams/platform/teams-sdk/get-started/quickstart-register)
- 사용자 조치·기록: 관리자의 앱 배포·필요 동의, tenant/app·팀/채널 ID, endpoint·자격증명 참조·수신 범위를 남긴다. 봇 대화 권한과 Graph로 사용자 문서·일정 등을 조회하는 권한은 별도다. 필요 시 [Entra 앱 등록](https://learn.microsoft.com/en-us/graph/auth-register-app-v2)을 적용한다.
- 시험·해제: 지정 사용자/팀에서 메시지·첨부·응답을 확인하고 다른 팀·게스트의 접근을 검사한다. 앱 배포/봇·Graph 동의를 각각 회수하고 endpoint·예약을 중지한다. 조직 정책이 막으면 관리자 대기로 남기고 우회 설치하지 않는다.

### Paseo·CLI 원격 접점

- 설정: 대상 호스트에 이미 실행 가능한 에이전트와 작업 폴더가 있는지 확인한다. Paseo Desktop은 자체 daemon을 포함하며 `Settings → 해당 host → Pair Device`로 기기를 연결한다. headless 서버는 공식 CLI 경로를 선택한다. 사용 중인 버전에 맞는 설치 명령·접속 경로를 설치 명세에 남긴다. [공식 시작 안내](https://paseo.sh/docs)
- 사용자 조치·기록: 기기 페어링, 대상 host·사용자·workspace·허용 파일/실행 범위·에이전트 제공자·연결 방식·세션/작업 ID를 확정한다. CLI만 사용하면 해당 호스트의 실제 실행·재개 명령을 안내한다.
- 시험·해제: 컴퓨터에서 작업 시작→클라이언트 종료→휴대폰에서 같은 작업 확인·재개를 시험한다. 호스트 OFF에서 새 실행 불가와 조회 가능한 기존 상태를 구분한다. 분실/중단 시 페어링·접속 자격·daemon을 실제 지원 방법으로 회수하고 재연결을 시험한다.

## 5. 로컬 자료·위키·Notion·대화 메모리

- **Obsidian·로컬 폴더·NAS:** 사용자가 기존 루트와 에이전트 쓰기 폴더를 정한다. Obsidian vault는 파일시스템의 폴더이므로 로컬 Markdown 접근으로 충족하면 REST 플러그인을 설치하지 않는다. 에이전트는 실제 마운트/경로·읽기/쓰기 주체·동기화·백업·파일 잠금/충돌 규칙을 설정하고 시험 파일의 생성·재조회·원상 복구와 연결 끊김을 확인한다. NAS 자격은 운영체제의 지정 저장소에 두고 공개 링크로 대체하지 않는다. 해제 시 watcher·마운트/접근을 중지하고 원본을 보존한다. [Obsidian vault 안내](https://help.obsidian.md/Files+and+folders/Manage+vaults)

[내부 연결](https://developers.notion.com/guides/get-started/internal-connections), [현행 API 시작 안내](https://developers.notion.com/guides/get-started/quick-start)
- **LLM Wiki·대화 메모리:** 외부 서비스 등록이 필요한 범주로 취급하지 않는다. 기존 파일/DB/내장 기억 중 정본·개인/팀 범위·쓰기/검색 경로·유효 시점·교정/삭제를 정한다. 위키의 종합 지식과 작업 상태, 관찰 메모와 활성 기억/스킬을 분리한다. 에이전트가 선택 접점의 검색을 실제 연결하고 새 세션의 조회·교정·삭제를 시험한다. [콘텐츠 순환](<콘텐츠 수집·지식 재사용.md>) 및 [기억 변경 절차](<업무 시나리오·셋업 질문.md>)를 적용하며 비활성화·색인/파생물 회수 방법도 인계한다.

## 6. 웹·브라우저·회의·음성

- **웹 검색·브라우저:** 이미 제공되는 검색·브라우저의 실제 읽기/다운로드·로그인 접근을 확인하고 허용 사이트·프로필·다운로드 폴더·반출 범위·결과 저장을 설정한다. 별도 검색 API가 필요하면 선택 제공자의 공식 계정/키·요금·한도를 확인해 비밀 참조와 호출 제한을 구성한다. 사용자는 필요한 사이트 로그인을 직접 한다. 에이전트는 공개 페이지와 선택한 인증 페이지의 본문·출처·파일을 표본 시험하고 접근 실패를 숨기지 않는다. 해제 시 연결/세션·키·예약을 필요한 범위에서 회수한다. 브라우저 로그인 성공만으로 상시 자동 수집을 약속하지 않는다.
- **회의·음성 파일:** 먼저 로컬 녹음/내보내기 파일 경로로 충분한지 확인한다. 서비스 자동 연결을 원하면 녹음 생성·목록 조회·파일 다운로드·전사 중 필요한 기능을 선택한다. Zoom의 경우 선택 계정의 녹화 기능/플랜·OAuth recording 권한·meeting/recording file ID와 인증된 다운로드를 확인한다. [Zoom 녹화 API](https://developers.zoom.us/docs/api/meetings/)

사용자는 수집 범위·허용 처리 위치와 필요한 계정 동의를 정한다. 에이전트는 선택한 로컬/클라우드 전사 도구의 설치·모델·언어·비용 한도를 설정하고 짧은 허용 표본의 수신→전사→시각 근거→지식/업무 후보를 시험한다. [대화 수집·전사·지식화](<대화 수집·전사·지식화.md>)를 적용하며, 앱 설치만으로 모든 회의가 녹음된다고 가정하지 않는다. 해제 시 수집/웹훅·OAuth·예약을 중지하고 원문/전사/파생물 보존을 처리한다.

## 7. 연락처·CRM·RSS·업무 시스템

- **연락처:** Google을 사용하면 People API와 실제 필요한 연락처 읽기/쓰기 범위를 선택한다. 직접 구성 시 API 활성화→OAuth client·동의→계정 연결→허용 표본 조회 순으로 진행한다. 사용자는 계정과 동기화 방향을 정하고 에이전트는 person/resource ID·필드·중복/병합 규칙을 기록한다. 연락처 이름만으로 사람을 병합하지 않는다. 표본 조회·선택한 시험 수정·재조회 후, 해제 때 OAuth/주기 수집을 회수한다. 다른 제공자는 해당 공식 주소록 경로를 같은 계약에 매핑한다. [People 시작 안내](https://developers.google.com/people/quickstart/python)
- **CRM:** 기존 커넥터에서 고객/회사/활동 중 필요한 객체와 읽기·쓰기 scope를 확인한다. HubSpot 직접 구성은 배포 범위에 맞게 단일 계정 static auth 또는 복수 계정 OAuth를 선택한다. 계정 관리자 동의 후 account·object/record ID·담당·필드 매핑·API 버전·토큰 참조·쓰기/검토 범위를 기록한다. 에이전트는 허용 표본을 읽고 쓰기를 선택하면 시험 레코드로 검증하며 다른 고객의 접근 경계와 중복 반영을 확인한다. 해제 시 앱/토큰·웹훅·주기 작업을 회수한다. [HubSpot 인증 안내](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/authentication/overview)
- **뉴스·RSS·구독:** 기존 리더/메일 수집을 재사용하거나 feed URL·허용 주제·최초 조회 기간·주기·건수·저장 위치를 정한다. RSS 항목의 guid/link와 범위·내용 버전으로 중복 규칙을 만들고 피드의 제목/요약을 전체 기사로 간주하지 않는다. [RSS 규격](https://www.rssboard.org/rss-specification) 에이전트는 항목 조회→허용 본문 접근→저장·재검색과 반복 조회 중복 방지를 시험한다. 사용자는 유료/인증 구독 접근을 제공하는 정식 경로를 선택한다. 해제는 구독/예약·키를 중지하며 접근 제한을 우회하지 않는다.
- **사내 업무 API·데이터:** 담당자가 제공한 API 명세·허용 endpoint·스키마·인증·망 접근·시험 환경부터 확인한다. 에이전트는 설치 버전에 맞는 어댑터와 필드 매핑, 요청/결과 ID·수정 조건·중복 방지·조회/쓰기 분리·감사/복구를 구성한다. 사용자는 서비스 계정/관리자 조치를 맡는다. 읽기 표본→허용된 시험 변경→원본 재조회·거부 범위를 확인하고 실제 업무 반영 범위를 확정한다. API가 없으면 허용 CSV/파일 교환·사용자 입력으로 시작하며 자동 연동이라고 부르지 않는다. 해제 시 계정/토큰·네트워크 접근·예약을 회수하고 남은 작업을 인계한다.
