# 선택 구성 검토·최종 체크리스트

**Jev와 Reason Network는 설치를 강제하지 않지만, 검토 결과는 최종 체크리스트와 구축 보고서에 반드시 남긴다.** 이름이 참고자료에만 있거나 설치 목록에서 빠졌다는 이유로 검토 완료로 간주하지 않는다. 필요한 역할을 기존 구성으로 충족하면 미도입이 정상적인 결정이다.

현재 문서는 절차·빈 기록 양식의 안내다. 실제 사용자의 두 제품 도입 여부·계정·설정·시험 결과는 미정이다. 기존 결정은 재사용하고, 제품 설명 전체를 매번 다시 읽거나 같은 선택을 반복 질문하지 않는다.

## 1. 두 선택 요소의 역할

| 항목 | 맡길 수 있는 역할 | 필요성을 판단할 때 | 미도입 시 가능한 구성 |
| --- | --- | --- | --- |
| Jev — 이 가이드에서는 TypeSafe 제품으로 해석 | 반복적인 문서 분류·도구 선택·검토 필요 여부처럼 범위가 좁은 의미 판단을 선택·점수·확률로 반환 | 기존 코드/모델의 반복 판단 비용·지연·품질을 같은 표본으로 비교할 필요가 있는가 | 확정적인 조건은 코드 규칙, 의미 판단은 기존 모델의 분류 전용 프롬프트 또는 사람. 데이터는 기존 DB·Wiki에 유지 |
| Reason Network | 여러 기기·하네스의 에이전트를 발견하고 메시지·업무 요청을 주고받는 통신 계층 | 둘 이상의 실행기가 실제로 협업해야 하며 기존 인계·요청 경로가 부족한가 | 단일 실행기, 기존 지원 handoff/resume, 권한을 확인한 공유 업무 기록과 기존 요청 경로 |

Jev는 DB·LLM Wiki·작업 실행기와 역할이 다르다. Reason Network도 업무 상태 정본·스케줄러·파일 동기화·권한 집행을 대신하지 않는다. 네트워크 연결만으로 다른 호스트의 자료와 완료 상태가 자동으로 합쳐지지 않는다. 두 요소를 쓰더라도 [능동 운영](<능동 운영과 완료 추적.md>)과 [실행기 검증](<../20_도구별/실행기 독립 운영 검증.md>)의 실제 시작·상태·권한·완료 기준을 유지한다.

제품 확인 근거와 비용·제약은 [SQLite와 Jev 확인 사항](<../90_참고자료/SQLite와 Jev 확인 사항.md>), [Reason Network 비용·적용 검토](<../90_참고자료/Reason Network 비용·적용 검토.md>)에 있다. 사용자가 다른 JEV 제품이나 Jev-Mem을 뜻하면 먼저 제품·저장소를 식별하고 해당 역할을 다시 비교한다. 연구 구현을 운영 제품으로 바꾸어 안내하지 않는다.

## 2. 셋업 질문과 결정

### Jev 전의 분류 대안

**추가 유료 API를 연결하기 전에 기존 모델에 분류 전용 역할을 맡기는 방법을 제안한다.** [분류 전용 프롬프트와 검증](<분류 전용 프롬프트와 검증.md>)에 사용자 제안 원문, 입력 후보·6개 JSON 필드, 근거/불확실성 검증과 실행 권한 차단을 담았다. 마스터 지침에는 링크만 두고 분류 작업에 해당할 때 읽는다.

| 비교 후보 | 적합한 범위 | 확인할 조건 |
| --- | --- | --- |
| 코드 규칙 | 날짜·ID·확정 조건 비교 | 기준의 명확성·누락/경계값·변경 관리 |
| 기존 모델 + 분류 전용 프롬프트 | 문맥을 읽어 자료 종류·후속 조치·프로젝트 후보를 제안 | 후보/근거 검증·uncertain·검토 경로·실제 도구 권한 차단·버전/비용/한도 |
| Jev | 기존 방법의 반복 판단 품질·지연·총비용에 확인된 한계가 있음 | 같은 표본 비교, 추가 API·전송·과금·장애 대안의 운영 부담 |
| 사람 검토 또는 혼합 | 모호하거나 오판 영향이 크고 자동 기준이 부족함 | 담당·검토 기한·보류 상태·재시도 상한 |

기존 모델 재사용은 별도 Jev API 도입을 줄이는 대안이다. 구독 사용량·토큰/API·호스트 비용까지 무료라는 뜻은 아니며 Jev와 동등한 성능을 보장하지 않는다. 동일한 한국어·불명확·입력 주입 표본에서 필드별 정확도·잘못된 no/프로젝트 배정·근거 적합률·검토량·총비용·지연을 비교한다. 필요 없는 유료 시험을 먼저 요구하지 않는다.

분류 기능을 선택하면 방식·프롬프트/모델·후보/정책 버전과 기준을 결정 기록에 남긴다. Jev 미도입으로 제외할 수 있는 것은 **Jev 제품 연결 시험**이다. 대신 채택한 분류 기능의 V20 및 해당 V03/V09/V19 검증은 남는다. 분류 자체가 필요 없으면 그 기능의 제외 근거를 별도로 적는다.


현재 업무와 기존 환경에서 답할 수 있는 부분은 먼저 확인한다. 아래는 질문 후보이며 전부 한 번에 묻지 않는다. 실제 선택이 필요한 질문만 1–3개씩 제시한다.

| 항목 | 개인 사용자 | 기업 사용자 |
| --- | --- | --- |
| Jev 필요성 | 반복 분류·판단이 어디에 있고, 현재 품질·월 호출량·지연·비용에 문제가 있는가? 추가 API 없이 기존 규칙/모델로 충분한가? | 어떤 업무의 판단을 줄이려는가? 오판 비용·한국어 평가·허용 전송 자료·처리/보존·예산 책임은 무엇인가? |
| Reason Network 필요성 | 어떤 기기의 어떤 에이전트들이 어떤 일을 주고받아야 하는가? 한 실행기와 기존 상태 재개로 충분한가? | 어떤 팀·기기·프로젝트 사이의 요청을 허용하는가? 참여/회수·수신 정책·허용 폴더·내외부 통신과 감사 책임은 무엇인가? |

두 제품 각각에 다음을 [결정 기록](<../30_양식/구축 결정·규칙 기록.md>)의 “Jev·Reason Network 도입 검토”에 남긴다.

- **도입:** 해결할 문제·제품/버전·역할·적용 범위·비용/권한 근거를 확정하고 설치 ID·시험 ID를 연결한다. 도입 결정과 설치/운영 완료는 다른 상태다.
- **미도입:** 필요 없음 또는 기존 기능으로 충족한다는 이유·대체 구성·재검토 조건을 적는다. 시험 결과는 `적용 제외 + 근거`이며 제품 시험 통과로 쓰지 않는다.
- **보류:** 부족한 정보·현재 업무 영향·대체 경로·담당·재검토 조건과 기한을 남긴다. 필요한 기능이 이 결정에 의존하면 그 기능은 대기/미완료다. 독립 범위는 계속 진행하되 선택한 전체 범위의 완료로 확대하지 않는다.
- **미검토/미정:** 기록이 없는 상태다. 미도입과 다르며 최종 인계에서 반드시 드러낸다. 가능한 설명·대안 비교를 진행한 뒤 남은 쟁점만 질문한다.

이미 확정된 답변·선택은 재질문하지 않는다. 개인/기업 혼합이면 같은 제품도 영역별 도입 여부·처리 자료·권한이 다를 수 있어 행을 나눈다. 새 제품 설치보다 기존 기능 활용을 우선하며, 미도입을 선택하기 위해 제품 설치나 유료 시험을 요구하지 않는다.

## 3. 도입한 경우 확인할 구현·시험

### Jev

- 실제 제품·API·모델 버전, 자격증명 참조, 전송할 필드·질문·출력 형식, 판단 임계값·불확실 처리·오류 대체 경로를 정한다.
- 같은 허용 표본에서 기존 코드/모델과 한국어 품질·오판 비용·전체 지연·총비용을 비교한다. 모델 단가가 낮다는 이유만으로 전체 비용 절감을 확정하지 않는다.
- API 한도·인증 실패·크레딧 소진 402·연결 단절·모델 변경·질문 변경을 시험하고 예산·재시도 상한을 적용한다. 외부 호출을 끈 상태에서도 정한 대체 경로로 업무를 이어갈 수 있는지 확인한다.
- 판단 결과가 권한을 부여하거나 외부 발송·자료 반출을 직접 승인하지 않게 한다. 실제 정책은 실행 계층에서 확인한다.
- 위 결과는 기존 V03/V09/V19/V20의 표본·증거에 연결한다. 문서·가격 확인을 실제 품질 시험으로 대신하지 않는다.

### Reason Network

- 참여 기기·하네스·버전·폴더·계정과 통신 경로를 정한다. 설치 전후 MCP/hooks/사용자 설정·데몬/자동 시작 변경, 중지·제거·복귀 방법을 기록한다.
- 선택 하네스가 공식 지원되는지 해당 버전에서 확인한다. 다섯 실행기를 능동 운영에 사용할 수 있다는 설계와, Reason이 다섯 제품을 모두 자동 연결한다는 주장은 다르다. 미지원이면 어댑터를 검증하거나 기존 경로를 유지한다.
- 허용된 시험용 에이전트에서 발견→요청→수신 정책→업무 실행→결과 재조회까지 확인한다. 메시지 전달·읽음과 실제 완료를 분리한다.
- 작업 ID·담당·권한·외부 결과를 유지하며 중복 요청·응답 유실·수신 거부·참여자 회수·기기 OFF/복귀를 시험한다. 꺼진 호스트의 실행이나 자동 장애 전환을 보장하지 않는다.
- 무료 연결 비용과 실제 모델·호스트·클라우드 세션 비용을 분리한다. 자체 호스팅이면 운영 비용·인증·감사 책임도 기록한다.
- 기존 V03/V05–V08/V15–V17/V19와 능동 P04–P06 중 해당 시험에 연결한다. 설치·peer 표시만으로 업무 인계 성공을 확정하지 않는다.

## 4. 최종 체크리스트와 구축 보고서

기록을 늘리지 않고 기존 세 양식을 사용한다. 결정 정본은 [구축 결정·규칙 기록](<../30_양식/구축 결정·규칙 기록.md>), 작업 위치·설치 포인터는 [셋업 진행 기록](<../30_양식/셋업 진행 기록.md>), **최종 체크리스트·구축 보고서는 [검증·운영 기록](<../30_양식/검증·운영 기록.md>)** 안에 작성한다.

인계 직전에 전체 선택 범위·구성 요소 목록·D01–D09·설치 계획·적용 V/P 시험·남은 작업을 대조한다. Jev·Reason Network 두 행은 미도입이어도 삭제하지 않는다. 이번 검토에 추가된 다른 선택 제품도 같은 표에 행을 추가한다.

- 체크는 검토 항목의 기록·근거가 충족됐다는 표시다. 사이트의 체크 표시나 보고서 작성 자체는 설치·운영 성공의 증거가 아니다.
- 보고서의 두 제품별 항목에는 결정 정본·이유·대안·현재 적용/시험 상태·증거·보류 영향/담당/기한을 요약한다. 같은 값을 새로 확정하거나 오래된 보고서로 정본을 덮어쓰지 않는다.
- 구성 누락, 미검토, 도입했지만 미설치/미검증, 필수 시험 실패가 있으면 해당 범위를 완료로 보고하지 않는다. 비필수 보류를 남길 때도 현재 범위에 영향이 없는 근거와 후속 조치를 공개한다.
- 사용자가 받은 결과는 `실제 운영 준비 완료 범위 / 부분 구축·대기 범위 / 설계·문서 확인만 한 범위`로 구분한다. 가이드 자체의 문서·사이트 배포와 사용자 시스템 구축 결과를 혼동하지 않는다.
