# 업무 시나리오·셋업 질문

이 문서는 **제품을 고르기 전에 어떤 도움이 필요한지 확인하고, 선택한 흐름을 구축 가능한 규칙으로 바꾸는 설계 제안**이다. [초기 셋업 흐름](<초기 셋업 흐름.md>) 1–2단계에서 사용한다. 지식관리·라이프 관리·기업 업무는 **하나, 여러 개 또는 전체를 함께 선택**할 수 있다. 첫 업무 하나로 시작하는 것은 구축 순서이며 최종 사용 범위를 하나로 제한하는 뜻이 아니다.

아래 예시의 시각·규칙·저장 방식은 실제 사용자 결정이 아니다. 답변은 [결정 기록](<../30_양식/구축 결정·규칙 기록.md>)에, 진행 순서·대기는 [셋업 진행 기록](<../30_양식/셋업 진행 기록.md>)에 남긴다. 같은 값을 여러 문서에서 따로 확정하지 않는다.

질문을 실제로 주고받는 순서·구조 갱신·질문 종료 조건과 운영 중 재점검은 [대화형 설계·운영 점검](<대화형 설계·운영 점검.md>)을 따른다. 이 문서는 필요할 때 고르는 질문·시나리오 자료이며 일괄 설문이 아니다. LLM Wiki를 채택하면 [구성 참고](<../90_참고자료/LLM Wiki 구성 참고.md>)로 원문·정리 지식·운영 지침의 경계와 수집·검색·검증·점검 규칙을 구체화한다.

## 1. 필요 선택 → 설계 선택 → 제품 선택

1. **필요한 흐름을 모두 확인한다.** 기존 답변을 먼저 반영하고 미정만 최대 3개씩 묻는다. “자료를 쌓고 다시 찾기 / 목표·일정·할 일 관리 / 팀·회사 업무 처리 중 필요한 것을 모두 골라 주세요. 연결해서 처리할 일도 있나요?”로 시작할 수 있다.
2. **공통 설정은 한 번 확인한다.** 주사용 접점·장비·허용 비용·시간대·기존 자료·인증을 재사용한다. 개인/기업 혼합이면 계정·기억·저장소·검색·발송 권한은 범위별로 나눈다. 개인에게 받은 답변이 회사 정책을 바꾸지 않는다.
3. **필요한 설계 패턴을 확인한다.** 아래 표에서 해당 흐름에 필요한 기능을 채택·보류·제외하고 이유·다시 검토할 조건을 남긴다. 선택한 패턴의 세부 질문만 한다. 제품명이 나온다고 해당 설계까지 채택된 것은 아니다.
4. **구축 순서를 정한다.** 사용자가 정한 전체 범위를 유지하면서 가장 유용한 첫 업무 → 후속 흐름 → 흐름 사이 연결 순으로 구현·검증한다. 각각의 담당·선행 조건·다음 행동을 남긴다. 첫 업무 성공만으로 전체 구축을 완료 처리하지 않는다.
5. **기존 기능과 제품을 대조한다.** 선택한 설계를 현재 도구로 충족하면 그대로 사용한다. 부족한 기능만 연결/구현/다른 제품 후보로 넘기고 실제 지원 범위·운영 부담·비용을 확인한다.

| 설계 선택 항목 | 필요 여부를 묻는 질문 | 필요할 때 정할 규칙 | 관련 요구사항 |
| --- | --- | --- | --- |
| 지식 축적·재검색 | 저장한 자료를 어떤 질문이나 결과물에 다시 쓰고 싶은가? | 원본·위키·검색의 역할, 근거·교정·잊기 | F04·F09 |
| 목표와 실행의 연결 | 목표별로 이번 주 할 일과 실제 진척을 함께 보고 싶은가? | 목표·프로젝트·할 일 연결, 완료 증거, 검토 주기 | F01·F06·F09 |

| 대화 전체 보관·전사 | 전체 음성·채팅을 남길 것인가, 전사/요약만 필요한가? | 입력·처리 범위·보존·접근·교정·후속 반영 | F03·F04·F08 |

| 여러 흐름의 연결 | 회의에서 나온 일을 목표·업무·지식에 함께 연결할 것인가? | 원본 ID·반영 대상·권한·중복·부분 성공 | F03·F04·F06 |

상태 기록·오류 표시·권한 경계처럼 **선택한 기능이 올바르게 동작하는 데 필요한 최소 조건**은 함께 구현한다. 능동 운영을 위해 필요한 예약/감지·상태·실행·전달은 구현한다. 고급 검색·기억/스킬 자기 개선·별도 제품은 역할이 필요할 때만 추가한다. 보류한 흐름의 상세 인터뷰도 실행할 단계까지 미룬다.

## 2. 대표 시나리오와 첫 결과

| 흐름 | 처음부터 끝까지의 처리 | 첫 결과와 검증 | 개인/기업 적용 |
| --- | --- | --- | --- |
| K. 지식관리 | 자료 수집 → 원본 식별·중복/충돌 확인 → 위키 정리·연결 → 검색·출처 답변 → 교정 | 사용자의 실제 질문으로 필요한 근거를 찾고, 수정/잊기 후 답변이 바뀌는지 확인 | 개인은 관심 주제·기존 볼트, 기업은 소유자·갱신 주기·원문 권한을 추가 |
| L. 라이프 관리 | 예약/변화 감지 → 목표·미완료·일정 조회 → 우선순위·첫 행동 선제 제안 → 허용 실행/수정·재조회 → 저녁 실제 완료·남은 일·내일 안 → 주간 목표 검토 | 목표에 연결된 다음 행동과 완료/대기 이유가 보임. 알림 전송·시간 경과로 완료되지 않음 | 개인은 본인의 확인·생활 리듬, 기업 일정과 함께 볼 때는 허용된 시간 정보만 통합 |
| E. 기업 업무 | 요청 접수 → 요청자 권한으로 근거 조회 → 초안/작업 생성 → 필요한 검토 → 실제 시스템 반영 → 조회 확인·감사 | 업무 원본의 결과 ID·담당·증거 확인. 다른 팀 자료·권한 밖 행동은 차단 | 개인 업무에도 인계·고객 요청이 있으면 적용. 기업은 조직 정책·업무 책임·검토 담당을 연결 |
| C. 대화 자료 처리 — 공통 선택 모듈 | 녹음/파일/채팅 수집 → 원본 보관 → 전사/화자·시각 정리 → 요약·결정·할 일 후보 → 검증 후 필요한 K/L/E에 연결 | 원본까지 추적 가능한 정리와 확정/미확정 구분. 전사 성공을 후속 업무 완료로 보지 않음 | 개인/기업 각각 보관·접근·처리 정책 적용. [대화 가이드](<대화 수집·전사·지식화.md>) 참조 |

K/L/E의 일부 단계만 원하면 해당 범위로 시작한다. 기본 목표는 에이전트가 먼저 확인·제안·후속 점검하는 운영이다. 아침·저녁·주간의 실제 시각/시간대·범위·발신 채널은 셋업에서 정하고 예약/이벤트를 실제 연결한다. 단순히 요청형 회고를 시연하고 능동 운영 완료로 기록하지 않는다. 모든 흐름을 고르면 공통 수집·인증·상태 역할은 재사용하되, 데이터를 무조건 한 기억 저장소에 합치지 않는다.

### 능동 운영에 필요한 공통 질문

[능동 운영과 완료 추적](<능동 운영과 완료 추적.md>)에 따라 관찰할 목표/작업·자료, 시작 시각/이벤트, 자동 수정 범위, 완료 근거, 결과 받을 위치, 중단·재알림/비용 한도를 정한다. 운영 때는 먼저 최신 근거와 다음 행동 안을 준비하고, 시스템이 알아낼 수 없는 판단만 묻는다. 개인은 생활 리듬·본인 확인을, 기업은 업무 시간·담당/부재·기한·팀 권한을 추가한다. [실행기 독립 운영 검증](<../20_도구별/실행기 독립 운영 검증.md>)으로 사용하는 도구의 실제 기동 경로를 확인한다.

### K. 지식관리에서 추가로 물을 것

- 공통: 자주 묻는 질문 3개와 원하는 출처 표시 방법은 무엇인가? 어떤 자료를 원본으로 보존하고 어떤 범위의 교정·삭제를 허용할 것인가?
	- 개인: 기존 Obsidian/문서/메모 중 기준 원본, 선호하는 분류·연결, 한국어·혼합언어·별칭 검색, 개인 기억에서 제외할 자료를 확인한다.
	- 기업: 문서 책임자·최신 버전·검색 사용자 범위, 권한 회수·퇴사·원문 삭제 시 색인/답변 반영 시간을 확인한다.
- 실제 질문을 소규모 평가 세트로 저장한다. 정답 문구보다 필요한 출처를 찾는지, 모르면 모른다고 하는지, 오래된/교정된 사실을 구분하는지, 제한 자료가 나오지 않는지 평가한다. 새 검색 제품은 이 기준에서 기존 기능의 부족이 확인될 때 비교한다.

### E. 기업 업무에서 추가로 물을 것

- 공통: 요청의 책임자는 누구인가? 초안·시스템 변경·발송 중 어디까지 맡길 것인가? 무엇을 조회하면 실제 완료를 확인할 수 있는가?
	- 개인: 본인 업무라도 고객·협업자 자료의 처리 범위와 외부 전달 대상을 구분한다.
	- 기업: 담당자와 실행 에이전트, 검토가 필요한 조건·권한·부재 시 인계, 계정 회수와 보존 의무를 조직 기준에 맞춰 정한다. 기존 업무 도구의 승인·권한·감사를 우선 사용한다.
- 에이전트의 초안 생성과 담당자의 업무 완료를 분리한다. 승인받은 내용·대상이 달라지면 해당 변경만 다시 판단한다. 모든 읽기·초안 작업에 일괄 승인 절차를 붙이지 않는다.

## 3. 목표·프로젝트·할 일·일정을 연결하는 방법

L 또는 목표 연계가 필요한 K/E를 선택했을 때만 상세화한다. 시작 질문은 “이번 기간에 이루려는 결과와 완료 기준은?”, “이미 쓰는 일정·할 일 관리 방식은?”, “제안·변경·완료 확인 중 어디까지 맡길 것인가?”다. 목표가 필요 없는 단순 할 일은 목표 연결 없이 사용할 수 있다.

| 역할 | 최소 기록 | 관계와 권위 |
| --- | --- | --- |
| 목표 | goalId·원하는 결과·기간·판정 기준·담당 | 할 일 개수와 별도로 결과 달성 여부를 검토 |
| 프로젝트 — 필요 시 | projectId·목표 참조·산출물·현재 상태 | 여러 행동을 하나의 결과로 묶을 때 사용 |
| 사용자의 할 일 | taskId·다음 행동·담당·상태·완료 기준·근거 | 업무 상태의 기준 원본 하나를 정하고 goal/project를 참조 |
| 일정/시간 블록 — 필요 시 | calendar/event 참조·시작/종료·시간대·관련 taskId | 약속 또는 실행할 시간. 같은 할 일을 여러 블록에 배치 가능 |
| 에이전트 실행 | runId 또는 내장 세션·사용자 task 참조·결과/오류 | 에이전트가 처리한 단계. 사용자의 할 일 상태와 분리 |

필드명은 개념 계약이다. 기존 제품의 ID·노트 링크·업무 설명으로 충족하면 별도 DB를 만들지 않는다. 목표·프로젝트 맥락을 노트에, 실행 상태를 기존 할 일 도구에, 시간을 Calendar에 두는 구성이 가능하다. 도구에 없는 목표나 마감 필드를 임의로 다른 필드에 덮어쓰지 않는다.

1. 목표에서 이번 기간에 가능한 행동을 제안한다. 이미 있는 할 일과 대조해 중복 생성하지 않는다.
2. 행동의 예정일·실제 마감·예상 소요 시간·가능 시간을 구분한다. 회의 참석자나 고객 약속의 변경 권한은 개인 시간 블록 변경과 별개다.
3. 정한 권한에 따라 시간 확보를 제안하거나 반영하고, 원본 ID·버전·결과를 조회한다. 일정 충돌·시간대 변경·반복 회차·미지원 필드는 명시한다.
4. 완료 근거를 확인해 해당 할 일/회차만 변경한다. 미완료는 허용된 누락/오류를 수정·재검사하고, 남은 사유·다음 행동·다음 확인 시각/조건·담당을 지속 상태에 남긴다. 자동 재배치 여부·횟수·최대 연기 범위는 사용자 규칙으로 정한다.
5. 주간 검토에서는 완료 개수 외에 목표 결과의 변화·막힌 이유·다음 행동을 본다. 목표 수정은 제안과 확정을 구분한다.

예시: `목표 G1: 강의 준비 완료 → 프로젝트 P1: 강의안 → 할 일 T1: 초안 1개 검토 → 시간 블록 E1: 수요일 14–15시`. 15시가 되거나 “검토하세요” 알림이 도착해도 T1은 미완료다. 사용자의 완료 표시 또는 미리 합의한 검토 결과가 확인돼야 T1을 완료한다. 초안 파일의 존재만으로 실제 검토·전체 목표 달성을 추정하지 않는다.

### Google Calendar를 사용할 경우

Calendar 화면의 **‘일정’은 시간·참석**, **‘할 일’은 해야 할 일과 완료 상태**에 사용한다. 별도 Tasks 앱을 설치하지 않아도 Calendar에서 할 일을 다룰 수 있지만 데이터는 Tasks와 연결된다. 화면에서 가능한 시간·Deadline·반복 기능과 공개 API 지원은 같지 않다. Tasks API의 `due`를 시각이 있는 실제 마감으로 구현하지 않는다. 정확한 현재 범위는 [일정·할 일 도구 확인 사항](<../90_참고자료/일정·할 일 도구 확인 사항.md>)을 따른다.

- 개인: 이미 Calendar를 쓰면 그 화면과 기존 노트부터 검토한다. 사용자가 화면에서 직접 관리하고 에이전트는 조회·제안을 하는 경로도 완성된 선택지다. 필요한 자동화가 미지원일 때만 Tasks 연결·이벤트 시간 블록·다른 업무 도구를 비교한다.
- 기업: 기존 업무 시스템을 담당·상태·검토의 원본으로 유지하고 Calendar는 회의/시간 접점으로 활용할 수 있다. Calendar 공유만으로 팀 업무 배정·업무 권한이 충족된다고 가정하지 않는다.
- 공통: Calendar 커넥터의 존재와 할 일 API 접근을 따로 확인한다. 미지원 값은 노트 등 지정 위치에 보존하고 사용자에게 수동/자동 지원 범위를 안내한다. 시간 확보는 Calendar 할 일 또는 별도 이벤트 중 채택한 경로로 만들고 중복 블록을 방지한다.

## 4. 알림과 실제 완료를 구분하는 규칙

최소한 **실행 결과·전달 상태·업무 상태**를 따로 확인한다. 실제로 쓰는 도구의 상태명에 매핑하며, 모든 상태를 별도 데이터베이스에 구현할 필요는 없다.

| 관찰 | 의미 | 업무 완료 판정 |
| --- | --- | --- |
| 알림 예약/전송 요청/전달 성공 | 플랫폼이 지원하는 수준의 전달 상태 | 완료 근거가 아님. 읽음도 실제 행동의 증거가 아님 |
| “확인”, 읽음, 이모지 반응 | 수신 확인 또는 모호한 응답 | 미리 합의한 명시적 완료 표현이 아니면 완료로 바꾸지 않음 |
| 일정 종료·마감 경과·알림 해제 | 시간이 지났거나 알림을 닫음 | 완료가 아님. 연체·확인 필요와 구분 |
| 원본 도구에 완료 표시를 기록 | 시스템의 상태 변경 성공 | 누가 어떤 근거로 표시했는지 함께 확인 |
| 사용자 “T1 완료” 또는 합의한 결과를 조회 | 선택한 완료 기준을 충족하는 증거 | 해당 할 일/회차 완료, 확인 주체·시각·근거 기록 |
| 조회 실패·응답 없음 | 결과를 알 수 없음 | 미확인/대기. 임의 완료나 반복 실행으로 보완하지 않음 |

개인 생활 행동은 사용자의 명시적 완료 체크만으로 충분하도록 정할 수 있다. 모든 행동에 사진·상세 생활 로그를 요구하지 않는다. 기업의 제출·발송·반영은 해당 업무의 합의된 원본 결과·검토 기준으로 판단한다. 완료를 되돌리면 원본 상태를 갱신하고 관련 회고도 정정한다.

알림을 선택한 사용자에게만 묻는다: “언제 조용히 있어야 하나?”, “어떤 변화만 즉시 알려야 하나?”, “한 번 놓치면 언제까지 몇 번 다시 알릴까?” 답변으로 시간대·조용한 시간·긴급 예외·정기 묶음·변화 없음 시 생략·횟수/빈도 상한·중복 키·일시 중지·해제 방법을 정한다. 개인/회사 알림을 함께 받으면 채널별 규칙과 합산 빈도를 함께 확인한다.

알림 실패와 업무 실행 실패를 구분한다. 결과가 이미 생성됐다면 알림 실패 때문에 같은 업무를 재실행하지 않는다. 서버가 꺼졌을 때 이미 서비스에 등록된 알림과 에이전트의 새 분석·맞춤 알림을 구분한다. 재시작 후 지난 알림을 모두 몰아 보내지 않고 만료·묶음·중복 규칙을 적용한다. 필요하지 않은 예약·상시 프로세스는 설치하지 않는다.

## 5. 기억·스킬 자동 변경의 검증 절차

먼저 **관찰을 저장하는 것**, **현재 유효한 기억을 바꾸는 것**, **앞으로 실행할 절차를 바꾸는 것**을 구분한다. 자동 개선을 원하지 않으면 사용자가 요청한 교정만 처리한다. 자동 축적이 곧 자동 정책 변경을 뜻하지 않는다.

| 단계 | 기억 변경 | 스킬·규칙 변경 |
| --- | --- | --- |
| 1. 후보 생성 | 출처·발언자·기록 시각·사실이 유효한 기간·개인/팀 범위·확정/추정 기록 | 실패/피드백 근거, 대상 파일·현재 버전, 변경 차이·예상 영향 기록 |
| 2. 기본 검사 | 원문과 일치, 중복·모순·만료·고정 기억·민감 정보·원문 권한 확인 | 호출 조건·필수 규칙·권한·비밀 노출·의존성·코드/명령 부작용 확인 |
| 3. 적용 전 검증 | 실제 질의 표본에서 최신/과거 구분·교정·잊기·근거·권한 검사 | 정상·예외·금지 행동 회귀 사례, 변경 전후 품질·시간·호출/비용 비교 |
| 4. 적용 판단 | 사전 허용한 종류·범위만 자동 반영. 미해결 모순·추정은 후보/검토 대기. 권한 있는 사용자의 명시 교정은 기존 허용 범위에서 검증 후 반영 | 사전 허용된 변경 유형과 검증 기준을 통과한 경우만 자동 적용. 그 밖은 담당자 검토 |
| 5. 활성화·추적 | 유효한 버전·적용 범위·근거·검증 결과 기록 | 배포 범위·실제 로드된 버전·검증 결과 기록 |
| 6. 관찰·복귀 | 오답/권한 문제 시 이전 유효 기억 또는 재검토 상태로 복귀 | 문제 버전 중지·정상 버전 복귀·영향받은 실행 확인 |

질문은 “어떤 기억/절차를 자동으로 바꿔도 되는가?”, “무엇은 고정하거나 담당 검토가 필요한가?”, “어떤 예시를 통과하면 적용해도 되는가?”로 구체화한다. 이미 허용한 저위험 기록·교정에 매번 재승인을 요구하지 않는다.

- 개인: 직접 밝힌 선호·수정 요청과 에이전트가 추론한 성향을 구분한다. “이번 주만”이라는 말은 영구 선호로 덮어쓰지 않는다. 고정한 기억·발송/삭제/과금 권한 확대는 일반 자동 학습 범위에서 제외한다.
- 기업: 개인·팀·조직 변경 담당을 구분한다. 개인 대화가 공용 규칙을 바꾸지 않으며, 정책·데이터 접근·공유 스킬 변경은 정해진 관리 경로를 적용한다. 조직별 실제 검토 요구를 확인하고 불필요한 승인 단계를 추가하지 않는다.
- 공통: 생성한 에이전트의 “괜찮다”는 판단만으로 적용하지 않는다. 출처 대조·권한 검사·실행 가능한 검사와 결과를 남긴다. 새 실행 코드·외부 스킬은 격리 검증 등 필요한 검토를 거치며 실서비스에 곧바로 실행하지 않는다. 검증 실패·시간 초과·비용 초과 시 기존 정상 버전을 유지한다.

기억 삭제·권한 회수는 검색 색인·요약·캐시에도 반영한다. 복귀가 삭제된 민감 기억이나 회수된 권한을 되살리지 않게 한다. 스킬 복귀는 이미 발송한 메시지·변경한 외부 자료를 자동으로 되돌리지 않으므로 실제 부작용과 후속 조치를 별도 기록한다. 근거·시험을 위한 보관도 정한 보존/삭제 정책 안에서 수행한다.

추가 기억을 반영할 때 기존의 유효한 기억을 통째로 덮어쓰지 않는다. 복귀는 문제를 일으킨 변경을 대상으로 하며, 다른 유효한 교정·추가·삭제가 유지되는지 확인한다.

## 6. 여러 흐름을 함께 사용할 때

예를 들어 대화 C에서 “다음 주 회사 제안서를 검토”라는 후보를 추출하면, 확인된 기업 업무 E를 원본으로 만들고 허용된 목표/프로젝트에 연결한다. 개인 L에는 바쁜 시간만 표시할 수 있고, 공유 가능한 지식만 K에 반영한다. 모든 원문을 개인 기억과 회사 위키 양쪽에 복제하지 않는다.

- 공통: 원본 대화/문서 ID → 후보 → 확정 task → 시간 블록 → 결과/지식의 참조를 유지한다. 같은 항목이 여러 흐름에서 감지돼도 중복 생성하지 않는다. 한 저장 실패를 전체 성공으로 보고하지 않는다.
- 개인: 일·생활 목표를 함께 보더라도 계정별 쓰기 범위와 민감 자료 노출을 정한다. 통합 일정이 필요 없으면 화면도 분리할 수 있다.
- 기업: 원문 권한이 없는 개인 접점으로 제목·요약·첨부를 내보내지 않는다. 허용된 busy 시간/비민감 참조만 통합하는 안을 제공하며, 그 메타데이터도 반출 정책을 따른다.
- 검증: 선택한 K/L/E 각각의 첫 업무 외에 연결 사례 한 가지를 시험한다. 대화 교정 후 잘못된 할 일/기억 수정, 회사 권한 회수 뒤 개인 검색 차단, 알림 전달과 실제 완료 분리, 부분 실패 재개를 해당 범위에서 확인한다.

## 7. 제품 도입 판단과 인계

설계 선택 뒤 제품마다 `필요한 능력 / 기존 수단 / 부족한 점 / 후보 / 실제 지원 버전·OS·앱·플랜 / 비용 / 원본·권한·이전·복귀 / 확인 근거`를 기록한다. 커뮤니티판과 유료판의 권한 동기화·SSO·감사 기능을 같은 것으로 가정하지 않는다. 공개 GitHub나 트렌딩 등재는 채택 이유 자체가 아니다.

이 문서의 연결·검증 패턴은 제품과 독립된 제안이다. 도입하는 제품만 설치 명세와 연결 계약에 올린다. Calendar 사실 확인은 [도구 확인 사항](<../90_참고자료/일정·할 일 도구 확인 사항.md>), 대화의 세부 질문은 [대화 가이드](<대화 수집·전사·지식화.md>), 기기·전원·비용은 [백엔드 설계](<백엔드·기기 연속성·비용 설계.md>)를 사용한다.

인계 시 선택한 전체 범위·완료한 흐름·보류/미완료 흐름·연결 상태와 다음 구축 순서를 보여 준다. 실제 자동화 지원 범위, 사용자의 완료 표시 방법, 알림 중지, 기억 교정·잊기, 잘못된 스킬 복귀를 직접 따라 할 수 있게 안내한다. 실제 검증은 [검증·운영 기록](<../30_양식/검증·운영 기록.md>)에 남긴다.
