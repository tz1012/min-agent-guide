# LLM Wiki 구성 참고

지식관리 흐름에서 LLM Wiki가 필요할 때 사용하는 구성 참고다. 라이프 관리·기업 업무와 함께 선택할 수 있다. 아래 확인 내용과 이 패키지의 설계 제안을 구분하고, 답변으로 정한 구성만 [결정 기록](<../30_양식/구축 결정·규칙 기록.md>)과 [초기 셋업](<../10_구축/초기 셋업 흐름.md>)으로 넘긴다. 이 문서는 외부 사이트 없이도 역할·질문·검증 범위를 이해하도록 작성했다. 키트를 설치하거나 기존 위키를 변경한 기록은 아니다.

## 1. 출처에서 확인한 구성

확인일은 **2026-10-28**이다. 사이트는 아키텍처 v2.9와 템플릿 v1.13.0을 안내하며, 해당 릴리즈는 2026-10-21 공개되었다. 버전별 실제 파일을 우선 확인한다. [사이트](https://llm-wiki.cmdspace.work/), [v1.13.0 릴리즈](https://github.com/johnfkoo951/cmds-llm-wiki/releases/tag/v1.13.0)

| 구분 | 역할 | 대표 경로 |
|---|---|---|
| 원자료 | 위키 주장을 추적할 수 있는 수집 원문 | `10. Raw Sources/` — 기사·논문·책·전사·클리핑 등 |
| 편집된 지식 | 원자료를 종합한 개념·인물/도구·가이드·주제 지도 | `20. Wiki/` — Concepts·Entities·Guides·Maps |
| 규칙 | 폴더·메타데이터·작업·검증 기준 | `CLAUDE.md`, `AGENTS.md` |
| 운영 지원 | 수집 대기, 질의 결과, 도구 산출물, 첨부, 설정 | `00. Inbox/`, `30. Queries/`, `70. Outputs/`, `80. References/`, `90. Settings/` |
| 맥락·탐색·이력 | 사용자 목적, 페이지 목록, 변경 기록 | `Core Context.md`, `index.md`, `log.md` |

핵심은 원자료·편집된 지식·규칙의 세 역할이다. 번호가 붙은 모든 폴더를 독립적인 아키텍처 계층으로 세지 않는다. 사람의 원래 노트와 에이전트가 편집하는 지식의 작성 책임도 구분한다. [사이트의 구조 설명](https://llm-wiki.cmdspace.work/)

공개 키트는 **단독 운영(Mode A)**과 **기존 PKM 볼트에 연결하는 위성 운영(Mode B)**을 제공한다. 모선 연결은 선택이며 qmd 검색과 Web Clipper도 선택 항목이다. 현재 위키가 있으면 새 키트 생성부터 시작할 필요가 없다. [v1.13.0 셋업 가이드](https://github.com/johnfkoo951/cmds-llm-wiki/blob/v1.13.0/90.%20Settings/Sharing/Setup%20Guide.md)

## 2. 명령 이름보다 작업 계약을 먼저 정한다

| 공개 문서의 작업 | 읽기·쓰기와 결과 |
|---|---|
| `ingest` | 목적을 확인하고 원문을 보존한 뒤 지식 페이지를 작성·연결 |
| `query` | 근거를 검색해 답변; 재사용할 결과는 별도 저장 가능 |
| `lint` | 링크·메타데이터·고아·오래된 맥락 등을 점검하고 보고; 자동 수정하지 않음 |
| `verify` | 한 페이지의 주장·출처·정합성을 검증하고 검증 상태와 이력을 기록 |
| `audit` | 볼트·주제군을 점검하여 개별 검증 우선순위를 만들고 보고서를 저장 |
| 보조 작업 | 수집 대기 처리, 상태 집계, 검색 색인 갱신, 사용자 맥락 갱신 |

따라서 `lint`의 읽기 중심 점검과 `verify`의 상태 쓰기, `audit`의 보고서 저장은 같은 권한으로 취급하지 않는다. 모든 페이지를 매번 재검증하기보다 변경·충돌·오래된 근거에 따라 범위를 정한다. [아키텍처 운영 문서](https://llm-wiki.cmdspace.work/docs/)

키트의 `onboard`는 위치·사용자 맥락·재활용 목적과 단독/모선 연결을 인터뷰하고 미완료 단계부터 재개한다. 이는 이 패키지의 대화형 설계에 참고할 수 있는 방식이다. [v1.13.0 onboard 원문](https://github.com/johnfkoo951/cmds-llm-wiki/blob/v1.13.0/90.%20Settings/94.%20Agent%20Settings/claude/commands/onboard.md)

**명령이 모든 에이전트에 내장된 것은 아니다.** 셋업 가이드는 Claude 명령 11개와 Codex 명령·스킬 10개를 구분하고 Codex 쪽의 `onboard` 제외를 명시한다. 키트 명령을 지원하지 않는 실행기에서는 이 패키지의 문답을 자연어로 수행하고, 선택한 제품·버전의 실제 지원 방식을 확인한다. 공개 사이트의 동등성 설명만으로 슬래시 명령·훅 실행까지 동일하다고 확정하지 않는다. [v1.13.0 셋업 가이드](https://github.com/johnfkoo951/cmds-llm-wiki/blob/v1.13.0/90.%20Settings/Sharing/Setup%20Guide.md)

에이전트 설정을 일반 폴더의 정본과 기기별 링크로 나누는 구성도 제공된다. 키트를 선택한다면 전달·동기화 뒤 숨김 폴더와 링크가 실제로 유효한지 확인한다. 이 프로젝트의 배포 폴더 자체를 외부 키트의 링크 구조로 바꾸는 요구는 아니다. [v1.13.0 README](https://github.com/johnfkoo951/cmds-llm-wiki/blob/v1.13.0/README.md)

## 3. 질문으로 확정할 항목 — 이 패키지의 설계 제안

다음은 출처의 질문을 그대로 복제한 목록이 아니라 **현재 시스템 목적에 맞춘 설계 질문**이다. 처음에는 첫 행에서 출발하고, 답변에 영향을 받는 항목을 한 번에 1–3개만 이어 묻는다. 다른 흐름에서 이미 정한 답변은 재사용한다.

| 질문의 초점 | 개인 사용자에게 확인할 예 | 기업 사용자에게 추가할 예 | 확정할 항목 |
|---|---|---|---|
| 1. 재사용 목적 | “한 달 뒤 어떤 질문이나 결과물에 이 자료가 쓰이면 성공인가요?” | “어느 역할의 어떤 업무 판단을 지원하나요?” | 목적·대상 사용자·대표 질의·성공 근거 |
| 2. 작성 책임과 경계 | “기존 노트는 직접 쓰고 AI 편집 공간만 나눌까요, 단독 위키로 시작할까요?” | “팀별 원본 접근 권한과 공유 지식 승인 책임은 누구에게 있나요?” | 기존 구조 유지/단독/위성, 사람·에이전트의 쓰기 범위 |
| 3. 수집 범위 | “웹·문서·대화 중 무엇을 남기고, 무엇은 남기지 않을까요?” | “외부 처리 금지 자료와 보존·회수 조건은 무엇인가요?” | 수집 목적·허용 원문·보존·삭제 전파·대화 분기 |
| 4. 지식의 단위 | “요약 한 장이면 충분한가요, 반복 활용할 개념과 근거를 연결해야 하나요?” | “주장별 원문·작성자·적용 시점까지 추적해야 하나요?” | 페이지 유형·출처 연결·충돌·유효 시점·중복 처리 |
| 5. 변경과 검증 | “자동 수정해도 되는 부분과 직접 검토할 부분은 무엇인가요?” | “게시·권한 변경·정책 문서 변경을 누가 확정하나요?” | 초안/활성 범위·검증 증거·검토자·복귀 기준 |
| 6. 검색과 연결 | “휴대폰에서 무엇을 찾고 어느 작업으로 이어가고 싶나요?” | “같은 질문에도 권한에 따라 결과가 달라져야 하나요?” | 검색 접점·원본 ID 연결·접근 통제·서버 꺼짐 대응 |
| 7. 유지와 중단 | “틀린 답이나 오래된 목적을 어떻게 발견하면 점검을 시작할까요?” | “관리자 변경·퇴사·원문 권한 회수 때 무엇을 재검증하나요?” | 점검 계기·책임자·비용 한도·보류/재개 조건 |

한 문답마다 **답변 요약 → 필요한 경우 실제 사례·반례 확인 → 확인된 사실과 가정 구분 → 설계 선택 및 영향 기록**으로 진행한다. 명확한 답변에는 추가 질문 없이 구조를 갱신한다. 예를 들어 “회의에서 나온 것은 전부 할 일로 만들기”에는 “아이디어·인용·이미 취소된 약속도 포함되나요?”를 이어 묻고, 대화 근거를 가진 업무 후보와 실제 등록·완료를 구분하는 규칙으로 바꾼다. 대화 자료를 선택한 경우 [대화 수집·전사·지식화](<../10_구축/대화 수집·전사·지식화.md>)를 함께 적용한다.

## 4. 첫 구축과 운영 점검에 연결하는 방법 — 설계 제안

자동 수집·재사용을 선택하면 [콘텐츠 수집·지식 재사용](<../10_구축/콘텐츠 수집·지식 재사용.md>)이 필수 구축 계약이다. 입력별 기본 동작·트리거·종합/연결·목록/이력·검색 접점을 실제 구성하고 새 대화 재검색까지 시험한다. 참고 문서를 읽거나 폴더만 만든 상태로 완료 처리하지 않는다.

| 단계 | 수행할 일 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 설계 확정 | 위 질문의 필요한 답변을 한 장의 구성 설명과 결정 기록으로 정리 | 누가·무엇을·어디에·어떤 권한으로·어떻게 검증하는지 설명 가능 |
| 최소 골격 | 정한 원자료/지식/규칙 역할과 맥락·목록·이력 파일만 준비 | 기존 자료와 규칙을 덮어쓰지 않고 경로·쓰기 범위 확인 |
| 첫 순환 | 허용된 자료 한 건 수집 → 필요한 지식 페이지 작성 → 실제 질문 → 근거 확인 | 원문 연결·실제 인용·중복 처리·미확인 표시가 일치 |
| 연결 검증 | 선택한 라이프·기업 흐름으로 필요한 정보만 넘김 | 원문·지식·업무 ID가 연결되고 접근 권한·완료 상태는 구분 |
| 운영 재점검 | 사용자의 기대와 실제 질의·변경 이력 표본을 비교 | 불일치를 근거 오류/규칙 오류/검색·연결 오류로 나누고 수정 범위 확정 |
| 수정 후 확인 | 영향받은 페이지·질문·권한 범위만 다시 검증 | 변경 전후 근거·복귀 지점·미해결 항목 기록 |

지식 저장소는 실행 중 작업의 상태 저장소를 대체하지 않는다. 위키에 업무 방법이 적혀 있어도 해당 업무가 실행·완료된 것은 아니다. 마찬가지로 위키의 설명을 에이전트 권한이나 활성 스킬로 자동 승격하지 않는다. 기억·스킬 변경은 [업무 시나리오·셋업 질문](<../10_구축/업무 시나리오·셋업 질문.md>)의 후보·검증·적용·복귀 절차로 넘긴다.

## 5. 그대로 가져오지 않을 부분과 미확인 범위

- **읽음과 검증을 분리한다.** 문서에는 `explored`를 사람의 읽음 또는 에이전트 근거 검증과 연결한 설명이 있지만, v1.13.0 학습 보드는 사람의 읽음으로 설명한다. 우리 설계에서는 인간 검토(`humanReviewed` 또는 의미를 명시한 `explored`)와 근거 검증(`verificationStatus`, 시각·주체)을 별도로 기록한다. MOC 지도 검토를 그 안의 모든 주장 검증으로 계산하지 않는다. [운영 문서](https://llm-wiki.cmdspace.work/docs/), [v1.13.0 릴리즈](https://github.com/johnfkoo951/cmds-llm-wiki/releases/tag/v1.13.0)
- **구조는 선택하고 페이지 수는 결과로 센다.** 재사용 목적에 필요한 분량만 작성한다. 외부 키트의 페이지 생성 목표나 예시 분류를 개인·기업 모두의 필수 수량으로 삼지 않는다. 기존 볼트 내부 분리를 별도 볼트로 자동 이관하지 않는다.
- **원문 보존과 보존 기간을 함께 정한다.** 근거를 요약으로 덮어쓰지 않되, 사용자가 정한 삭제·접근 회수 정책은 관련 원문·지식·검색 사본에 반영한다. 원문 저장 공간과 접근 권한부터 확정한다.
- **검색 제품과 보드는 선택이다.** 기존 검색으로 대표 질의를 만족하면 유지한다. 검색 인덱스·학습 보드·별도 벡터 저장소는 필요와 비용을 확인한 뒤 추가한다. 재검색이 불필요해지거나 잘못된 인용이 사라진다고 보장하지 않는다.
- **외부 명령은 현재 실행 권한이 아니다.** 외부 문서의 삭제·일괄 치환·설정 링크 복구 코드를 복사해 곧바로 실행하지 않는다. 선택한 키트의 버전·대상 경로·현재 설정·되돌리는 방법을 설치 명세에서 확인한다.
- **실행은 미검증이다.** 이번 확인은 공개 문서·v1.13.0 파일의 역할과 절차까지다. 다운로드 ZIP의 전체 내용·훅 실행·현 사용자의 검색 환경·Codex/Hermes 호환·동기화·기업 권한 차단·복구 성능은 실제 구축 단계의 검증 대상으로 남긴다.

외부 자료의 역할 설명을 이 문서에 요약했으며 사이트 전체를 복제하지 않았다. 새 위키 설치나 기존 볼트의 인제스트·전면 개편은 별도 실행 작업이다.
