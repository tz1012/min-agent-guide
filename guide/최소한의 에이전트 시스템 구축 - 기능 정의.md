# 최소한의 에이전트 시스템 구축 — 기능 정의

## 1. 문서의 목적과 판단 기준

이 문서는 **에이전트의 도움으로 개인 또는 엔터프라이즈 시스템을 구축하고 운영하는 데 필요한 기능·설정 정보·검증 방법을 정의**한다.

사용자가 얻으려는 것은 **자신의 자료를 기억하고, 할 일을 챙기며, 업무를 이어가는 AI**다. 에이전트가 목표·자료·진행 상태를 먼저 확인해 다음 행동을 제안하고, 허용된 작업은 실제 결과를 재조회해 누락·오류를 수정하며 완료까지 이어가는 것이 기본 목표다. 아침의 우선순위·첫 행동, 낮의 변화 대응, 저녁의 완료 근거·남은 일·내일 안을 사용자의 매번 요청 없이 준비한다. [README의 요청·결과 예시](README.md)를 안내 사이트에도 먼저 보여주고, 제품·DB·설치 설명은 그 목적을 달성하는 수단으로 안내한다. 실제 제공 기능은 선택한 연결·규칙·실행 환경에서 검증한다.

판단 기준은 하나다. **이 문서를 가지고 시스템을 구축하고 운영할 때 빠지는 요소나 정보가 있는가?**

여기서 최소한이란, 선택한 업무를 처음부터 끝까지 처리하고 결과를 확인하며 실패에서 복구하는 데 필요한 가장 작은 구성을 뜻한다. 필수 역할은 기존 도구의 내장 기능으로 충족할 수 있다. 선택한 기능에는 담당자, 설정값, 실행 방법, 완료 증거를 붙인다.

- **문서 상태**: 1차 정리본. 아직 실제 구축 환경·대표 업무·구체 설정값은 미정이다.
- **문서 운영**: 핵심 요구사항은 이 문서를 단일 원본으로 유지한다. 폴더 단독 구축을 위해 공통 절차·도구별 안내·결정 양식·시험 자료·공식 참고자료 요약을 함께 제공한다. 실제 결정·규칙·연결 계약은 [결정 기록](<30_양식/구축 결정·규칙 기록.md>), 구현·시험·운영 증거는 [검증 기록](<30_양식/검증·운영 기록.md>)에 남긴다.
- **폴더 진입점**: [README](README.md)와 [공통 원칙](AGENTS.md). [참고자료 목록](<90_참고자료/참고자료 목록.md>)에 공식 문서와 필요한 확인 내용을 수록했다. 개인 원문은 공개하지 않으며 필수 구축 의존성이 아니다.
- **적용 방식**: 아래 공통 요구사항에 개인 또는 엔터프라이즈 하위 항목을 적용한다. 두 형태가 함께 존재하면 데이터·권한 경계를 명시한다.
- **설계와 사실의 구분**: 하위 항목과 우선순위는 구축을 위한 설계 제안이다. 특정 제품의 지원 여부나 설치 완료를 의미하지 않는다.

## 2. 최소 구축 범위

- **공통 출발점**
	- 대표 업무 한 가지, 요청 창구 한 가지, 그 업무에 필요한 자료 연결부터 구성한다.
	- 지식관리·라이프 관리·기업 업무는 복수 또는 전체를 선택할 수 있다. 필요한 전체 범위와 구축 순서를 나눠 기록하고, 첫 업무 이후 선택한 후속 흐름과 상호 연결까지 진행한다. 공통 설정은 재사용하고 개인/기업 권한은 분리한다.
	- 하나의 에이전트로 시작하는 안을 기본 후보로 두고, 역할 분리가 필요할 때 확장한다.
	- 요청 → 맥락 확보 → 도구 실행 → 결과 검증 → 전달·저장 → 피드백까지 연결한다.
- **개인 시스템**
	- 사용자 본인의 업무·자료·계정과 운영 가능한 장비 또는 서비스 범위에서 시작한다.
	- 메모리·위키·실행 기록은 파일이나 기존 도구 기능으로 관리할 수 있다.
	- 무료·최소비용을 우선 고려한다. 보유 장비·가상 PC의 실행기와 기존 메신저·CLI·Paseo 접점, 내장 상태 저장소·Markdown LLM Wiki를 먼저 검토하고 Google Docs 연결·추가 DB·원격 경로는 필요한 범위만 추가한다. 실제 제품 선택은 미정이다.
- **엔터프라이즈 시스템**
	- 한 업무·팀의 사용자, 데이터, 실행 권한과 운영 책임을 먼저 정한다.
	- 조직의 인증·저장소·모니터링·승인 체계를 활용하고, 여러 사용자의 요청과 데이터 경계를 지킨다.
- **필요에 따라 추가할 기능**
	- 정기·사건 기반 실행, 여러 서비스 연결, 고급 검색, 자동 기억 정리, 멀티에이전트, 통합 관리 화면.
	- 선택한 업무의 성공에 필요한 기능은 첫 구축 범위로 올린다. 미사용 기능은 이유와 도입 조건을 기록한다.

## 3. 구축·운영 공통 요구사항 — 3단계 목록

각 항목의 공통 요구사항에 해당 적용 형태를 더한다. F01–F12는 누락 점검 번호이며, 별도 제품이나 서버의 개수를 뜻하지 않는다.

### 기반과 연결

- **F01. 업무 정의와 완료 기준**
	- 공통
		- 대상 사용자, 해결할 업무, 시작 조건, 입력 예시, 결과물 예시·위치, 완료 기준, 제외할 업무를 정의한다.
		- 사용자의 실제 업무 사례와 원하는/원하지 않는 결과를 질문으로 확인한다. 답변을 실행 가능한 규칙·검증 사례로 바꾸고, 이미 확정한 내용과 아직 필요한 결정을 구분한다. 구축 시작 시 7절의 규칙 정의 프롬프트를 사용한다.
		- 필요한 시나리오를 모두 확인하고 설계 패턴 채택과 제품 도입을 별도 결정한다. 목표·프로젝트·할 일·시간 배치를 선택하면 원본 ID·담당·기간·완료 기준으로 연결한다. 첫 구축 순서가 후속 선택 범위를 축소하지 않게 한다.
		- 핵심 질문 하나→답변 해석→필요한 가정·반례 확인→전체 구조 갱신으로 설계를 진행한다. 사용자 확정·관찰·가정을 구분하고, 구성 요소·연결·경계와 현재 단계 필수 결정이 모이면 허용된 구축으로 넘어간다.
	- 개인 시스템
		- 반복 업무 한 가지와 본인이 결과를 확인할 방법, 절약하려는 시간·노력을 정한다.
		- 라이프 관리를 원하면 목표 결과와 이번 주 행동·실제 완료·막힌 이유를 연결한다. 목표 없는 단순 할 일도 허용하고, 일정 종료·알림 확인을 실제 행동 완료로 간주하지 않는다.
	- 엔터프라이즈 시스템
		- 업무 책임자·사용자·승인자·운영자를 구분하고, 기존 업무 절차·인계 지점·품질 및 처리시간 목표를 정한다.
		- 조직 목표·프로젝트·담당 업무·검토·결과 증거를 기존 업무 시스템에 연결한다. 개인 일정과 통합할 경우 허용된 정보만 전달한다.

- **F02. 모델·실행 환경과 설치 정보**
	- 공통
		- 에이전트 실행기·모델·버전, 필요한 도구, 설치 위치, 설정 경로, 인증 방식, 입력 길이·시간·비용 한도를 기록한다.
		- 접속 화면·요청 API·장시간 실행기·작업 DB·문서 저장소의 배치와 데이터 흐름을 정한다. Jev 등 판단 모델은 선택 요소이며 [기존 모델 + 분류 전용 프롬프트](<10_구축/분류 전용 프롬프트와 검증.md>)를 먼저 비교한다. 허용 후보·JSON·근거·검토 규칙과 도구 권한 차단을 정의하며 생성 모델·DB·위키와 역할을 구분한다.
	- 개인 시스템
		- PC·서버·관리형 서비스 중 실행 위치, 켜져 있어야 하는 시간, 절전·재부팅 시 동작, 시작·종료 방법을 정한다.
		- 집 PC/Mac mini·외부 가상 PC·중앙 PC 중 담당 실행 서버와 노트북·태블릿/휴대폰의 접점 역할을 정한다. 담당 서버 가동/중지 시 기능을 구분하고, 꺼졌을 때 실행 불가·접수 미확인·기존 결과 조회·문서 직접 편집을 표시한다. 상시 가용성이 실제 필요한 경우에만 확장한다.
	- 엔터프라이즈 시스템
		- 승인된 모델·배포 환경·네트워크 접근, 개발·검증·운영 환경 구분, 동시 사용량·자원 한도·변경 및 배포 책임을 정한다.
		- 내부 실행 영역과 외부 접속·클라우드 처리 영역을 구분한다. 단일 서버 DB와 다중 작업자·고가용성 DB의 선택은 동시 쓰기·복구 목표·운영 책임으로 판단한다.

- **F03. 요청 창구와 외부 서비스 연결**
	- 공통
		- 사용자와 요청을 식별하고, 연결마다 조회·작성·변경 범위, 계정·자료 위치, 연결 방식, 응답·첨부 처리, 실제 연결 시험 결과를 기록한다.
		- Google Sheets·Docs·Drive 등은 파일 ID·고정 레코드 ID·버전·변경 커서·공유 권한을 연결 계약에 포함한다. 기존 도구의 연결을 재사용할 수 있는지 확인하고, 구축 도구의 인증과 운영 실행기의 인증을 구분한다.
		- 일정과 할 일은 화면 접점·데이터 원본·API 지원을 구분한다. Google Calendar의 할 일은 Tasks 데이터와 연결되며 일정 커넥터가 할 일까지 지원한다고 가정하지 않는다. Google Calendar·Gmail 등의 연결은 [Google 계정 연결·대리 설정](<10_구축/Google 계정 연결·대리 설정.md>)으로 기존 연결 선택·대리 설정·사용자 로그인/동의·관리자 조치·실제 운영 호스트 검증을 진행한다. 연결 허용과 메일 발신·일정 초대/통지 허용은 구분하고, 인증 성공 뒤 허용 기능의 결과 ID 재조회·실패 재개까지 확인한다. 대화 수집을 선택하면 녹음·회의·채팅 입력 방식과 전체 원본/전사/요약의 범위를 정한다.
	- 개인 시스템
		- 채팅·터미널·메신저 중 한 접점과 허용된 계정·대화방·폴더를 정한다. 메신저의 요청 창구 역할과 대화 수집 역할을 구분한다.
	- 엔터프라이즈 시스템
		- 조직 사용자 인증, 역할별 접근, 서비스 계정 또는 사용자 권한 위임, 부서별 데이터 접근, 계정 변경·퇴사 시 권한 회수를 연결한다.

- **F04. 메모리·위키·절차·작업 상태**
	- 공통
		- 기억, 원문·지식, 반복 절차, 임시 작업 상태를 구분한다. 저장 위치·소유자·출처·갱신일·보관 기준과 검색·수정·삭제 방법을 정한다.
		- Sheets의 표·관계·상태와 Drive의 문서·파일을 연결한 전체 DB, SQLite+파일, LLM Wiki와 검색 색인의 역할 및 데이터별 정본을 정한다. SQLite 추가는 필수가 아니며 [전체 DB 비교·셋업](<10_구축/Google 도구 기반 최소 구성.md>)으로 기존 구조·동시 수정·권한·복구·비용을 판단한다. Docs와 위키의 원본·사본·파생 요약, 동기화 방향·버전 충돌·삭제 전파를 명시한다.
		- LLM Wiki를 선택하면 사용자 지정 자료를 정리한 [구성 참고](<90_참고자료/LLM Wiki 구성 참고.md>)로 원자료·편집 지식·규칙, 기존 볼트와의 경계, 수집·질의·구조 점검·근거 검증·감사의 역할을 정한다. 인간의 읽음과 근거 검증을 구분하며 외부 템플릿의 수량·명령·기존 자료 변경을 자동 적용하지 않는다.
		- 기억의 기록 시각과 사실의 유효 기간, 직접 확인한 사실과 추정을 구분한다. 자동 변경은 후보→출처·충돌·권한·회귀 검증→허용 범위 적용 또는 담당 검토→버전 추적·복귀로 진행한다. 원문 관찰 기록을 곧 유효 기억이나 지시로 승격하지 않는다.
		- 대화 전체 보관·전사를 선택하면 원본→타임코드/화자 전사→교정→요약·결정·할 일 후보→검증·반영을 추적한다. 원본·전사·파생물별 보존·접근·정정·삭제 전파와 비용을 정하고, 수집·전사·후속 업무 완료를 분리한다.
	- 개인 시스템
		- 대화의 선호·피드백과 문서 원문·정리 노트를 연결하고, 기억 조회·교정·고정·잊기를 제공한다. 일회성 진행 상태는 따로 관리한다.
		- 여러 기기에서 같은 담당 실행기의 세션·작업 상태를 지원 접점으로 조회한다. 실행 중 SQLite 파일을 클라우드 파일 동기화로 공동 사용하지 않고 일관된 백업 사본만 옮긴다.
	- 엔터프라이즈 시스템
		- 개인·팀·조직 기억의 읽기·쓰기·공유 범위를 정하고, 원문 권한을 검색 결과·맥락 전달·산출물에도 적용한다. 공유 지식의 책임자와 갱신·삭제 전파 범위를 정한다.

### 실행과 통제

- **F05. 에이전트 역할과 작업 절차**
	- 공통
		- 목표, 사용할 도구, 작업 순서, 결과물 형식, 예외 처리를 지침·스킬로 기록한다. 운영 규칙의 우선순위를 정하고 외부 문서의 지시문은 입력 자료로 취급한다.
		- 스킬의 배포 범위, 자동·명시 호출 조건, 동명 스킬 선택, 지침 충돌 처리, 강제 정책을 각각 정의한다. 실제 적용된 지침·스킬의 출처와 버전을 확인할 방법을 둔다.
		- 마스터 지침에는 공통 원칙과 작업 분기만 짧게 남긴다. 작업 절차·예시·예외는 해당 스킬과 참조 자료로 분리하고 필요한 조건에만 읽는다. 축적된 규칙은 주기적으로 통합·축소·폐기한다.
		- 여러 에이전트의 협업이 필요한 경우에만 통신 계층을 추가한다. 참여 세션·요청할 업무·수신 정책·최종 담당을 정하고, 메시지 전달을 작업 완료나 기억·권한의 자동 통합으로 해석하지 않는다. 무료 연결도 상대 에이전트의 모델 호출 비용을 만들 수 있다.
	- 개인 시스템
		- 사용자의 역할·선호·현재 프로젝트 맥락을 짧게 유지하고, 반복되는 작업은 재사용 절차로 만든다.
		- 모든 프로젝트에 쓰는 개인 절차와 특정 프로젝트 절차를 구분하고, 중복 이름·오작동 시 원하는 스킬을 명시적으로 선택하거나 비활성화할 방법을 정한다.
		- 자동 스킬 개선을 선택하면 허용 변경 유형·고정 규칙·회귀 사례·성능/비용 한도·복귀를 정한다. 생성한 에이전트의 판단만으로 새 실행 코드나 권한 확대를 적용하지 않는다.
	- 엔터프라이즈 시스템
		- 조직 공통 규칙과 업무·팀별 규칙의 적용 범위, 정책 충돌 처리, 절차 변경 담당·검토자·버전과 배포 경로를 정한다.
		- 조직·팀/프로젝트·개인별 수정 가능 범위와 예외 승인 담당을 정한다. 공용 스킬의 검토·배포·회수·버전 복귀와 구성원 변경 시 적용 여부를 확인한다.

- **F06. 실행 상태·실패·재시작 처리**
	- 공통
		- 작업 ID, 접수·실행·확인 대기·완료·실패·취소 상태와 다음 담당을 기록한다. 대기 만료, 중단·재개, 제한된 재시도, 중복 방지, 부분 완료와 복구 지점을 정한다.
		- 기기·모델·실행기가 달라져도 기존 세션/작업 ID·결정·근거·산출물·다음 행동으로 이어받는다. 중복·동시 변경·승인이 있는 업무는 기존 대조 기능을 확인하고 부족한 부분만 보완한다. 임대·heartbeat·세대 번호 등은 다중 작업자나 자동 인계를 선택할 때 적용한다.
	- 개인 시스템
		- 중단된 작업의 마지막 결과와 다음 행동을 확인하고, 앱 종료·네트워크 단절 뒤 다시 실행해도 같은 저장·발송이 반복되지 않게 한다.
		- 모바일 미전송 초안과 허브 접수 완료를 구분한다. 앱 종료 후 서버 작업 지속, 재접속 후 최신 상태 조회, 두 기기의 동시 답변 충돌을 시험한다.
		- 메신저·Paseo·CLI 등의 기존 접점·세션 저장·공식 handoff/resume을 먼저 사용한다. 별도 웹앱·자체 작업 API·새 세션 DB는 필수가 아니다. 같은 접점에서의 기기 전환과 다른 채널·에이전트로의 인계를 구분하고, 필요한 기능만 보완한다.
	- 엔터프라이즈 시스템
		- 동시 요청의 대기·우선순위·자원 한도, 작업 담당과 소유권, 장애 후 재처리 범위를 정한다. 외부 변경 결과가 불명확하면 먼저 상태를 조회한 뒤 재시도한다. 부분 변경의 되돌림·보상 처리 또는 사람에게 인계할 경로를 정한다.

- **F07. 능동·수동 운영, 자동 실행과 사람의 개입**
	- 공통
		- 능동(Active)/반응형(Passive)은 누가 시작·점검하는지, 수동(Manual)/자동(Automatic)은 누가 실행하는지를 구분한다. 능동 운영은 예약·이벤트·상태 변화로 먼저 관찰→다음 행동 제안→허용 실행→결과 재조회→미완료 수정/재점검을 수행한다. 사용자 판단이 필요한 단계도 먼저 근거와 안을 준비한다.
		- 실행기 종류와 별도로 시작 조건·지속 작업 상태·실행 어댑터·결과 전달을 구현한다. 내장 기능이 부족하면 외부 예약/감지와 연결하고, 대화를 닫아도 새 입력 없이 시작하는 시험을 한다.
		- 선별·저장·검색·실행·전달 단계별 수동/자동 여부를 정한다. 자동 실행을 쓰면 시각·시간대·조건·중복 방지·중지 방법을 명시한다.
		- 정기 요약·변화 알림을 선택하면 조용한 시간·긴급 조건·묶음·변화 없음 생략·재알림 상한·서버 재기동 후 만료 처리를 정한다. 명시적으로 선택한 직접 요청형은 해당 범위로 기록하되 능동 운영 검증을 통과한 것으로 표시하지 않는다. 알림 실패로 완료된 업무를 재실행하지 않는다.
	- 개인 시스템
		- 아침에는 우선순위·이유·첫 행동, 낮에는 변화·막힘과 허용된 수정, 저녁에는 실제 완료·남은 이유·다음 계획을 먼저 준비한다. 부족한 판단만 묻고 직접 요청·중단·방향 수정·재개도 지원한다. 시각·시간대·집중 시간·수신 위치는 사용자 규칙으로 정한다.
	- 엔터프라이즈 시스템
		- 업무 시간·서비스 운영 시간, 사건 발신자 확인, 자동 실행 변경 권한, 담당자 부재·승인 지연·실행 누락 시 대체 처리와 통보 경로를 정한다.

- **F08. 실행 권한·승인·자격증명 관리**
	- 공통
		- 허용 작업, 확인이 필요한 작업, 금지 작업을 구분하고 도구 권한으로 제한한다. 비밀번호·토큰은 별도 보관해 프롬프트·로그 노출을 막고, 문서에는 참조 위치·관리자·갱신 방법만 남긴다.
		- 접속 인증·자료/행동 인가·실행기 권한·데이터 반출을 별도 경계로 둔다. Tunnel은 접속 경로이며 사용자 인증을 대체하지 않는다. 모델의 분류·신뢰도도 실행 권한을 부여하지 않는다.
	- 개인 시스템
		- 읽기·쓰기 가능한 폴더·계정, 발송·삭제·중요 정보 변경의 확인 조건, 연결 해제와 전체 실행 중단 방법을 정한다.
		- 노트북·모바일 분실 시 세션·기기·연결 권한 회수와 캐시 처리 방법을 정한다. 브라우저에 DB·모델·클라우드 관리자 키를 배포하지 않는다.
	- 엔터프라이즈 시스템
		- 요청자·실행 주체·승인자를 추적하고, 승인한 대상·내용이 바뀌면 다시 판단한다. 조직별 격리, 비밀정보 관리, 데이터 외부 전송·처리 위치·보존 정책과 감사 책임을 정한다.
		- 필수 정책은 지원되는 관리자 설정·도구 및 원본 시스템 권한으로 집행한다. 스킬의 저장 위치나 문장만으로 조직 정책이 강제된다고 간주하지 않고, 개인 지침·스킬이 달라져도 금지 동작이 차단되는지 시험한다.
		- 사내/사외, 관리/비관리 단말, 사용자/서비스 계정, 자료 등급/행동별 정책표를 만든다. 내부망만으로 신뢰하지 않고 역할·단말·상황·자료 권한을 확인한다. Google Docs·Cloudflare·외부 모델로 원문·메타데이터가 이동하는 범위를 정한다.

### 검증과 지속 운영

- **F09. 결과 검증·전달·저장**
	- 공통
		- 미완료·품질 불합격이면 허용 범위의 원인을 수정하고 결과를 다시 검증한다. 횟수·시간·비용 상한이나 외부 판단 대기에 이르면 이유·다음 담당·다음 점검 조건을 저장한다. 무한 반복·알림 폭주·무응답 완료 처리는 하지 않는다.
		- 내용·출처·형식·대상·저장 위치를 확인한다. 생성·저장·전달 상태를 구분하고, 실제 파일 재열람이나 서비스 조회 등 완료 증거를 남긴다.
		- 에이전트 실행 성공·알림 전달·시스템 상태 반영·사용자의 실제 업무 완료를 구분한다. 완료는 명시적 사용자 확인 또는 합의한 결과 증거로 판정하고 조회 실패·시간 경과·읽음·무응답을 완료로 바꾸지 않는다.
	- 개인 시스템
		- 결과를 열어 확인하고, 받은 위치·추가할 일·미완료 사항을 짧게 보고한다. 피드백을 다음 작업에 반영한다.
	- 엔터프라이즈 시스템
		- 업무별 품질 기준, 검토 담당, 기록 반영·전달 확인, 추적 가능한 결과 ID를 정한다. 부분 성공과 실패 항목을 분리 보고한다.

- **F10. 상태 관측·알림·비용 제어**
	- 공통
		- 사용한 도구·자료, 단계별 결과·오류·실행 시간·비용을 작업 ID로 연결한다. 실행 시간·반복 횟수·비용 한도와 초과 시 동작을 정한다.
		- 지침 변경 시 상시·작업별 입력량, 참조 읽기와 모델 호출 수, 첫 유의미한 응답·전체 완료 시간, 성공률을 비교한다. 제공되는 경우 캐시 사용량도 구분하고, 입력 감소만으로 속도 개선을 단정하지 않는다.
		- 무료·최소비용을 설계 기준으로 적용하되 모델·서버/전기·DB·저장·요청·접속·로그·백업·운영 비용을 함께 계산한다. 무료 한도·유효 조건·초과 시 차단/과금·유료 전환 허용 여부와 확인일을 기록한다.
	- 개인 시스템
		- 실행 중·다음 예약·실패·사용량을 확인하고, 필요한 성공·실패 알림을 받는다. 로그에 남기지 않을 정보와 보관 기간을 정한다.
	- 엔터프라이즈 시스템
		- 업무·팀별 사용량과 비용, 응답 시간·실패율·적체를 관측하고 알림 담당·대응 시간을 정한다. 운영 로그와 감사 기록의 접근 권한·보존·변경 방지를 관리한다.
		- 요청자·기기·접속 경로·실행 계정·정책 버전·허용/거부·승인·외부 전달 대상을 작업 ID로 추적한다. 비밀값·불필요한 문서 본문을 남기지 않으며 무료 요금제의 로그 보존이 조직 기준을 충족하는지 확인한다.

- **F11. 백업·복구·업데이트**
	- 공통
		- 기억·문서·규칙·설정·필요한 작업 상태의 백업 범위·주기·복원 방법을 정한다. 도구·모델·지침 변경 전후 시험과 이전 버전 복귀 방법을 기록한다.
		- DB와 파일·Docs 산출물의 일관된 복구 지점, DB 스키마·적용 버전, 외부 처리 결과 재조회 방법을 남긴다. 파일 동기화·서비스의 버전 기록만으로 백업과 복구 시험을 대신하지 않는다.
	- 개인 시스템
		- 복구할 사본 위치와 실제 복원 순서, 재인증 방법을 남기고 표본 복원을 확인한다. 동기화 충돌·잘못된 덮어쓰기에서 되돌릴 방법을 정한다.
	- 엔터프라이즈 시스템
		- 허용 가능한 데이터 손실 시간·복구 시간, 백업 접근·보호·보존, 복구 책임·훈련, 배포 승인·점진 적용·롤백 기준을 정한다.

- **F12. 운영 책임·평가·개선**
	- 공통
		- 대화형 운영 점검에서 합의된 구조·규칙, 실제 설정/실행/원본 결과, 사용자 체감을 비교한다. 기간·표본·증거·한계를 남기고 유지/보완/설계 재결정/미확인을 구분한다. 변경된 부분만 다시 질문·검증하며 점검을 무조건 재설치로 바꾸지 않는다.
		- 시작·상태 확인·중단·재시작·재인증·실패 재처리·백업·복구 절차를 실제 명령 또는 화면 경로로 기록한다. 변경 후 대표 업무를 다시 확인한다.
		- 규칙 추가의 원인과 적용 범위를 기록하고, 중복·오래된 예외·실제 호출되지 않는 절차를 정리한다. 축소 전후 대표 업무와 필수 제약을 확인하고 이전 버전으로 복귀할 수 있게 한다.
	- 개인 시스템
		- 본인이 유지할 수 있는 점검 주기로 실패·수정량·시간 절감·비용을 확인하고 기억·규칙·스킬을 개선한다.
	- 엔터프라이즈 시스템
		- 업무 소유자·기술 운영자·보안/데이터 담당의 책임, 장애 대응·사용자 지원·인수인계·정기 검토·서비스 종료 및 자료 이관 절차를 정한다.

능동 운영의 실제 설정·P01–P06 시험은 [능동 운영과 완료 추적](<10_구축/능동 운영과 완료 추적.md>), 도구별 적용은 [실행기 독립 운영 검증](<20_도구별/실행기 독립 운영 검증.md>)을 따른다.

## 5. 메모리와 에이전트의 관리 원칙

### 관리의 두 축

토푸경 강의의 구분을 적용한다. **Active/Passive는 사람이 기준을 정하고 조정하는 정도**, **Manual/Automatic은 건별 지시와 조건에 따른 처리의 구분**이다. 두 축은 독립적이며, 에이전트가 먼저 알림을 보내는 동작은 실행 조건으로 따로 정의한다.

| 조합 | 적용 예시 |
| --- | --- |
| Active + Manual | 내 기준으로 자료를 선택·수정하거나 작업마다 실행 지시 |
| Active + Automatic | 내가 정한 저장·검색·실행 규칙에 따라 자동 처리 |
| Passive + Manual | 도구의 기본 기준을 사용하며 건별 실행 요청 |
| Passive + Automatic | 도구의 기본 기준에 따라 자동 축적·실행 |

- **개인 시스템**: 사용자가 선호·저장·실행 기준을 조정한다. 대화 기억은 기준에 맞게 자동 축적하고, 문서는 목적을 정해 선별하는 방식부터 검토한다.
- **엔터프라이즈 시스템**: 조직·업무 정책 안에서 조정 가능한 사용자·팀 설정을 구분한다. 공유 기억·규칙의 변경 권한과 검토 책임을 명시한다.
- **공통 적용**: 선별·저장·정리·불러오기·외부 반영의 자동화 정도를 각각 정한다. 수동으로 요청한 작업 안에서도 허용된 검색·정리는 자동 수행할 수 있다.

### 정보의 역할과 보존

| 정보 | 역할 | 관리 기준 |
| --- | --- | --- |
| 대화 메모리 | 선호·결정·반복 피드백 등 지속 맥락 | 출처·소유 범위·갱신일, 조회·교정·고정·잊기, 기억 후보 검토 |
| 문서 위키 | 원문·출처·정리 지식·문서 사이의 연결 | 자료 선별, 원문 보존 여부 확인, 요약·해석 수정, 접근 권한 |
| 지침·스킬 | 역할·작업 순서·검증·예외 처리 | 적용 조건, 변경 책임, 버전과 변경 후 시험 |
| 작업 상태 | 진행 단계·결과 위치·다음 행동·실패 | 작업 ID, 재개·취소·중복 방지, 임시 상태의 보관 기간 |

대화 메모리와 문서 위키는 보완 관계다. 파일·URL이 대화에 등장하면 실제 원문 보존 여부와 참조 위치를 확인한다. 기억·문서가 상충하면 출처와 시점을 표시하고, 기준이 없는 충돌은 검토 대상으로 둔다. 장기 기억으로 승격할 정보와 임시 상태를 구분한다.

- **개인 시스템**: 같은 폴더나 기존 도구 안에서도 정보의 역할을 구분할 수 있다. 원문·설정·기억의 수정 및 복구 경로를 확인한다.
- **엔터프라이즈 시스템**: 모든 정보에 소유자·접근 범위·보존 기준을 연결하고, 권한 변경·삭제 시 색인·캐시·파생 기억·백업에 적용할 정책을 정한다. 개인 기억이 조직 공유로 바뀌는 조건을 명시한다.

### 마스터 지침의 경량화와 작업별 조건부 참조

**운영 원칙: 지식과 규칙은 축적하되, 매번 모델이 읽는 지침은 짧게 유지한다.** 핵심 요구사항은 이 문서에 유지하고 작업 절차·결정·검증은 폴더 내 안내·양식으로 연결한다. 실제 운영 시 문서 전체를 마스터 프롬프트에 넣는 방식과는 구분한다.

- **역할과 로딩 범위**
	- 마스터 지침
		- 목적, 공통 원칙, 권한·확인 경계, 충돌 처리, 작업별 참조 조건을 담는다. 모든 작업에 필요한 제약과 조건부 자료를 읽어야 할 판단 기준은 남긴다.
	- 작업별 스킬
		- 적용 조건·제외 조건, 필수 입력, 핵심 절차, 완료 확인을 담는다. 세부 예외·긴 예시·양식은 참조 자료로 옮기고 읽을 조건을 함께 적는다.
	- 참조 분기
		- 작업 → 해당 스킬 → 필요한 세부 자료로 짧게 연결한다. 전체 규칙 탐색을 기본으로 삼지 않고 순환 참조·중복 복사·불필요한 재열람을 줄인다. 작업이 여러 분야에 걸치면 관련 스킬을 함께 적용한다.

- **두꺼워진 규칙을 다시 얇게 만드는 과정**
	- 공통
		- 문제·피드백 기록 → 해당 작업 규칙으로 반영 → 반복되는 내용 통합 → 공통 원칙만 마스터에 유지 → 오래된 예외 정리 → 변경 후 검증 순서로 관리한다. 무조건 줄이는 대신 필수 제약과 실제로 도움이 된 예외를 보존한다.
	- 개인 시스템
		- 반복해서 수정하는 작업을 중심으로 규칙을 다듬는다. 마스터 분량·초기 입력량·참조 단계의 검토 기준을 정하고, 초과하거나 무관한 스킬이 자주 호출되면 분리·설명 수정을 검토한다.
	- 엔터프라이즈 시스템
		- 조직 공통 원칙과 팀별 절차의 소유자를 정한다. 삭제·통합 근거, 검토자, 버전·배포 기록을 남기고 대표 업무·권한 경계가 유지되는지 확인한 후 적용한다.

- **부하·응답 속도와 검증**
	- 공통
		- 조건부 로딩은 무관한 입력과 컨텍스트 점유를 줄일 수 있다. 반면 파일 읽기·분기 판단·추가 모델 호출은 시간이 든다. 전체 시간에는 입력 처리 외에 추론·출력 생성·도구 및 네트워크 대기도 포함되므로 ‘더 짧은 지침 = 항상 더 빠른 응답’으로 해석하지 않는다. [지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization)
		- 파일을 나눠도 모두 불러오면 입력량은 줄지 않는다. 캐시 재사용은 입력 처리 비용·시간을 줄일 수 있지만 컨텍스트에서 규칙을 제거하지 않으며, 긴 고정 지침과 짧은 조건부 지침의 실제 속도는 캐시 상태에도 좌우된다. 캐시 적중과 성능 향상은 보장되지 않는다. [프롬프트 캐싱](https://developers.openai.com/api/docs/guides/prompt-caching)
	- 개인 시스템
		- 같은 모델·설정·대표 요청으로 기존/분리 구조를 비교한다. 스킬 불필요 작업, 한 스킬 작업, 여러 스킬 작업에서 첫 유의미한 응답·완료 시간·읽은 자료·정확성을 확인한다. 작은 로컬 파일의 읽기 비용과 원격 조회·모델 호출 대기를 따로 관측한다.
	- 엔터프라이즈 시스템
		- 업무별 충분한 표본으로 중앙값·느린 요청의 지연·성공률·규칙 누락·잘못된 분기를 비교한다. 신규 세션과 반복 요청, 캐시 적중 여부, 동시 요청량을 구분한다. 품질·필수 정책 유지와 시간·비용 목표를 함께 통과해야 한다.

상시 지침과 작업별 지침의 토큰 예산, 분리·정리 시점, 허용 참조 단계, 점검 담당·주기는 D09에서 정한다. 특정 줄 수를 보편적 성능 기준으로 삼지 않는다. 현재는 설계 원칙이며 분리 전후 성능을 측정한 결과는 없다.

### 실행 도구별 적용 지침

다음은 구축 시 사용할 적용안이다. 파일 경로는 주로 로컬 Claude Code·Codex CLI의 기본 위치를 기준으로 하며, Hermes는 여러 적용 예시 중 하나이며 OpenClaw·OmO 등은 아래 도구별 안내로 연결한다. 기존에 사용 중이거나 필요에 맞는 에이전트를 선택하고 목록 밖의 제품도 공통 운영 계약으로 검증한다. 또한, 웹·클라우드·관리형 앱에서는 지원 범위와 배포 경로를 별도로 확인한다. 실제 선택한 제품·버전·운영체제·경로·권한은 D03·D04·D09에 기록한다. 현재 이 절차에 따라 설정 파일을 생성하거나 정책을 적용한 상태는 아니다.

- **Claude를 사용할 경우 — Claude Code 기준**
	- 공통
		- 지속 지침은 `CLAUDE.md`, 업무별 반복 절차는 `SKILL.md`로 정리한다. 여러 `CLAUDE.md`의 내용을 함께 읽는 동작과 동명 스킬 선택 순위를 구분한다. 적용된 지침은 `/memory` 또는 `/context`에서 확인한다. [지침 문서](https://code.claude.com/docs/en/memory)
		- 같은 이름의 스킬은 기업 관리 → 개인 → 프로젝트 순으로 선택된다. 플러그인 스킬은 `/플러그인명:스킬명`으로 구분된다. 팀 절차가 개인 스킬에 가려지지 않도록 이름과 호출 방법을 명시한다. [스킬 문서](https://code.claude.com/docs/en/skills#resolve-skills-that-share-a-name)
		- `CLAUDE.md`의 `@path` 가져오기는 파일을 나누어도 함께 로드된다. 작업별 절차는 스킬로, 특정 파일에만 필요한 규칙은 `paths` 조건으로 분기한다. 조건 없는 `.claude/rules`는 시작 시 로드된다. [조건부 규칙과 가져오기](https://code.claude.com/docs/en/memory)
		- 스킬 본문도 핵심과 참조 안내 위주로 유지한다. 호출한 본문은 이후 턴에도 남으므로 사용이 끝났다고 즉시 사라진다고 가정하지 않는다. [참조 파일과 스킬 수명](https://code.claude.com/docs/en/skills#skill-content-lifecycle)
	- 개인 시스템
		- 전역 선호는 `~/.claude/CLAUDE.md`, 프로젝트 지침은 프로젝트의 `CLAUDE.md`에 둔다. 현재 프로젝트에만 쓰는 개인 지침은 `CLAUDE.local.md`로 구분하고 공유 저장소에서 제외한다.
		- 개인 공통 스킬은 `~/.claude/skills`, 프로젝트 스킬은 `.claude/skills`에 둔다. 개인 설정과 프로젝트 설정은 각각 `~/.claude/settings.json`, `.claude/settings.json`에서 관리한다. [설정 범위](https://code.claude.com/docs/en/settings#settings-files-and-who-they-affect)
	- 엔터프라이즈 시스템
		- 조직 지침은 관리형 `CLAUDE.md`, 팀 지침·절차는 프로젝트의 `CLAUDE.md`·`.claude/skills`로 배포한다. 조직 공용 스킬과 팀별 스킬의 담당·버전·배포 대상을 정한다. 계정 기반 조직 배포를 쓰면 Enterprise의 플러그인 그룹 할당 가능 여부도 확인한다. [조직 스킬 관리](https://support.claude.com/en/articles/13119606-provision-and-manage-skills-for-your-organization)
		- 필수 실행 제한은 `managed-settings.json` 등 관리형 설정과 연결 서비스 권한으로 집행한다. 조직 지침이나 스킬 제공만으로 실행 제한이 강제된다고 가정하지 않는다. 관리형 설정의 지원 항목·예외와 로컬/클라우드 적용 차이를 확인한다. [설정 우선순위](https://code.claude.com/docs/en/settings#settings-precedence)

- **Codex를 사용할 경우 — 로컬 CLI 기준**
	- 공통
		- 지속 지침은 `AGENTS.md`, 업무별 반복 절차는 `SKILL.md`로 정리한다. 전역 → 저장소 루트 → 현재 작업 폴더 순서로 지침을 합치며, 더 가까운 폴더의 지침이 앞선 지침보다 우선한다. 따라서 조직의 필수 실행 제한을 상위 `AGENTS.md`에만 맡기지 않는다. [지침 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
		- 동명 스킬은 병합되지 않고 선택 목록에 둘 다 나타날 수 있다. 조직·팀·개인 스킬의 이름을 구분하고, 적용 조건과 함께 사용할 공통 절차를 명시한다. CLI의 `/skills`와 `$` 선택으로 사용 가능한 스킬을 확인한다. [스킬 문서](https://learn.chatgpt.com/docs/build-skills)
		- `AGENTS.md`에 모든 자료를 먼저 읽으라고 쓰지 않고, 작업 조건과 해당 스킬·자료를 연결한다. Codex는 먼저 스킬 이름·설명·경로를 보고 선택 시 본문을 읽으므로 설명도 짧고 구체적으로 유지한다. 스킬이 많아지면 초기 목록의 설명 축약·누락 여부를 확인한다. [점진적 로딩](https://learn.chatgpt.com/docs/build-skills)
	- 개인 시스템
		- 기본 전역 지침은 `~/.codex/AGENTS.md`, 프로젝트 지침은 루트와 필요한 하위 폴더의 `AGENTS.md`에 둔다. 같은 위치의 `AGENTS.override.md`는 기본 파일보다 먼저 선택되므로 사용 여부를 함께 기록한다.
		- 개인 스킬은 `~/.agents/skills`, 프로젝트 스킬은 `.agents/skills`에 둔다. 필요할 때 `~/.codex/config.toml`의 `skills.config`로 특정 스킬을 비활성화하고 새 실행에서 적용 여부를 확인한다.
	- 엔터프라이즈 시스템
		- 관리자 공용 스킬은 `/etc/codex/skills` 등 지원 위치에 배포하고, 팀·업무 절차는 저장소의 `AGENTS.md`·`.agents/skills`로 관리한다. 여러 저장소에 배포할 때는 플러그인도 선택지로 둔다. 저장 위치만으로 ‘조직 > 팀 > 개인’이라는 강제 우선순위가 생기는 것은 아니다.
		- 지원되는 조직 제한은 `requirements.toml` 등의 관리자 요구사항과 연결 서비스 권한으로 집행한다. 승인·실행 권한·MCP·플러그인 출처 제한과 사용자가 바꿀 수 있는 기본값을 구분한다. [관리형 설정](https://learn.chatgpt.com/docs/enterprise/managed-configuration)
		- 워크스페이스 공유, 로컬 파일 배포, 플러그인 설치를 각각 검증한다. 대상 사용자의 로딩 결과, 실제 적용 버전, 권한 차단, 회수·롤백을 확인한다. [배포·권한 경계](https://learn.chatgpt.com/docs/enterprise/skills)

- **Hermes를 선택한 경우의 적용 예시**
	- 공통
		- 패키지 루트를 작업 디렉터리로 열고 `AGENTS.md`·`README.md`를 명시적으로 읽게 한다. 자동 발견이나 외부 스킬 설치가 없어도 폴더 내 문서로 구축을 진행한다. [Hermes 적용 안내](20_도구별/Hermes.md)
	- 개인 시스템
		- 구축을 수행하는 Hermes와 실제 운영할 실행기를 구분하고 모델·프로필·연결·메모리·예약 실행의 필요한 범위를 정한다. 설치·인증·스킬 신뢰 상태를 확인 전에는 완료로 기록하지 않는다.
	- 엔터프라이즈 시스템
		- 실행 계정·자료·도구 권한과 조직 정책 집행 수단을 별도로 정한다. 프로필 분리만으로 조직 격리를 보장한다고 가정하지 않고 실제 접근 차단·감사·복구를 시험한다.

- **OpenClaw·OmO 등 다른 에이전트를 사용할 경우**
	- 공통
		- [OpenClaw](20_도구별/OpenClaw.md)·[OmO](20_도구별/OmO.md) 중 선택한 안내를 읽는다. 목록 밖 제품도 [실행기 독립 운영 검증](<20_도구별/실행기 독립 운영 검증.md>)의 역할을 실제 지원 기능과 대조하고 필요한 설정·대안·제약을 기록한다.
	- 개인 시스템
		- 기존 장비·에이전트·구독을 우선하며 예시 때문에 Hermes를 추가 설치하지 않는다. 실제 기동·저장·재개·알림 경로를 선택한다.
	- 엔터프라이즈 시스템
		- 조직에서 허용한 실행기·계정·자료 경계를 적용하고 지침 로드·접근 차단·감사·회수를 검증한다.

	- 집 PC·외부 가상 PC·중앙 PC 중 담당 실행 서버를 정하고 메신저·Paseo·CLI만으로 요구사항을 충족하는지 먼저 확인한다. 서버 중지 시 기존 결과·독립 문서 편집·초안 작성만 가능할 수 있으며 자동 인계·상시 가용성은 필요할 때 추가한다.
- **엔터프라이즈 시스템**
	- 기존 조직 인프라와 인증·감사 체계를 재사용한다. 무료 서비스라도 사내 자료·메타데이터의 외부 처리와 보존 요구를 충족하는 범위에서 선택한다.

## 7. 구축 에이전트에 넘길 작업과 인수인계

폴더와 README만 전달받은 첫 시작·재개는 [초기 셋업 흐름](<10_구축/초기 셋업 흐름.md>)을 따른다. 환경 확인을 먼저 하고 현재 단계에 필요한 결정만 확정한다. [셋업 진행 기록](<30_양식/셋업 진행 기록.md>)에 실제 대상·설치 명세·현재 단계·대기 행동·재개 지점을 남긴다. 아래 질문 프롬프트는 그 흐름 안에서 필요한 규칙을 구체화할 때 사용한다.

필요 여부 확인과 대표 시나리오는 [업무 시나리오·셋업 질문](<10_구축/업무 시나리오·셋업 질문.md>)을 따른다. 지식관리·라이프 관리·기업 업무를 하나/여러 개/전체로 선택하고, 대화 전체 보관·전사는 공통 선택 모듈로 연결한다. 필요한 설계→현재 도구로 충족 여부→부족한 제품/연결 순으로 결정한다.

실제 문답과 질문 종료·구축 착수, 운영 중 재점검은 [대화형 설계·운영 점검](<10_구축/대화형 설계·운영 점검.md>)을 따른다. 운영 점검은 아래 신규 구축 질문을 모두 반복하지 않고 기존 결정·증거의 차이가 있는 부분만 확인한다. 전체 구조와 버전은 결정 기록, 증거·점검 결과는 검증 기록, 다음 질문·재개 위치는 진행 기록에 둔다.

### 사용자와 세부 규칙을 만드는 프롬프트

구축 시작 또는 미정 규칙을 보완할 때 사용하는 공통 프롬프트다. OpenClaw·Codex·Claude·OmO·Hermes 등 선택한 구축 도구의 적용 지침과 함께 사용한다. Hermes는 적용 예시이며 특정 제품을 필수로 선택하지 않는다. 질문의 목적은 사용자가 자신의 판단 기준을 구체화하도록 돕고, 그 답변을 구현·시험할 수 있는 규칙으로 바꾸는 것이다.

```text
당신은 이 문서를 바탕으로 시스템을 구축하는 에이전트다.
구현에 필요한 사용자 판단을 질문으로 이끌어내고, 답변을 명시적인 규칙으로 정리하라.
필요한 질문은 번거롭더라도 생략하지 않되, 다음 원칙을 따른다.

1. 문서와 기존 대화에서 이미 정한 내용을 먼저 확인하라.
확정된 답변을 재사용하고, 확정·제안·미정을 구분하라.
기존 자료로 확인할 수 있는 사실은 먼저 조사하라. 실제로 결정이 필요한 빈칸을 F01–F12와 D01–D09에 연결하라.

2. 필요한 전체 흐름을 고른 뒤 첫 대표 업무부터 구축하라.
지식관리·라이프 관리·기업 업무는 택 1로 제한하지 말고 복수/전체 선택을 허용하라.
필요한 전체 범위와 구축 순서를 따로 기록하고, 첫 업무 후 선택한 후속 흐름·상호 연결을 이어가라.
제품 도입 목록과 목표·일정·완료/알림·기억/스킬 검증·대화 수집 같은 설계 필요 여부를 구분하라.
업무 시나리오·셋업 질문 문서에서 공통 설정은 한 번 확인하고 필요한 기능의 세부 질문만 적용하라.
최근 실제 요청, 원하는 결과, 피하고 싶은 결과를 받아 업무 흐름을 그려라.
개인/엔터프라이즈 또는 혼합인지 확인하라. OpenClaw·Codex·Claude·OmO·Hermes 등 구축을 수행하는 도구와 완성 후 운영할 실행기를 구분해 결정하라.
기술 용어로 모든 규칙을 직접 작성하게 하지 말고, 사용자의 사례를 규칙 초안으로 바꿔 제시하라.

3. 핵심 질문 하나를 기본으로 하고 직접 관련된 경우만 최대 3개로 묶어라.
답변의 의미와 구조 변화를 짧게 설명하고, 모호한 부분에만 사례·가정·반례·대안 질문을 이어가라.
명확한 답마다 맞는지 재확인하지 말고 전체 구성 요소·연결·검증 기준을 계속 갱신하라.
각 질문에 왜 필요한지와 어떤 동작이 달라지는지 짧게 설명하라.
선택지가 도움이 되면 2–3개와 차이를 제시하고, 직접 수정하거나 보류할 수 있게 하라.
추천안을 제시할 때는 근거를 설명하고, 추천·기본 선택을 사용자 답변으로 간주하지 마라.

4. 해당 업무의 중요한 갈림길을 구체적으로 물어라.
무엇이 시작 조건인가? 어느 계정·자료·대상까지 처리하는가?
어떤 자료를 우선하고, 충돌하거나 부족하면 어떻게 하는가?
무엇까지 자동 실행하고, 어떤 경우에 사용자 확인이 필요한가?
결과의 형식·저장·전달·완료 기준은 무엇인가?
실패·중복·부분 완료 시 재시도, 중단, 인계 중 무엇을 하는가?
무엇을 기억하고, 어떤 정보는 저장하지 않으며, 언제 수정·삭제하는가?
사용할 기존 접점과 공식 세션 인계 기능은 무엇인가? 담당 서버는 집 PC·외부 가상 PC·중앙 PC 중 어디인가?
서버 가동/중지 시 작업을 구분하는 원칙은 재질문하지 말고, 요청 유효 기간·누락 예약·재개 기준을 구체화하라.
기존 Sheets·Drive DB가 있는가? Sheets·Drive 전체 DB와 로컬 SQLite+파일의 차이를 설명한 뒤 각 자료의 정본을 어디에 둘 것인가? 수정 충돌·관계 검증·삭제·권한 회수·복구는 어떻게 처리하는가?
사내/사외·관리/비관리 기기에서 허용할 자료·행동·외부 전송은 무엇인가?
이미 정한 무료·최소비용 방향에서 월/작업당 한도와 한도 소진 시 동작·유료 전환 조건은 무엇인가?
위 질문을 한꺼번에 묻지 말고 현재 업무에 필요한 미정 항목만 골라라.
라이프 관리 선택 시 목표·할 일·일정의 원본과 완료 근거, 알림 시간·빈도·중지 규칙을 구체화하라.
대화 보관·전사 선택 시 대화 수집·전사·지식화 문서로 전체 원본/전사/요약 범위·참여자·권한·보존·교정을 확인하라.
기억/스킬 자동 변경 선택 시 후보·검증·자동 적용 범위·담당 검토·복귀 규칙을 구체화하라.

5. 답변을 조건과 행동이 분명한 규칙으로 바꿔라.
“깔끔하게”, “중요한 것만”, “알아서”처럼 기준이 불분명하면 예시·반례·허용 범위를 확인하라.
정상 사례와 중요한 경계 사례를 제시해 기대 동작을 구체화하라.
명확한 답변은 그대로 기록하고, 추가 해석·범위 확대·기존 규칙과 충돌이 생긴 부분만 확인하라.
질문에 대한 답이 없다는 이유로 동의나 권한 부여가 있었다고 간주하지 마라.

6. 개인 선호와 조직 규칙을 구분하라.
개인 시스템에서는 사용자의 판단 기준과 상황별 예외를 정리하라.
엔터프라이즈에서는 답변자의 역할과 규칙을 결정할 수 있는 범위를 확인하라.
조직 필수 정책·팀 절차·개인 선호를 분리하고, 권한 밖의 답변은 제안으로 남겨 담당자에게 연결하라.
기존 권한 안의 명확한 결정을 반복 승인받지 말고, 정책 변경·권한 확대 등 확인이 필요한 부분을 특정하라.

7. 규칙마다 확정 상태와 검증 방법을 남겨라.
아래 규칙 기록 양식에 답변 근거와 관련 F/D 항목을 연결하라.
미정 항목에는 영향받는 작업, 결정 담당·시점, 그동안 가능한 작업과 임시 처리 방식을 표시하라.
사용자가 기본값 선택을 위임한 항목은 근거·변경 방법을 기록하되, 권한이나 조직 정책을 임의로 확대하지 마라.

8. 답변을 모두 마스터 지침에 붙이지 마라.
공통 원칙·분기 조건은 마스터, 작업 절차·예외는 스킬, 긴 예시·양식은 참조 자료로 분류하라.
실행 제한이 필요한 규칙은 문장뿐 아니라 도구·관리자 설정으로 집행할 방법을 연결하라.
같은 뜻의 규칙은 통합하고, 특정 사례를 모든 작업의 규칙으로 일반화하지 마라.

9. 전체 구조와 현재 단계의 구축·시험에 필요한 정보가 확보되면 인터뷰를 마쳐라.
전체 선택 범위·구성 요소·연결·권한과 구축 순서를 요약하고 현재 단계 필수값·확인/복귀 방법을 정하라.
구조·첫 구현 계획·남은 사항을 보여 주고 이미 허용된 구축을 이어가라. 형식적 최종 승인 단계를 추가하지 마라.
필수 미정 사항은 해소하거나 해당 기능을 범위에서 제외한 뒤 구현하라.
답변이 필요한 작업만 보류하고, 답변과 무관하게 가능한 조사·설계·구현은 계속하라.
운영에서 새 예외가 나타나면 기존 규칙을 확인한 뒤 필요한 질문만 다시 하라.
```

### 답변을 규칙으로 남기는 양식

아래는 앞으로 채울 양식이며 현재 확정된 사용자 규칙이 아니다. 질문 답변이 곧 실제 설정 적용·검증 완료를 뜻하지 않으므로 상태를 분리한다.

| 범위·근거 | 개인/팀/조직, 결정 담당, 사용자 답변 또는 기존 정책 근거 |

예를 들어 사용자가 “답장은 초안까지만”이라고 답했다면, 해당 이메일 업무에 대해 “초안 생성·저장까지 수행하고 발송하지 않는다”로 기록한다. 이를 모든 메신저나 다른 업무의 발송 금지로 확대하지 않는다. “중요한 메일만 알려줘”라면 중요도를 결정할 발신자·주제·기한 등의 기준을 추가 질문한다. 이 예시는 질문·규칙화 방법이며, 실제 사용자 설정으로 확정한 내용은 아니다.

- **Claude Code의 범위와 이름 충돌**: 기업 관리·개인·프로젝트 위치가 있으며, 같은 이름의 스킬은 기업 관리 → 개인 → 프로젝트 순으로 선택된다. 플러그인 스킬은 별도 이름 공간을 사용하므로 함께 로드된다. 따라서 이를 곧바로 ‘조직 > 팀 > 개인 플러그인’이라는 단일 상속 구조로 해석하지 않는다. [Claude Code 스킬 문서](https://code.claude.com/docs/en/skills#resolve-skills-that-share-a-name)
- **Claude의 조직 배포**: 조직 전체에 스킬을 제공할 수 있고, Enterprise는 플러그인으로 묶어 그룹별 제공도 할 수 있다. 조직 제공 스킬도 사용자가 끌 수 있으므로, 배포와 반드시 실행해야 하는 정책은 구분한다. 플러그인은 개인용 등급이 아니라 배포 단위다. [조직 스킬 관리](https://support.claude.com/en/articles/13119606-provision-and-manage-skills-for-your-organization)
- **Codex의 스킬 범위**: 관리자 `/etc/codex/skills`, 사용자 `~/.agents/skills`, 저장소·하위 폴더의 `.agents/skills` 등에서 로드한다. 같은 `name`의 스킬을 병합하지 않으며 선택 목록에 둘 다 나타날 수 있다. 조직 스킬이 개인 스킬을 자동으로 덮어쓴다고 가정하지 않는다. [Codex 스킬 문서](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills)
- **Codex의 지침 계층**: 전역 `AGENTS.md`와 저장소 루트부터 현재 작업 폴더까지의 지침을 합치며, 더 가까운 폴더의 지침이 앞선 지침보다 우선한다. 이는 업무 지침 조합 방식이며 조직 정책을 강제하는 수단과는 구분한다. [AGENTS.md 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- **Codex의 조직 통제**: 지원되는 실행 환경에서 `requirements.toml` 등의 관리자 요구사항으로 승인·실행 권한·MCP·플러그인 출처 등 지원 항목을 제한할 수 있다. 사용자가 바꿀 수 있는 기본 설정과 강제 요구사항을 구분하고, 로컬·클라우드·클라이언트별 지원 범위를 확인한다. [관리형 설정](https://learn.chatgpt.com/docs/enterprise/managed-configuration)
- **배포 경계**: ChatGPT 워크스페이스 스킬 공유, 로컬 파일 배포, 플러그인 설치는 별도 경로다. 파일을 배포하거나 플러그인을 설치해도 연결 서비스의 접근 권한이 함께 부여되는 것은 아니다. [스킬 관리 경계](https://learn.chatgpt.com/docs/enterprise/skills)

이 문서의 설계 제안: 조직의 필수 정책, 팀/프로젝트의 작업 절차, 개인의 선호·편의 절차를 구분한다. 공용 스킬에는 `org-…`, 팀 스킬에는 `team-…`, 개인 스킬에는 `personal-…`처럼 충돌을 피하는 이름을 고려하고, 상위 공통 절차를 언제 함께 적용할지 지침에 명시한다. 이 접두사는 제안한 명명 규칙이며 제품이 자동으로 인식하는 권한 등급이 아니다. F05·F08, D09와 검증 사례에 반영했다.
