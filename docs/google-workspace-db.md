# Sheets·Drive 전체 DB 설계와 로컬 DB 비교

**Sheets의 구조화된 표와 Drive의 파일을 연결해 시스템 전체의 논리 DB로 사용할 수 있다.** 목표·업무·기억·문서 관계·실행 상태·변경 이력을 필요한 표에 저장하고, 긴 본문과 첨부 파일을 Drive에서 관리한다. SQLite를 추가하는 것은 필수가 아니다.

이 공개 문서는 전체 구축 패키지의 저장소 선택 부분을 설명한다. 기존 자료와 사용자 답변부터 확인하고, 선택한 정본·연결 계약·실제 검증 결과를 별도로 기록한다. 전체 패키지의 비공개 문서나 실제 운영 기록은 포함하지 않는다.

공식 문서 확인일은 **2026-10-28**이다. 아래 실사 사례는 읽기 전용으로 확인한 구조이며, 이 가이드를 작성했다는 사실은 구현·자동화·복구 검증 완료를 뜻하지 않는다.

## 1. 전체 DB로 구성하는 방법

| 역할 | 저장 위치와 책임 |
| --- | --- |
| 구조화된 정본 | Sheets의 안정적인 레코드 ID, 상태, 관계, 담당자, 시각, 버전, 외부 결과 ID |
| 본문·파일 정본 | Drive의 문서·원문·음성·첨부·결과 파일; 표의 `drive_file_id` 등으로 연결 |
| 실행·재개 기록 | 필요하면 Sheets에 요청 ID, 실행 ID, 단계, 체크포인트, 실패·재시도·완료 근거 저장 |
| 실행 환경 | PC·가상 PC·승인된 클라우드 실행기가 실제 모델·도구를 호출; 저장소가 실행기를 대신하지 않음 |
| 파생 자료 | 검색 색인·미리보기·요약·로컬 캐시; 정본 ID·버전과 연결하고 재생성·삭제 규칙 적용 |

- 표를 사람이 읽고 편집하는 평문 DB처럼 사용할 수 있다. 다만 네이티브 Sheets는 로컬 CSV 파일 자체가 아니므로 외부 이전용 내보내기 형식과 복원 방법을 정한다.
- 실행기의 기존 세션 저장 기능은 재사용한다. 세션 내부 상태와 업무 정본의 역할을 구분하고 같은 업무 상태를 두 저장소에서 독립 확정하지 않는다.
- 기억·스킬도 표에서 출처·버전·검토 상태를 관리할 수 있다. 런타임이 파일을 요구하면 승인된 버전만 파일로 배포하고 해당 버전을 기록한다. 표에 등록됐다는 이유로 실행 권한이 생기지는 않는다.
- 사용자가 직접 표를 수정할 수 있는 편의성과 데이터 검증 책임을 함께 설계한다. 로컬 DB를 쓰지 않아도 중복·관계·상태 전이 검증은 필요하다.

## 2. 기존 Sheets에서 확인한 설계 패턴

실제 파일의 헤더와 극소수 표본에서 다음 구조를 확인했다. 공개 가능한 설계 설명을 위해 열 이름과 연결 방식만 추상화했다. 개인 파일명·URL·ID·대화 내용은 포함하지 않는다.

| 패턴 | 확인한 구조 | 재사용할 설계 |
| --- | --- | --- |
| 라이프 관리 | `project → todo → plan → task`, PK/FK 역할의 열, project·todo의 `google_task_id` | 목표·업무·계획·행동을 구분하고 외부 할 일 ID와 연결 |
| 기간별 아카이브 | `months(month, spreadsheet_id)` | 기간별 저장 파일과 탐색용 목록 분리 |
| 메시지 기록 | `messages(message_key, room_key, content_hash, collected_run_key, attachment_refs)` | 메시지 식별·변경 대조·수집 실행·첨부 관계 유지 |
| 첨부 저장 | `attachments(attachment_key, message_key, drive_file_id, drive_size, drive_md5, status, drive_link)` | 표 레코드와 Drive 파일을 ID로 연결하고 저장 결과 확인 |
| 실행 기록 | `runs(run_key, checkpoint, schema_version)` | 중단 후 재개 지점과 처리한 스키마 버전 기록 |
| 작업 관제 | `TaskID`, `status`, `LastChecked`, `Changes`의 이전 값·새 값 | 현재 상태와 변경 이력을 함께 추적 |

이 구조는 이미 Sheets를 업무 DB·파일 목록·실행 기록으로 활용하는 사례다. 다만 **전체 PK/FK 연결의 일관성, 누락·중복 여부, 실제 첨부 파일 저장, 자동화 작동, 백업 복구는 미검증**이다. 열의 존재만으로 기능이 작동한다고 판정하지 않는다.

새 시스템에서도 이 표를 모두 만들 필요는 없다. 첫 업무에 필요한 기존 표를 재사용하고 부족한 ID·상태·참조·복구 정보만 추가한다. `google_task_id`는 외부 연결 정보이며 Sheets와 할 일 서비스 중 어느 쪽이 상태를 확정하는지는 별도로 정한다.

## 3. 로컬 SQLite+파일과 무엇이 다른가

여기서 로컬 DB는 주로 **SQLite와 같은 호스트의 파일 저장소**를 뜻한다. PostgreSQL 같은 서버 DB와 SQLite를 같은 조건으로 비교하지 않는다.

| 기준 | Sheets + Drive 전체 DB | 로컬 SQLite + 파일 |
| --- | --- | --- |
| 접속·오프라인 | Google 접속·계정 권한이 있으면 여러 기기에서 사용. 사전 설정한 편집기의 오프라인 기능과 API 실행은 구분 | 해당 기기에서 네트워크 없이 DB 사용 가능. 외부 기기는 담당 호스트의 API·원격 접속 등이 필요 |
| 조회·성능 | API 왕복과 범위·배치 처리, 호출량을 고려 | 로컬 SQL·인덱스로 조회. 실제 속도는 데이터·인덱스·디스크·작업량으로 측정 |
| 동시 쓰기 | 사람과 에이전트의 같은 셀 수정에 대한 충돌 규칙 필요 | 여러 읽기, DB 파일당 동시 쓰기 트랜잭션 하나; 짧은 쓰기를 순차 처리 |
| 트랜잭션 | 한 요청의 일괄 갱신과 여러 파일·Drive 업로드를 구분 | 한 DB 안의 변경은 트랜잭션으로 묶지만 외부 첨부 파일 I/O까지 자동 포함하지 않음 |
| 관계·제약 | 고유 ID·참조 유효성·상태 전이를 애플리케이션에서 검증 | PK·UNIQUE·CHECK·NOT NULL·외래 키 활용; 외래 키 활성화 확인 필요 |
| 접근 경계 | 실제 파일 공유·OAuth 범위가 경계. 보호 범위·숨긴 탭은 비밀정보 격리 수단이 아님 | OS 파일 권한과 서비스 인증·인가가 경계. 기본 SQLite에 사용자별 네이티브 RLS를 기대하지 않음 |
| 백업·복구 | 표·파일·관계·권한을 함께 복구할 내보내기와 매니페스트 필요 | 일관된 DB 스냅샷과 첨부 파일을 함께 백업·복원 |
| 비용·운영 | API·저장공간·실행기·계정 플랜·운영 비용과 쿼터 확인 | DB 서버 프로세스는 불필요하지만 호스트·전기·백업·원격 접속·운영 비용은 남음 |

Google 편집기의 오프라인 사용은 사전 설정이 필요하며 에이전트의 클라우드 API 호출을 오프라인으로 실행해 주는 기능이 아니다. SQLite는 애플리케이션이 디스크 파일에 직접 접근한다. [Google 오프라인 안내](https://support.google.com/docs/answer/6388102?hl=en), [SQLite 구조](https://sqlite.org/serverless.html)

SQLite는 여러 읽기와 하나의 쓰기 트랜잭션을 지원한다. WAL도 writer를 여러 개로 늘리지는 않는다. 관계 제약은 스키마에 정의하고, 외래 키는 연결마다 활성화·확인한다. [트랜잭션](https://sqlite.org/lang_transaction.html), [테이블 제약](https://sqlite.org/lang_createtable.html), [외래 키](https://sqlite.org/foreignkeys.html)

SQLite의 권한은 기본적으로 OS 파일 접근 권한이며 `GRANT/REVOKE`가 없다. API를 통한 사용자별·행별 제한은 애플리케이션에서 집행한다. 높은 동시 쓰기·조직별 행 격리·고가용성이 실제 요구일 때 서버 DB를 검토한다. [미지원 기능](https://sqlite.org/omitted.html), [적합한 사용처](https://sqlite.org/whentouse.html)

## 4. 답변으로 구조를 확정하는 셋업 질문

질문을 한 번에 모두 나열하지 않는다. 기존 자료를 먼저 확인하고 현재 결정에 필요한 핵심 질문 하나씩 묻는다. 이미 확인한 사실은 요약해 재사용한다.

1. **“이미 쓰는 표와 파일에서 어떤 업무가 완결되며, 어디에서 끊기나요?”**

	- 허용된 기존 파일의 메타데이터 → 헤더 → 필요한 최소 표본 순으로 조사한다. 자동화·스크립트·트리거의 존재와 실제 성공 증거를 구분한다.
	- 개인: 기존 목표·할 일·자료·아카이브의 관계를 유지할 필요를 확인한다.
	- 기업: 업무 소유자·자료 등급·공유 위치·조직이 허용한 계정과 앱을 먼저 확인한다.

2. **“같은 상태가 서로 다르면 어느 기록을 최종 기준으로 삼아야 하나요?”**

	- `Sheets+Drive 정본`, `SQLite+파일 정본`, `데이터 영역별 정본을 정한 혼합` 중 현재 업무에 맞게 결정한다.
	- 혼합은 `Sheets 정본 → SQLite 검색 캐시`처럼 방향·갱신 주기·삭제 전파·재생성 방법을 기록한다. 같은 업무 상태를 양쪽에서 독립 수정하는 구성을 기본안으로 두지 않는다.

3. **“담당 컴퓨터가 꺼져 있을 때 무엇까지 할 수 있어야 하나요?”**

	- 기존 파일 열기·표 직접 편집·요청 접수·에이전트 실행을 나눠 정한다. 실행을 쉬어도 된다면 상시 클라우드 실행기를 추가하지 않는다.
	- 개인: 휴대폰에서 초안을 남기고 집 실행기가 켜진 뒤 처리해도 되는지 확인한다.
	- 기업: 외부 기기의 조회·입력 허용과 내부 실행기의 처리 권한을 각각 정한다.

4. **“사람과 여러 에이전트가 같은 값을 바꾸면 누구의 변경을 적용하나요?”**

	- 표 직접 편집 허용 열, 입력·검토 영역, 자동화 담당, 충돌 시 보류·재조회 규칙을 결정한다.
	- 자동화 한 곳만 쓰게 해도 사람의 직접 수정은 그 경로를 우회할 수 있다. 통제할 수 없는 동시 수정에 강한 일관성이 필요하면 저장소·편집 방식을 다시 선택한다.

5. **“파일은 저장됐지만 표 등록이 실패하면 어떻게 알아내고 이어가야 하나요?”**

	- 허용 손실 기간·복구 시간·백업 위치·담당자·미완료 대조 주기를 정한다. 실제 복원 시험이 없으면 복구 가능으로 확정하지 않는다.

6. **“요청이 늘거나 무료 한도에 도달하면 기다릴까요, 멈출까요, 비용을 쓸까요?”**

	- 월 작업 수·표 조회 범위·첨부 크기·보존 기간·재시도 횟수로 비용과 지연을 추정한다.
	- 개인: 감수할 대기 시간과 월 상한을 정한다. 기업: 계정 플랜·감사·지원·백업 운영비를 포함한다.

필수 결정이 모이면 허용된 구축으로 넘어간다. 미사용 기능의 세부 규칙 때문에 첫 업무를 막지 않고, 지식·라이프·기업 업무를 여러 개 선택한 경우 전체 범위를 구축 순서에 남긴다.

## 5. 데이터·쓰기·복구 계약

- **식별과 관계**
	- `spreadsheet_id`·탭의 `sheet_id`·레코드 ID·Drive 파일 ID를 구분한다. 정렬·삽입으로 변하는 행 번호와 파일 제목을 고유 ID로 쓰지 않는다.
	- 필요한 표만 고른다. 예: 업무 표의 `record_id / parent_id / status / updated_at`, 문서 표의 `record_id / drive_file_id / content_hash`, 실행 표의 `run_id / request_key / checkpoint / result_id`.
	- 필수 값·고유성·참조 대상 존재·삭제된 대상 참조·허용 상태 전이를 쓰기 전에 검증하고 주기적으로 대조한다. 수식·입력 검증만으로 전체 무결성이 보장된다고 가정하지 않는다.
- **수정 충돌**
	- Sheets `batchUpdate`는 요청 안의 갱신을 함께 적용하지만 협업자의 변경까지 격리하지 않는다. `revision` 열을 읽고 비교한 뒤 쓰는 절차만으로 강한 조건부 갱신(CAS)이 되지는 않는다. [공식 일괄 갱신 계약](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate)
	- 자동화 쓰기를 한 실행 경로로 모으고, 사람이 작성하는 제안·입력과 확정 상태를 분리하는 안을 검토한다. 보호 범위는 실수 방지용이며 사용자 권한·공유 경계를 대체하지 않는다.
	- 확정 상태를 사람이 직접 편집할 수 있으면 재조회·변경 감지·충돌 보류·검토 담당을 둔다. 중복 요청 키 검사도 동시에 우회할 수 있는 쓰기 경로가 있으면 유일성을 보장하지 못한다.
- **표와 파일의 단계별 저장**
	- `pending` 기록에 작업 ID·예정 파일·입력 해시를 남기고 파일 저장 → 실제 ID·크기·지원되는 해시 확인 → 표 참조 등록 → `ready`로 진행한다.
	- 중간 실패 시 같은 작업 ID로 기존 결과를 먼저 찾는다. 업로드 재시도마다 새 파일을 만들거나, 표에 없는 파일을 바로 삭제하지 않는다. 소유자·실행 기록과 대조해 복구·검토 대상으로 분류한다.
	- Drive 업로드와 Sheets 갱신은 하나의 트랜잭션이 아니다. SQLite와 별도 첨부 파일도 같은 문제가 있으므로 두 구성 모두 미완료 단계·끊긴 참조·중복 파일을 대조한다.
- **백업과 삭제**
	- 표 내보내기만으로 Drive 파일·수식·검증 규칙·공유 권한·자동화 설정까지 복구되지는 않는다. 필요한 항목의 매니페스트·파일 사본·설정 기록과 복원 후 ID 재연결 절차를 둔다.
	- 백업 복원 시 이후 삭제·권한 회수 결정을 다시 적용한다. 버전 기록이 있다는 사실만으로 전체 시스템의 복구 목표를 충족했다고 하지 않는다.
	- SQLite는 Online Backup API·`VACUUM INTO` 등으로 일관된 사본을 만들고 첨부와 복구 시점을 맞춘다. 실행 중인 DB 파일을 여러 호스트에서 파일 동기화로 공동 사용하지 않는다. WAL에는 아직 본체에 반영되지 않은 커밋이 있을 수 있고 같은 호스트가 전제된다. [온라인 백업](https://sqlite.org/backup.html), [WAL](https://sqlite.org/wal.html), [네트워크 사용](https://sqlite.org/useovernet.html)

## 6. 서버가 꺼져 있을 때의 동작

Google 서비스·네트워크·계정 권한은 정상이고 해당 에이전트의 담당 서버만 꺼진 상황을 기준으로 한다.

| 행동 | 가능 범위와 표시 |
| --- | --- |
| Sheets·Docs·Drive 직접 조회·편집 | 사용자 권한 안에서 가능. 에이전트가 변경을 반영했다는 뜻은 아님 |
| 표에 요청 입력 | 입력 창구를 설계했다면 저장 가능. 실행기 확인 전에는 `접수 대기` 등으로 표시 |
| 이전 결과·저장 상태 조회 | 가능하되 마지막 확인 시각 표시. 서버의 현재 실행 상태로 단정하지 않음 |
| 에이전트·로컬 도구 실행 | 해당 서버에 의존하는 처리는 불가. 별도 실행기가 실제로 구성된 업무만 독립 실행 |
| 복귀 후 재개 | 저장한 요청 ID·체크포인트·실제 외부 결과·만료·권한을 대조하고 미완료 단계만 처리 |

알림 발송·표의 완료 표시·실제 업무 완료는 업무 시나리오의 완료 근거 규칙을 따른다. 중앙 PC가 꺼졌다는 이유로 다른 에이전트가 작업 소유권을 자동 승계하지 않는다.

## 7. 개인·기업의 접근 경계

- 개인 시스템
	- 선택한 파일 범위로 연결하고 기기 분실·계정 만료·오프라인 사본·공유 링크 회수를 정한다. 개인 Drive와 조직 자료가 같은 색인·검색 결과에 섞이지 않도록 한다.
- 엔터프라이즈 시스템
	- 개인 계정·조직 Workspace·서비스 실행 계정의 책임을 나눈다. 자료 등급별로 파일·저장 위치·허용 앱·외부 모델 전송을 결정한다.
	- 사내/사외 접속 허용, 원본 접근, 결과 조회, 파일 다운로드, 공유 권한 변경을 각각 통제·기록한다. 사외에서 표를 볼 수 있다는 이유로 사내 원문까지 내려받게 하지 않는다.
	- 같은 파일의 숨긴 탭·보호 범위로 고객·부서의 비밀정보를 나누지 않는다. 파일 분리와 실제 ACL을 쓰거나, 요구를 충족하는 서버 DB·API를 선택한다.

Sheets API의 권한 범위는 개별 탭 단위로 제한되지 않는다. 보호 범위도 보안 수단이 아니므로 본문 편집 제한과 비밀정보 열람 제한을 구분한다. 상세 결정은 보안 운영에 연결한다. [API 범위](https://developers.google.com/workspace/sheets/api/scopes), [보호·숨김 안내](https://support.google.com/docs/answer/1218656?hl=en)

## 8. 필요한 경우에만 추가하는 입력·자동화

- **Google Forms**: 정형 입력 창구가 필요하면 응답을 Sheets에 연결한다. 응답을 실행 승인으로 삼으려면 작성자·대상·권한을 별도로 검증한다. Form과 연결 Sheet의 권한 회수는 각각 확인한다. [응답 저장·권한](https://support.google.com/docs/answer/2917686?hl=en)
- **Apps Script**: 가벼운 정기 대조·입력 처리 등이 필요할 때 선택한다. 설치형 트리거는 생성자 계정으로 실행되므로 실행 주체와 계정 변경·회수 담당을 기록한다.
	- API·스크립트로 셀을 썼다고 편집 트리거가 실행되는 것은 아니다. API 갱신 후 명시적 처리 호출 또는 주기적 미처리 조회를 설계한다.
	- 시간 기반 트리거는 정확한 분 단위 실행을 보장하는 스케줄러로 간주하지 않는다. 로컬 서버가 꺼져도 독립 실행되도록 실제 구현·권한을 갖춘 기능만 가능하다. [설치형 트리거](https://developers.google.com/apps-script/guides/triggers/installable)
	- 실행 시간·일일 트리거 시간·호출량·연결 제품 쿼터를 확인한다. 한도 초과로 중단된 일을 성공으로 기록하지 않고 재시도·인계 기준을 둔다. [Apps Script 쿼터](https://developers.google.com/apps-script/guides/services/quotas)

Sheets API는 표준 사용에 추가 비용이 없지만 요청 쿼터가 있으며 공식 문서는 2026년 후반 초과 요청 과금 계획을 안내한다. 영구 무료를 전제로 확장하지 않는다. API·Drive 저장·모델·실행기·운영비는 저비용 서비스 확인 사항과 함께 재확인한다. [Sheets 쿼터·가격](https://developers.google.com/workspace/sheets/api/limits)

## 9. 선택한 구성의 검증과 인계

1. 기존 표 하나와 시험 파일로 `기록 생성 → 파일 저장 → 참조 등록 → 조회 → 수정 → 재조회`를 확인한다. 실제 운영 데이터에 파괴적인 시험을 하지 않는다.
2. 정렬·행 삽입 후 같은 레코드 ID를 찾는지, 중복 요청·없는 참조·금지된 상태 전이를 거절하는지 확인한다.
3. 사람과 자동화의 충돌 및 파일 저장 후 표 등록 실패를 재현하고, 보류·재조회·재개가 중복 결과를 만들지 않는지 확인한다.
4. 담당 서버 중지·기기 전환·재가동 시 저장 상태와 실제 실행 상태를 구분하고 같은 작업을 이어가는지 확인한다.
5. 허용되지 않은 계정·범위에서 원문·첨부·파생 결과를 읽을 수 없는지 확인한다. 권한 회수·삭제가 캐시·공유 결과에 반영되는지 확인한다.
6. 별도 시험 위치에 백업을 복원하고 레코드·파일 연결·삭제 정책을 대조한다. 완료 근거와 남은 제한을 검증 기록에 남긴다.

실측한 조회 지연·동시 수정·실패율·비용·복구 시간이 요구를 충족하면 기존 구성을 유지한다. 충족하지 못하는 요구가 드러날 때만 쓰기 경로 개선·캐시·서버 DB 전환을 검토한다. 전환 시 정본 변경 시점, ID 보존, 미완료 작업 인계, 검증·되돌리기 절차를 먼저 확정한다.
